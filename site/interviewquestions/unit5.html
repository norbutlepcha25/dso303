    Unit 5: Interview Questions¶

    5.1 AWS CI/CD Services: CodeCommit, CodeBuild and CodeDeploy¶

    Conceptual Questions¶

    1. Distinguish continuous integration, continuous delivery and continuous deployment, and explain what each additionally requires.

    Continuous integration is a development practice: every developer merges to the mainline at least daily and every merge triggers an automated build and test. Its requirements are a fast, trustworthy test suite and a branching model with short-lived branches trunk-based development because long-lived feature branches recreate exactly the deferred-integration cost that CI exists to eliminate. Continuous delivery adds that every change passing the pipeline is deployable to production at any moment, so releasing becomes a business decision rather than an engineering project. It additionally requires automated deployment, meaningful environment parity, and changes that are reversible which in practice means backward-compatible schema migrations, because an irreversible migration silently removes the deployability guarantee. Continuous deployment removes the human gate entirely: every passing change goes to production automatically. It additionally requires confidence that the tests genuinely gate quality, progressive delivery so exposure is gradual, and automated rollback driven by a signal that reflects user experience. The practical distinction I would draw for a team is that the step from integration to delivery is mostly technical, while the step from delivery to deployment is mostly organisational and that stopping at continuous delivery with a real approval is perfectly defensible, provided the approval is a genuine decision and not a signature from someone with no information on which to refuse.

    2. Why is build-once-deploy-many a correctness requirement rather than an efficiency optimisation?

    Because if you build separately per environment, the artefact you tested in staging is not the artefact you deployed to production, and therefore none of your staging verification applies to what is running. The divergence sources are mundane and common: an unpinned transitive dependency publishing a patch release between the two builds, a floating base image tag changing under you, a different toolchain version on a different build agent, or any non-deterministic step such as a timestamp or a resolved "latest". The efficiency argument one build instead of three is real but secondary. The correctness argument is that build-once gives you a property worth a great deal during an incident: since the binary in production is byte-identical to the one that passed staging, any behavioural difference must come from configuration or data, which eliminates an entire hypothesis space in the first five minutes. The implementation requirements follow directly: artefacts must be immutable and content-addressed, so deploy by digest rather than by a mutable tag; all environment-specific behaviour must be injected at deployment time through environment variables, Parameter Store or AppConfig; and the pipeline must promote a specific artefact identifier rather than rebuilding from a branch name. A pipeline stage whose first action is docker build before deploying to production has violated this, however the stage is labelled.

    3. Explain the CodeDeploy lifecycle hooks and why ApplicationStop is the source of so many stuck deployments.

    On EC2 and on-premises the order is ApplicationStop, DownloadBundle, BeforeInstall, Install, AfterInstall, ApplicationStart, ValidateService, where DownloadBundle and Install are reserved for CodeDeploy itself. On ECS and Lambda, which are blue/green only, the order is BeforeInstall, Install, AfterInstall, BeforeAllowTraffic, AllowTraffic, AfterAllowTraffic. ApplicationStop is the troublesome one because it runs from the previously deployed revision, not the one being deployed which is logically necessary, since the point is to stop the currently running application, and only the old revision knows how. The consequence is that if you deploy a revision with a broken ApplicationStop script, every subsequent deployment attempts to run that broken script first and fails before the new code is ever downloaded. The deployment appears stuck for reasons that are invisible in the new revision's source. The remedies are to make the script idempotent and tolerant of a stopped application a stop on a dead process should exit zero to keep it minimal, and, when already stuck, either to remove the script from the instance's last-successful-deployment directory or to redeploy with the option to ignore ApplicationStop failures. I would add that ValidateService on EC2 and BeforeAllowTraffic on ECS and Lambda are the hooks that carry the real value: they are where automated verification runs, and on ECS and Lambda that verification happens before a single user reaches the new version.

    4. Why is rollback capability more important than test coverage for safe frequent deployment?

    Because they bound different things. Testing reduces the probability that a change is bad, and it can only reduce it for failure modes someone anticipated. Rollback bounds the cost of a bad change, and it does so regardless of why the change was bad including the interaction with real traffic, real data volumes, a third party's behaviour, or a race condition that appears only at production concurrency. Empirically, those unanticipated categories are where most production failures come from, which is precisely the set that testing cannot address by construction. The quantitative version is the argument for blue/green: with an in-place deployment, recovery means redeploying the previous version, which takes as long as a deployment and is performed under pressure; with blue/green plus a CloudWatch alarm, recovery is a traffic shift measured in seconds and it happens without a human. That difference in mean time to restore is what makes deploying twenty times a day safer than deploying monthly, because the expected damage is the failure rate multiplied by the duration, and frequent small deployments cut both terms. The corollary I would emphasise is that anything destroying rollback capability is a more serious defect than a gap in test coverage an irreversible database migration being the canonical example, since it disables the property silently and only reveals itself at the moment you need it.

    5. What makes a build role dangerous, and how should build and deploy identities be structured?

    A build executes arbitrary code: your repository's build scripts, plus the install hooks and runtime code of every dependency and transitive dependency it downloads typically hundreds of packages from authors you have never evaluated. All of it runs with the build container's credentials, available at the container credential endpoint. So the build role's permissions are effectively granted to your entire dependency tree and to anyone who can merge to a branch that triggers a build. If that role can deploy to production or modify IAM, then a single compromised transitive dependency is a full account compromise, and the attack requires no sophistication: read the credential endpoint, call an API. The correct structure separates identities by function. The build role may read the source, write to one specific artefact location, push to one specific ECR repository, and read named parameters nothing else, and specifically no ability to change running infrastructure. A separate deploy role is assumed by the pipeline's deploy stage, which executes a much smaller and more reviewable surface of code, and which is what holds the power to change production. In a stronger setup the deploy role lives in a different AWS account entirely, so the boundary is an account boundary rather than a policy. I would add three supporting controls: no long-lived credentials in the build environment at all, secrets referenced from Secrets Manager rather than set as environment variables, and privileged mode enabled only on the projects that genuinely build images.

    Scenario Questions¶

    1. A team's pipeline has grown from eight to forty minutes. Developers have started batching changes. Diagnose and fix.

    The symptom matters as much as the cause: batching is a rational response to slow feedback, and it raises change failure rate months later through a mechanism nobody will connect back to build duration so this is a reliability problem, not a convenience one. I would start by reading CodeBuild's per-phase timings rather than guessing, because in most projects the time is concentrated in one phase and optimising elsewhere achieves nothing. The usual findings, in the order I would check them: no dependency cache, so every build redownloads everything fix with a cache keyed on the lockfile hash; a Dockerfile that copies source before installing dependencies, invalidating the dependency layer on every commit fix by reordering so layers change in increasing frequency, with source last; sequential stages that have no ordering dependency lint, unit tests and image build often need not be serial, and CodeBuild batch builds or parallel pipeline actions express that; a test suite that has accumulated slow integration tests in the unit-test stage split them, running the fast ones on every commit and the slow ones on the mainline; and queue time rather than build time, which is the only finding that justifies reserved-capacity fleets and which teams frequently assume without measuring. I would also check whether the build is on x86 where ARM/Graviton would serve, since that is usually both cheaper and faster, and whether compute is right-sized a larger instance that halves the build costs the same per build and delivers feedback twice as fast. Finally I would set a build-duration alarm, because this degradation happened gradually and silently, and without a threshold it will happen again.

    2. A deployment succeeded, the dashboards are green, and customers report errors. Walk through the investigation.

    Green dashboards with unhappy customers is the gray-failure pattern from chapter 4.3, and the first question is what the deployment's success criterion actually measured. Almost always the answer is a container or instance health check, which proves a process started and a port answers not that the application works. So my first action is to look at user-visible metrics rather than infrastructure metrics: error rate by endpoint, latency percentiles, and a business outcome such as checkout completion, compared against the pre-deployment baseline with the deployment marker overlaid. If those are degraded, I roll back immediately and investigate afterwards with blue/green that is a traffic shift and costs almost nothing, so there is no reason to diagnose first. If they look fine in aggregate, I would look for a partial failure: one endpoint, one tenant, one Region, or one path exercised only by a subset of users, which aggregate metrics hide. Then the causes, in likelihood order: a configuration difference between staging and production, since the artefact is identical if build-once is being followed and configuration is therefore the remaining variable; a schema or data difference, where production has data shapes staging did not; a dependency the new version calls differently, perhaps under different credentials; and mixed-version incompatibility, if the deployment left both versions running and they disagree about a message format or a cache key. The corrective actions afterwards are structural: replace the health check with a real smoke test in BeforeAllowTraffic that exercises a genuine request path over the test listener, and add a CloudWatch alarm on the metric that was actually degraded, wired to automatic rollback because this incident's real finding is that nothing was watching the thing that mattered.

    3. Your organisation requires that no single person can both write and deploy code to production. Design the pipeline.

    Separation of duties here has to be enforced by identity and permission, not by process documentation, because a process that a determined or compromised individual can bypass is not a control. I would build it in four layers. At the source: branch protection on main so that no direct push is possible, enforced by IAM conditions on codecommit:GitPush with codecommit:References, or by provider-side protection for GitHub; an approval rule template requiring at least one approval from a defined pool; and, where the requirement is strict, a rule that the author cannot approve their own pull request. At the build: a build role that can read the source, write artefacts and push to ECR and that explicitly cannot deploy, so that even a compromised build cannot reach production. At the deploy: a separate role assumed only by the pipeline's deploy stage, and for a strong boundary, production in a separate AWS account with a cross-account deployment role that trusts only the pipeline's role. This turns the separation from a policy statement into an account boundary. At the gate: a manual approval action before the production stage whose approver group is defined in IAM and excludes the change's author, with the approval recorded in CloudTrail against a named identity. I would add two things that are usually forgotten. First, alarm on out-of-band changes a CloudTrail event for ecs:UpdateService or lambda:UpdateFunctionCode from any identity other than the deploy role should page someone, because otherwise the whole structure can be walked around with one CLI command. Second, a documented break-glass path with elevated access that is time-bounded, heavily audited and alarmed on use, because emergencies will happen and an undocumented workaround is worse than a controlled one.

    4. A team wants to move from monthly releases to daily deployment. What must change, and in what order?

    The mistake would be starting with the pipeline, because the pipeline is rarely the binding constraint. I would sequence it by what blocks what. First, make changes reversible. Audit the last year of database migrations; if any were destructive, establish expand-and-contract as the standard and practise it, because without reversibility every later step increases risk rather than reducing it. Second, make changes small. Move to trunk-based development with short-lived branches and feature flags via AppConfig, so that incomplete work can ship disabled. This is the organisational change and it is usually the hardest. Third, build the signal. Define what "the deployment is bad" means in metrics a user would feel error rate, latency, a business outcome and create the alarms. Without this, gradual rollout decides nothing and automated rollback cannot exist. Fourth, make deployment reversible in seconds: blue/green or canary with automatic rollback on those alarms. Fifth, automate the path: the pipeline itself, defined in code, with the build and deploy identities separated. Sixth, reduce the batch size progressively weekly, then twice weekly, then daily measuring change failure rate at each step, and treating a rise as a signal to fix the gap rather than to retreat. I would also establish the four DORA metrics as a baseline at the start, because the case for continuing will need evidence, and because the counter-intuitive claim being made that deploying more often reduces failures is only believable with data from their own system. The thing I would explicitly not do is add approval gates to compensate for nervousness: gates encourage batching, and batching is the thing actually causing the risk.

    Architecture Questions¶

    1. Design a complete delivery pipeline for a containerised microservice on ECS, and justify each decision.

    Source and gate. A Git repository with main protected: no direct pushes, at least one approval from someone other than the author, and a required status check. The pull request is the only path to production, which makes the audit trail complete by construction rather than by policy.

    Build. A CodeBuild project on ARM/Graviton compute, triggered on merge to main. The buildspec runs npm ci against a committed lockfile, then lint, then unit tests with a JUnit report, then a vulnerability scan that fails the build on critical findings, then docker build from a Dockerfile whose base image is pinned by digest and whose layers are ordered so source is copied last. The image is tagged with CODEBUILD_RESOLVED_SOURCE_VERSION, pushed only if $CODEBUILD_BUILD_SUCCEEDING is 1, and its digest is emitted as an exported variable. An SBOM is generated and stored alongside. Caching is keyed on the lockfile hash. The build role can read source, read named parameters, write the artefact bucket and push to exactly one ECR repository and cannot deploy.

    Artefact custody. ECR with tag immutability enabled, enhanced scanning through Amazon Inspector, a lifecycle policy retaining tagged releases and expiring untagged images after a short window, and AWS Signer signing the image so provenance is verifiable rather than assumed.

    Deployment. Promotion by digest, never by tag, through development, staging and production. Production uses blue/green either CodeDeploy or ECS native, and I would choose ECS native for an ECS-only estate and CodeDeploy where one deployment model spans EC2, Lambda and ECS. The green task set registers with a second target group and is validated in BeforeAllowTraffic by a Lambda making real requests over a test listener, not by a container health check. Traffic then shifts 10 per cent for a five-minute bake, with a CloudWatch alarm on checkout error rate and p99 latency authorised to roll back automatically, then 100 per cent, with a fifteen-minute termination wait so manual rollback stays instant.

    Configuration and release. Nothing environment-specific in the image. Configuration from Parameter Store and secrets from Secrets Manager, injected as task-definition references. Feature flags in AppConfig, so release is separate from deployment and the fastest incident mitigation is a configuration change rather than a deploy.

    Identity. Distinct roles for source, build and deploy; production in a separate account with a cross-account deploy role trusting only the pipeline.

    Observability. Deployment markers overlaid on application dashboards; alarms on rollback triggered, mainline build failure, deployment failure rate and build duration; CloudTrail alarms on any production mutation by an identity other than the deploy role. Schema discipline. Expand and contract on every migration, because two versions run simultaneously by construction and because rollback is the property the whole design exists to preserve.

    2. Design the build and artefact strategy for a monorepo containing twelve services, where a typical commit touches one of them.

    The defining constraint is that building everything on every commit wastes most of the compute and, worse, makes feedback slow enough that developers batch changes. So the design centres on change detection and on artefact identity.

    Change detection. Webhook filter groups on file paths, so a commit touching services/orders/** triggers only the orders pipeline. For shared libraries the dependency is real, so libs/common/** must trigger every service that depends on it which requires a dependency graph rather than a path list, and I would generate that from the build tool (Nx, Turborepo, Bazel, or a language-native equivalent) rather than maintaining it by hand, because a hand-maintained list will be wrong within a month and will be wrong silently.

    Artefact identity. Each service produces its own image, tagged with the commit SHA of the monorepo, not a per-service version. That keeps traceability simple: one SHA identifies the state of everything. Since a commit only rebuilds affected services, some services' current image will carry an older SHA, and that is correct it means they genuinely did not change.

    Build execution. A CodeBuild batch build fanning out per affected service, running them in parallel, with a shared dependency cache keyed on the relevant lockfile. Lambda compute for the fast checks (lint, type-check) and EC2-based compute for the image builds that need a Docker daemon.

    Pipelines. One pipeline per service rather than one giant pipeline, so that a failing deployment of one service does not block the others, and so that each service's deployment configuration and alarms are its own. The trade-off accepted is more pipeline definitions to maintain, which I would mitigate by generating them from a shared construct in CDK pipeline as code, with one definition and twelve instantiations.

    The failure mode to design against. Change detection that is subtly wrong produces a service that was not rebuilt when it should have been, which surfaces much later as an inexplicable production difference. So I would add a scheduled full build nightly that rebuilds everything and compares digests, catching drift between what the graph believed and what is true. This is cheap insurance for the one failure mode of this design that is otherwise invisible.

    3. Design the deployment strategy for a Lambda-based API where a bad change would be expensive, and explain how you would know it was bad.

    The mechanism is Lambda's alias-based weighted routing, which is what CodeDeploy's Lambda platform drives. Each deployment publishes a new version immutable by construction and the alias that the API Gateway integration points at shifts weight between the old and new versions. Nothing about the old version is destroyed, so rollback is a weight change taking effect in seconds.

    Strategy. Canary10Percent5Minutes for a normal change: 10 per cent of invocations for five minutes, then the remainder. For a change touching anything payment-related I would use a longer canary or a linear configuration, because the relevant failures may be low-frequency and a five-minute window may not contain one.

    How I would know it was bad is the more important half of the question, and it has three parts. First, the pre-traffic gate: a BeforeAllowTraffic hook Lambda invoking the new version directly with a set of known-good and known-bad inputs and asserting the responses. This catches gross breakage before any user is exposed, and it is a real functional test rather than a health check. Second, the canary signal: CloudWatch alarms on the new version's metrics specifically using the version dimension, not the function aggregate, which is the detail teams get wrong, because a 10 per cent canary failing completely moves the function-level error rate by only a few per cent and may not cross a threshold. I would alarm on the new version's error rate, its p99 duration, and a business metric published by the function itself, such as successful authorisations. Third, the bake time must exceed the alarm's evaluation window, or the shift to 100 per cent completes before the alarm can possibly fire which produces a canary that looks like a safety mechanism and is not.

    Supporting decisions. Automatic rollback enabled on alarm, on hook failure and on stopped deployment. Provisioned concurrency on the alias if cold-start latency is user-visible, remembering that it must be configured on the version being shifted to or the canary measures cold starts rather than the change. Feature flags via AppConfig for anything whose risk is behavioural rather than structural, because disabling a flag is faster than any deployment mechanism. And, because this is an API, contract tests in the pipeline against the published schema, since the failure mode that hurts most in an API is a breaking change that is entirely healthy from the server's point of view.

    Troubleshooting Questions¶

    1. A CodeDeploy deployment has been stuck at "In Progress" for an hour with no lifecycle event completing. Diagnose.

    Stuck with no event completing, as opposed to a failing event, points at the agent or at reachability rather than at the deployment content. On EC2 the sequence I would check is: is the CodeDeploy agent running on the target instances, and can it reach the CodeDeploy service endpoint either through a route to the internet or through a VPC endpoint? A recently changed security group, NACL or route table is a common cause, as is an agent that stopped and was never restarted after a patch cycle. Does the instance profile permit reading the revision from S3, including kms:Decrypt if the bundle is encrypted with a customer-managed key a missing KMS grant produces exactly this symptom, because the agent cannot download and therefore never reports progress. Is the instance actually in the deployment group's target set, by tag or Auto Scaling group; an instance whose tags changed silently drops out. Is a lifecycle script hanging without hitting its timeout the agent log at /var/log/aws/codedeploy-agent/codedeploy-agent.log and the deployment logs at /opt/codedeploy-agent/deployment-root/ are definitive here, and a script waiting on input or on a network call with no timeout is the usual finding. And specifically, is ApplicationStop from the previous revision hanging the hook that runs from the old deployment and is invisible in the new revision's source. On ECS the equivalent checks are different: whether the green task set is failing to reach a steady state because tasks cannot pull the image, cannot resolve a secret, or are failing their target-group health check in which case the deployment waits rather than failing, and the ECS service events are where the real error is. The systemic lesson is to set hook timeouts deliberately and a deployment timeout overall, so that "stuck" becomes "failed with a reason" without an hour of human attention.

    2. Builds pass in CodeBuild but the same commit fails when a developer builds locally or the reverse. Diagnose.

    A difference between two builds of the same source means something outside the source differs, and there are only a few candidates. Dependency resolution: if the build uses npm install rather than npm ci, or a lockfile is not committed, the two builds resolve different versions this is the most common cause and it is also intermittent, which makes it maddening. Base image or toolchain version: a floating tag such as node:20 or a CodeBuild managed image that was updated resolves differently from the developer's local version; pinning by digest removes it. Environment variables: values present in the CodeBuild project, from Parameter Store or Secrets Manager, that the developer does not have or the reverse, where a developer's local .env makes something work that the pipeline lacks. Cache state: a stale CodeBuild cache serving artefacts from an older dependency set, which is why cache keys should derive from the lockfile. Architecture: an ARM build container versus an x86 laptop, or the reverse, where a native dependency compiles differently. Case sensitivity: a macOS developer's case-insensitive filesystem tolerating an import of ./Utils for a file named utils.js, which fails on the build container's Linux filesystem a genuinely common and very confusing one. Network: a VPC-configured build project without a NAT path or endpoints failing to reach a registry the developer can reach. My diagnostic order would be to compare resolved dependency trees first, then the image digest and toolchain versions, then the environment, and to fix the class rather than the instance: commit lockfiles, use ci installs, pin base images by digest, and give developers a way to run the build in the same container image locally, which removes this category of question permanently.

    3. Following a deployment, error rates rose but the automatic rollback did not trigger. Describe your response and the fix.

    First, roll back manually with blue/green that is a traffic shift and there is no reason to investigate while customers are affected. Then the question is why the automation did not act, and there are five candidates worth checking in order. Was an alarm configured on the deployment group at all? Automatic rollback on alarm requires the alarm to be attached; a canary configuration alone does nothing. Did the alarm measure the right thing? An alarm on CPU or on invocation count will not move for an application-level failure; it must watch error rate, latency or a business outcome. Was the alarm scoped to the new version? This is the subtle one: on a 10 per cent Lambda canary or a 10 per cent ECS traffic shift, a completely broken new version moves the aggregate error rate by roughly 10 per cent, which frequently sits below a threshold set for the whole service. The alarm must use the version or target-group dimension so it sees the canary's own error rate, which would be near 100 per cent. Did the bake time exceed the alarm's evaluation window? With a five-minute alarm say two evaluation periods of one minute plus reporting delay and a one-minute bake, the shift to 100 per cent completes before the alarm can possibly enter ALARM. Was the alarm treating missing data as breaching or not breaching? A new version publishing no data yet, with treat-missing-data set to notBreaching, looks healthy precisely when it is most broken. The fix is usually two or three of these together, and I would verify it the way chapter 4.3 argued for: deliberately deploy a known-bad change to a pre-production environment and confirm the rollback fires, because a rollback path that has never been exercised is not a rollback path. I would also add an alarm on "rollback triggered" itself, so the next time it works, someone knows.

    Certification-style Questions¶

    1. A company deploys a containerised application to Amazon ECS and must be able to revert within seconds if error rates rise. Which approach meets the requirement with the least operational overhead?

    A. An ECS rolling update with a higher minimumHealthyPercent B. A blue/green deployment with a CloudWatch alarm configured for automatic rollback C. Rebuild the previous image and redeploy when errors are detected D. Increase the ECS service's desired count before each deployment

    Answer: B. Blue/green keeps the previous task set running, so rollback is a listener weight change taking seconds, and the alarm makes it automatic. A still replaces tasks in place, so reverting means another rolling deployment. C is a rebuild, which both violates build-once-deploy-many and takes minutes. D adds capacity without changing the deployment mechanism.

    2. A CodeBuild project pushes an image to Amazon ECR in its post_build phase. The team notices images in ECR from builds whose unit tests failed. What is the cause?

    A. ECR tag immutability is disabled B. post_build executes regardless of whether build succeeded, and the push is not guarded C. The build role has excessive permissions D. The buildspec version is 0.1

    Answer: B. post_build runs even after a failing build phase; the push must be conditional on $CODEBUILD_BUILD_SUCCEEDING. A affects whether tags can be overwritten, not whether a push occurs. C is a genuine concern but not this symptom. D is unrelated.

    3. Which statement about AWS CodeDeploy deployment types is correct?

    A. In-place deployments are supported for EC2, Lambda and ECS B. Blue/green is supported only for EC2 C. Lambda and ECS support blue/green only; EC2/On-premises supports both in-place and blue/green D. Canary deployments are an alternative to blue/green and use a single environment

    Answer: C. Lambda shifts traffic between alias versions and ECS between target groups both inherently blue/green. D is wrong in a way worth remembering: canary and linear are traffic-shifting configurations on top of blue/green, and they require both versions to be running.

    4. A deployment uses Canary10Percent5Minutes with a CloudWatch alarm on the ECS service's overall 5xx rate at a 5 per cent threshold. A completely broken version is deployed and the rollback does not fire. Why?

    A. The canary percentage is too low for the alarm to detect the failure B. Canary deployments do not support automatic rollback C. The alarm's period is too short D. CloudWatch alarms cannot trigger CodeDeploy rollbacks

    Answer: A. With only 10 per cent of traffic on the broken version, the service-wide 5xx rate rises to roughly 10 per cent of requests failing near the threshold and easily below it depending on baseline while the canary itself is failing nearly every request. The alarm must be dimensioned on the green target group so it observes the new version's own error rate. B and D are false; C is not the defect described.

    5. A security review finds that a compromised npm dependency could deploy to production. Which change most directly addresses this?

    A. Enable ECR image scanning B. Separate the build role from the deploy role, removing deployment permissions from the build C. Enable CodeCommit approval rule templates D. Turn on CloudTrail for the build account

    Answer: B. The dependency executes with the build role's credentials, so the direct fix is that the build role cannot deploy. A detects known vulnerabilities but does not bound what a build can do. C strengthens the human path to production but not the machine one. D records the compromise rather than preventing it.

    6. A team builds a separate container image for staging and for production from the same commit. Staging passes; production fails. What is the architectural defect?

    A. Insufficient test coverage in staging B. Building per environment means the artefact tested is not the artefact deployed C. The production environment needs more capacity D. The deployment configuration is AllAtOnce

    Answer: B. Two builds of the same commit can differ through unpinned dependencies, a changed base image or a different toolchain. Build once and promote the identical artefact with injected configuration. A, C and D may all be true in general but none explains a failure that staging could not have caught.

    5.2 CI/CD Pipelines with CodePipeline and Amazon ECR¶

    Conceptual Questions¶

    1. Explain why a pipeline must promote one artefact rather than rebuild per environment, and what breaks when it does not.

    Because rebuilding means the thing verified in staging is not the thing running in production, so none of your staging evidence applies. The divergence sources are mundane: an unpinned transitive dependency publishing a patch release between builds, a floating base image tag resolving differently, a different toolchain on a different build host, or any non-deterministic step. The retail example is the canonical one two builds forty minutes apart from an identical commit, one working and one not. What breaks is subtle and severe: every gate in the pipeline becomes evidence about an artefact that no longer exists. The implementation requirements follow directly. Build once and emit an immutable, content-addressed artefact a digest, not a tag. Deploy by that digest, so what runs is fixed at deployment time rather than resolved whenever a task happens to launch. Move every environment difference into configuration injected at deploy time. And, for multi-account and multi-Region estates, use replication rather than a per-Region build, because that is precisely where organisations abandon the principle for convenience. The diagnostic value is what I would emphasise: when the production binary is byte-identical to the one that passed staging, any behavioural difference must come from configuration or data, which eliminates an entire hypothesis space in the first five minutes of an incident.

    2. Explain the difference between push and pull deployment for Kubernetes and why it matters beyond preference.

    In a push model an external pipeline holds credentials to the cluster and applies changes to it. In a pull model an agent inside the cluster watches a Git repository and reconciles the cluster toward what is declared there. Three differences matter structurally rather than stylistically. Credentials and network direction: push requires inbound reachability to a frequently private API server and an IAM-to-RBAC mapping held by an external system, so the pipeline is inside the cluster's threat model; pull requires only outbound access from the cluster to Git and the registry, and no external system holds cluster credentials at all. Drift: a push pipeline knows only what it last pushed and has no representation of current state, so a manual kubectl change during an incident is invisible and permanent which is how clusters that are supposed to be identical quietly diverge. A reconciliation loop compares declared against actual continuously and either corrects the difference or reports it immediately. The logistics example in this chapter found that this, rather than deployment speed, was the main benefit of migrating. Source of truth: with push, the answer to "what should be running" is ambiguous between the cluster and the last pipeline run; with pull it is unambiguously the repository, and the Git history is the deployment history diffable, signed if you require it, and answering "what was declared on 14 March" with a checkout. The costs are real: a second repository whose write access is now production deployment access and must be protected accordingly, a reconciliation delay, and a controller to operate though the EKS Capability for Argo CD, announced in November 2025, makes that controller AWS-managed and removes most of the last objection.

    3. What do stage conditions provide that a Lambda action does not, and which condition would you add first to a production pipeline?

    Functionally a Lambda action can implement any check, so the difference is not capability it is that conditions are declarative, reviewable and consistent. A Lambda gate is code each team writes slightly differently, with its own failure modes, its own permissions, its own deployment lifecycle, and its own bugs; three teams produce three implementations of "check whether an alarm is firing". A condition with an alarm rule is four lines of configuration that a reviewer can evaluate at a glance, that cannot fail for reasons unrelated to the check, and that behaves identically everywhere. Conditions also attach at points a Lambda action cannot express cleanly: an entry condition evaluated before the stage begins, an on-success condition after it completes, and an on-failure condition that can trigger rollback whereas an action only exists inside the stage's sequence. The one I would add first, without hesitation, is an entry condition with an alarm rule on the production stage: do not enter production if production is currently unhealthy. It prevents a compounding failure that is common and expensive a team is mid-incident, an unrelated merge triggers a pipeline, and a deployment lands in the middle of the investigation, destroying the correlation between what changed and what broke and turning one problem into two. It costs nothing, needs no code, and removes an entire category of human coordination that otherwise depends on someone remembering to disable a transition.

    4. Why is deploying by image digest rather than tag a correctness property rather than a stylistic preference?

    Because a tag is a mutable pointer resolved at pull time, and pulls happen continuously not only at deployment. When an ECS task definition or a pod spec references repo:stable, every task or pod launch resolves that tag independently: at deployment, at every autoscaling event, and at every replacement of a crashed task. If the tag is repointed between those moments, the fleet runs a mixture of versions non-deterministically, and nothing in any dashboard reports this. The media-company incident in this chapter is exactly that: a "rollback" performed by repointing a tag produced twenty minutes of two versions serving simultaneously, with the mix depending on when each task happened to start. A digest is derived from the image's content, so it cannot be repointed by construction; a task definition referencing repo@sha256:9f2c… is a statement of fact whose truth does not depend on when it is evaluated. Three supporting controls make this robust rather than aspirational: tag immutability on the repository, so a tag once written cannot be repointed at all and the failure mode is prevented rather than merely avoided; tagging with the commit SHA, so the artefact remains traceable to source even though deployment uses the digest; and lifecycle policies that never expire a referenced image, because deploying by digest is only as durable as the image's continued existence an expired digest makes task replacement fail, which is a data-plane failure rather than a delivery one.

    5. Why are ECR pull failures a different class of problem from the other failure modes in this chapter?

    Because everything else here fails safely in the sense that it delays a release without affecting what is already serving. A broken pipeline, a failed build, a rejected approval, a rolled-back deployment in all of those, the previously running version continues to serve. An ECR pull failure is not like that, because image pulls are on the runtime path for ECS task replacement and Kubernetes pod scheduling, not only for deployment. If the registry becomes unreachable or an image disappears, then autoscaling cannot add capacity under load, a crashed task cannot be replaced, a node replacement permanently loses its pods, and a rollback to a previous version fails if that version's image was expired. The service appears healthy right up until the moment it needs to launch something, which is typically the moment it is under stress. The causes worth designing against are specific: a lifecycle policy expiring an image a live task definition still references, which is the most common and entirely self-inflicted; missing VPC endpoints and specifically having ecr.api and ecr.dkr but not the S3 gateway endpoint, which produces a successful authentication followed by a layer-download timeout; cross-Region pulls adding latency and a dependency on another Region, which replication fixes; and a pull-through cache whose upstream is rate-limiting, which reintroduces a public registry as a production dependency. The design conclusion is that the image pull path deserves the same availability analysis as a database or any other runtime dependency, which is not how most teams treat a registry.

    Scenario Questions¶

    1. A team's pipeline deploys to staging and production from separate builds off the same commit. They want to fix this. Walk through the change.

    The change is conceptually simple and organisationally larger than it looks, so I would sequence it. First, establish artefact identity. Enable tag immutability on the ECR repository, tag every image with the full commit SHA, and capture the digest as a pipeline variable from the build action. This is the foundation; nothing else works without it. Second, find what actually differs between environments, because there is always something the second build was doing. Typically it is a build-time environment variable baking an API endpoint, a different configuration file copied in, or a NODE_ENV-style flag changing what gets compiled. Each of these must move from build time to deployment time into task definition environment variables, Parameter Store or AppConfig. This is the real work and it is where the migration usually stalls, because something is genuinely compiled in. Third, restructure the pipeline: one build stage producing one artefact, then deploy stages consuming the same digest through a variable reference. Remove the second build project entirely rather than leaving it unused, so nobody reinstates it. Fourth, handle multi-account and multi-Region if present: ECR replication rules or a repository policy granting pull to the other accounts, so they consume the identical digest rather than rebuilding for access reasons. Fifth, verify it: assert in a deploy-time gate that the digest deployed to production is the digest that passed staging, which converts the guarantee from a design intention into a checked precondition. I would also raise the thing this usually reveals: if the environments needed different builds, the application probably has environment knowledge compiled into it, and that is worth fixing on its own merits regardless of the pipeline.

    2. An EKS deployment pipeline reports success but the change is not live. Diagnose and redesign.

    The symptom is diagnostic: the pipeline's success criterion is wrong, not its execution. Almost certainly a CodeBuild stage runs kubectl apply and treats exit code zero as success but kubectl apply returning zero means only that the API server accepted and persisted the object, which is a long way from the workload being healthy and serving. The fintech example in this chapter is exactly this: a namespace typo created a Deployment somewhere nothing routed to, and the pipeline was green for three days. I would check, in order: is the object where it should be, since a wrong namespace or a wrong cluster context is the commonest cause; did the rollout actually complete, which kubectl rollout status --timeout would have caught, as pods can be created and then crash-loop, or be Pending forever because nothing can schedule them; is the image pullable, since ImagePullBackOff produces a perfectly successful apply and no running pods; and is anything routing to it, because a Service whose selector does not match the pods' labels is healthy, green, and receives nothing. The redesign has two levels. The minimum fix is to make the stage verify rather than assume: kubectl rollout status with a timeout, followed by a smoke test against the Service the same argument chapter 5.1 made about health checks versus smoke tests, in a Kubernetes idiom. The better fix is to stop pushing: with GitOps, health assessment is what the controller does continuously, so Argo CD reports Synced and Healthy as separate facts, and Degraded is visible immediately rather than three days later. That also removes the cluster credentials from the pipeline and gives drift correction, which this team almost certainly also needs given that nobody noticed for three days.

    3. A cross-account pipeline that has worked for six months starts failing with an S3 access-denied error on the deploy stage. Nothing about S3 changed. Diagnose.

    An access-denied on S3 in a cross-account pipeline is, in my experience, more often a KMS problem than an S3 problem, because the deploying role must both read the object and decrypt it, and a kms:Decrypt failure surfaces as a failure to read the object. So I would check the artefact store's KMS key policy first, specifically whether the target account's deployment role still has kms:Decrypt and kms:DescribeKey. The bank example in this chapter is precisely this: a key rotation created a new key, the pipeline's own role was updated, and the cross-account role's grant on the old key was never carried across. Other candidates, in order: the artefact bucket policy no longer granting the target account's role someone tightening bucket policies organisation-wide is a common trigger; the cross-account role's trust policy changed, perhaps by adding a condition such as an external ID or a source-ARN requirement that the pipeline does not satisfy; a service control policy newly applied at the organisational unit denying the action, which is invisible from within the account and produces a denial that looks like a resource-policy problem; and the pipeline role's own identity policy, though that is least likely if nothing in the tooling account changed. The diagnostic that settles it quickly is the IAM policy simulator or a CloudTrail lookup for the denied event, because the CloudTrail record names the service that denied kms.amazonaws.com versus s3.amazonaws.com which resolves the ambiguity the error message creates. The structural lesson I would draw is that cross-account delivery has three coupled permission surfaces and the KMS one is both the most forgotten and the one whose failure points elsewhere, so it belongs in the runbook explicitly.

    4. Your organisation runs forty microservices on EKS across four clusters and three accounts, with a push-based pipeline per service holding cluster credentials. Design the migration to GitOps and state what you expect to find.

    The migration is straightforward; what it reveals usually is not. Design. A manifest repository I would start with one repository containing a base per service and Kustomize overlays per cluster, because separate repositories per environment add access-control precision that most organisations do not yet need and definitely add synchronisation pain. Argo CD deployed through the EKS Capability, so the controller is AWS-managed rather than another thing to upgrade and keep available. An App of Apps root application per cluster, so bootstrapping a cluster is one application definition. Each service's existing pipeline keeps its build and its ECR push, and its deploy stage is replaced by a commit to the manifest repository writing the new digest into the relevant overlay after which the pipeline holds no cluster credentials at all, which is the security win. Sync policy automated with selfHeal enabled and prune considered deliberately, since pruning deletes resources removed from Git and the first run against a drifted cluster will want to delete rather a lot.

    Migration order. One non-critical service in one non-production cluster first, with Argo CD in read-only mode sync disabled so it reports OutOfSync without acting. That report is the interesting part.

    What I expect to find, and this is the substance of the question. Substantial undocumented drift: manual kubectl changes made during past incidents and never reverted replica counts, resource limits, environment variables, and occasionally an entire resource that exists in a cluster and in no repository. Clusters that were believed identical and are not, which is usually where the "works in staging, fails in production" backlog comes from. Resources nobody owns: objects created by someone who has left, or by a tool that was removed. Secrets handled by hand, since manifests in Git cannot contain secrets and something must be arranged External Secrets Operator or the Secrets Store CSI driver, which is a project in its own right and is the most common thing to underestimate. I would plan for the drift inventory to take longer than the tooling work, and I would treat it as the migration's main deliverable rather than a side effect, because reconciling it is what actually makes the environments comparable.

    Architecture Questions¶

    1. Design a complete multi-account delivery architecture for twelve microservices deploying to ECS in two Regions, and justify each decision.

    Accounts. A tooling account holding the pipelines, the artefact store and the ECR registry; separate dev, staging and production accounts. The account boundary is the strongest control AWS offers, and it makes "a developer cannot change production" an enforced fact rather than a policy.

    Pipelines. One V2 pipeline per service twelve of them generated from a shared CDK construct so they are one reviewed definition with twelve instantiations. V2 for variables, conditions, rollback and retry; per-minute pricing removes the cost objection to pipeline count. Triggers filtered by branch and file path so a commit touching one service runs one pipeline.

    Build. A CodeBuild action assuming a build role that can read source, push to one ECR repository and read named parameters and that cannot deploy. Tests, lint and scanning run as parallel actions at the same runOrder after the build. The image is tagged with the commit SHA and the digest exported as a pipeline variable.

    Artefact custody. ECR in the tooling account with tag immutability, enhanced scanning through Inspector, lifecycle policies retaining a bounded number of tagged images, and replication rules to the second Region and to the production account so every consumer gets the identical digest and no one rebuilds for access or locality.

    Promotion. Dev, then staging with integration tests as a runOrder 2 action in the same stage, then an entry condition on the production stage with an alarm rule and a deployment-window rule, then a manual approval scoped to an IAM group excluding the author, with the evidence links attached. Each deploy action assumes a cross-account deploy role in the target account; the artefact key's policy grants each of those roles kms:Decrypt.

    Production deployment. ECS blue/green with a canary, a BeforeAllowTraffic smoke test over a test listener, and a CloudWatch alarm dimensioned on the green target group driving automatic rollback chapter 5.1's design, invoked from the pipeline. Task definitions reference the image by digest.

    Regions. The second Region deploys after the first has baked, orchestrated by a Step Functions invoke action rather than by parallel deploy actions, so a regional rollout is progressive and can stop after Region one.

    Observability. Alarms on pipeline failure, pipeline duration, rollback and ECR pull failures; deployment markers on application dashboards; CloudTrail alarms on production mutations by non-deploy identities.

    2. Design delivery for a platform running both ECS and EKS, where the organisation wants one coherent model. What do you unify and what do you deliberately keep different?

    I would unify everything up to the artefact and deliberately keep the delivery direction different, because forcing one model onto both costs more than it saves.

    Unified: everything before deployment. One source and review process, one build pipeline shape generated from a shared construct, one artefact standard commit-SHA tags, digest references, immutability, enhanced scanning, lifecycle policies one ECR registry with replication, one promotion policy defining what evidence justifies each environment transition, and one identity model with build and deploy separated and production in its own account. This is where consistency has real value: an engineer moving between an ECS service and an EKS service finds the same build, the same artefact rules and the same gates.

    Deliberately different: the deployment mechanism. ECS gets a push a CodePipeline deploy action driving blue/green with canary and alarm rollback because ECS has an AWS API, an IAM identity model and a deployment controller designed to be driven externally. EKS gets a pull the pipeline commits a digest to the manifest repository and Argo CD reconciles because Kubernetes is already a reconciliation loop and pushing into it creates a competing source of truth that cannot detect drift.

    What I would unify at the observation layer, which is the part that makes them feel coherent despite differing: one deployment-event stream. The ECS path emits CodeDeploy events; the EKS path emits Argo CD sync events. Normalising both into EventBridge and onto the same dashboards means "what was deployed where, when" is one query, and deployment markers appear on every application dashboard regardless of orchestrator.

    What I would resist. Running Argo CD for ECS through a Kubernetes-adjacent abstraction, or pushing to EKS with kubectl from CodeBuild to match the ECS pattern. Both are attempts to make the diagram symmetrical at the cost of fighting one platform's model, and the asymmetry is not accidental it reflects a real difference in how the two systems are designed to be changed.

    3. Design the artefact custody strategy for an organisation that must prove, to an auditor, what was running in production at any moment in the last three years.

    The requirement decomposes into three claims that must each be evidenced: what artefact was running, where it came from, and that it has not changed.

    Artefact identity and immutability. ECR with tag immutability, images tagged with the full commit SHA, and every deployment referencing a digest. This makes "what was running" a content-addressed fact. Lifecycle policies must be designed around the three-year requirement rather than around cost: I would retain every image that ever reached production indefinitely most simply by promoting production artefacts into a separate production-only repository that has no expiry rule and that only the pipeline can write to, while development repositories expire aggressively. That separation also means "images that reached production" is a physically distinct set an auditor can enumerate.

    Provenance. Sign every image with AWS Signer at build time and verify the signature before deployment, so "our pipeline built this" is checkable rather than assumed. Generate an SBOM per build and store it as an OCI artefact in the same repository alongside the image, so the dependency inventory travels with the artefact and the question "were we exposed to this CVE in March 2024" is a query against stored data rather than a reconstruction.

    Deployment history. CodePipeline execution history plus CloudTrail gives the ECS side: who approved, which identity deployed, which digest, when. For the EKS side the Git history of the manifest repository is the deployment history, which is a better artefact than a log diffable, and with signed commits, attributable. I would require signed commits on that repository precisely for this reason.

    Vulnerability state over time. Enhanced scanning with Inspector records findings against images continuously, so the auditor's likely question "when did you learn about this, and how long did it run?" is answerable from stored findings rather than from memory.

    What I would tell the auditor is weak. Configuration is the gap: the image is immutable and evidenced, but what was in Parameter Store or AppConfig at a given moment is only as auditable as those services' own history. I would put environment configuration in version control and deploy it through the pipeline for exactly this reason, rather than relying on console-edited parameters otherwise "what was running" is provable and "how it was configured" is not.

    Troubleshooting Questions¶

    1. A pipeline execution shows the deploy stage succeeded but the ECS service is still running the previous task definition. Diagnose.

    A successful deploy action with an unchanged running version means the action did something other than what you assume. The candidates, in order. The standard ECS deploy action registered a new task definition and updated the service, but the service's deployment then failed and rolled back the action reports the API call's success, and the ECS service events are where the real story is: tasks failing health checks, ImagePullBackOff, insufficient capacity, or a task role that cannot reach a required resource. The imagedefinitions.json named a container that does not exist in the task definition, in which case the mapping silently applies to nothing. The new task definition is identical to the old one, which happens when the artefact referenced a tag rather than a digest and the tag had not moved ECS registers a revision, sees no effective change, and does very little. minimumHealthyPercent: 100 with maximumPercent: 100 leaves no room to launch a replacement task, so the deployment waits indefinitely while reporting progress. The deploy action targeted a different cluster or service than the one being inspected, which is embarrassingly common across accounts and Regions. I would look at aws ecs describe-services for the deployment's rolloutState and rolloutStateReason and at the service events first, because those name the cause directly in most of these cases. The structural fix, whichever it turns out to be, is that the pipeline stage should not report success on an API call's return: for ECS the deploy action should wait for the service to reach a steady state, and for anything user-facing the blue/green path with a smoke test makes "succeeded" mean something.

    2. Pods in a private EKS cluster are stuck in ImagePullBackOff for an image that exists in ECR and that the pipeline pushed successfully. Diagnose.

    The pipeline pushing successfully tells you the image exists and that the build's network path works; the pods' path is different, and in a private subnet there are several ways for it to fail. VPC endpoints are the first thing I would check, and specifically all three: com.amazonaws.<region>.ecr.api for authentication, com.amazonaws.<region>.ecr.dkr for the registry protocol, and an S3 gateway endpoint, because the layers themselves come from S3. Having the first two and not the third is the classic configuration, and it produces an authentication success followed by a layer-download timeout which looks nothing like a permissions problem and sends people to IAM. The node role's permissions next: the nodes pull the image, so the node instance role (or the pod identity, if using one) needs ecr:GetAuthorizationToken, ecr:BatchGetImage and ecr:GetDownloadUrlForLayer. The repository policy, if the cluster is in a different account from the registry a cross-account pull needs the repository policy to grant it, and an IAM policy alone is insufficient. Region mismatch: an image in us-east-1 referenced from a cluster in eu-west-1 requires cross-Region pull, which works only if there is a network path and is slow even then replication is the fix. The digest actually existing: a lifecycle policy may have expired it, which is the failure I would check if this worked yesterday and does not today. And security groups on the endpoints permitting HTTPS from the node security group, which is easy to omit when endpoints are created separately from the cluster. kubectl describe pod gives the precise error, and the distinction between "authentication failed" and "timeout pulling layer" separates the permissions causes from the networking ones immediately.

    3. Argo CD reports an application as Synced but Degraded, while the pipeline that updated the manifest reported success. What does this mean and how do you respond?

    These three facts are consistent and their combination is exactly what GitOps is designed to surface. Synced means the cluster matches what Git declares the apply worked and the desired state is in place. Degraded means the workload declared is not healthy pods are crash-looping, failing readiness probes, or unschedulable. The pipeline reporting success is correct too, because its job ended at committing a digest to the manifest repository; it never had an opinion about cluster health. So nothing is broken in the delivery mechanism: the delivery mechanism is telling you the change is bad, which is precisely the separation of concerns you wanted. My response: roll back through Git git revert the manifest commit, since with automated sync Argo CD reconciles back to the previous digest within its sync interval, and that is both faster and more auditable than any out-of-band action. Then diagnose from the pods: kubectl describe and the container logs, looking for the usual causes of Degraded after a successful sync a readiness probe failing because a dependency is unreachable from the new version, a missing or renamed secret or ConfigMap, a resource request the cluster cannot satisfy, or an image that pulls but crashes on startup due to a configuration mismatch. The improvement I would make afterwards is to stop learning about this from a status field: Argo CD's health status should feed an alarm, and for user-facing services I would add Argo Rollouts so that a new version is exposed progressively and analysed against metrics before it takes full traffic which gives the Kubernetes path the same canary-plus-automatic-rollback property the ECS path already has.

    1. A pipeline builds a container image and deploys it to Amazon ECS. The team wants deployments to be reproducible and wants to guarantee that the image running in production is the image that was tested. Which combination achieves this?

    A. Tag images latest and enable ECR scan on push B. Enable ECR tag immutability, tag with the commit SHA, and reference the image by digest in the task definition C. Rebuild the image in each deployment stage from the same commit D. Use imagedefinitions.json with a version tag and enable lifecycle policies

    Answer: B. Immutability prevents a tag from being repointed, the commit SHA gives traceability, and the digest makes the deployed content fixed at deployment time rather than resolved at every task launch. A deploys a mutable pointer. C violates build-once-deploy-many. D still resolves a tag at launch time.

    2. Which statement about actions within a CodePipeline stage is correct?

    A. All actions in a stage always run sequentially in the order declared B. Actions with the same runOrder value run in parallel; a higher runOrder waits for all lower ones C. Actions in a stage always run in parallel D. Parallelism requires the PARALLEL execution mode

    Answer: B. runOrder controls ordering within a stage. D confuses execution mode, which governs concurrent pipeline executions, with action parallelism inside a stage.

    3. A company must prevent a release from being deployed while the production service is experiencing an incident. Which approach requires no custom code?

    A. Disable the pipeline transition manually whenever an incident starts B. Add a stage entry condition with a CloudWatch alarm rule on the production stage C. Add a Lambda action that queries CloudWatch before the deploy action D. Set the execution mode to QUEUED

    Answer: B. An entry condition with an alarm rule is built-in configuration. A depends on a human remembering during an incident. C works but is the custom code the question excludes. D changes how overlapping executions queue, not whether they deploy into an unhealthy environment.

    4. Pods in a private subnet fail to pull images from Amazon ECR. Authentication succeeds but the pull times out during layer download. What is missing?

    A. The com.amazonaws.region.ecr.api interface endpoint B. An S3 gateway endpoint C. The ecr:GetAuthorizationToken permission D. A NAT gateway for the ECR control plane

    Answer: B. Authentication succeeding means ecr.api and the IAM permissions are working; ECR layers are served from S3, so layer download requires S3 access. This specific symptom auth succeeds, layers time out is the signature of the missing S3 endpoint.

    5. Which is a property that GitOps with Argo CD provides and a push-based CodePipeline deployment does not?

    A. Rollback to a previous version B. Continuous detection and correction of drift between declared and actual cluster state C. Deployment to private EKS clusters D. Audit of who deployed what

    Answer: B. A reconciliation loop compares declared against actual continuously; a push pipeline knows only what it last pushed. A is available in both. C is available in both the native EKS action handles private clusters. D is available in both, through execution history or Git history.

    6. An ECR lifecycle policy expires images older than 30 days. After a quiet period, an ECS service fails to launch replacement tasks although the service was healthy. What happened?

    A. The task definition was deleted by the lifecycle policy B. The image referenced by the running task definition was expired and can no longer be pulled C. ECR scanning blocked the image D. The service's minimumHealthyPercent is too high

    Answer: B. Running tasks do not re-pull, so the service appears healthy until it must launch a task. This is a data-plane failure caused by a delivery-side configuration, and it is why lifecycle policies must never expire images referenced by live task definitions.

    5.3 Infrastructure as Code¶

    Conceptual Questions¶

    1. Explain declarative provisioning, and why idempotency and convergence are the properties that matter.

    Declarative provisioning means you describe the desired end state and the engine determines how to reach it: it reads current state, computes the difference, orders operations by dependency, and applies them. Imperative provisioning means you specify the steps, which makes you responsible for ordering, for error handling, and for the awkward question of what to do when half of it already exists. The two properties that make the declarative model work are idempotency applying the same definition repeatedly produces the same result rather than compounding and convergence the engine moves toward the declared state from whatever state actually exists. Together they are what make automation safe: a failed run can simply be re-run, and a partially-applied change can be completed rather than untangled by hand. Without them, automation would need to know exactly what had already happened, which is precisely the problem it exists to remove. The observation I would add is that this is the same loop as a Kubernetes controller and the same loop as GitOps reconciliation declared state, observed state, difference, act which is why the failure modes rhyme across all three: drift, a reconciliation that will not complete, and a declared state that is itself wrong. Recognising them as one pattern rather than three is worth more than knowing any individual tool's syntax.

    2. Why is drift dangerous, and why is drift detection an insufficient answer?

    Drift is divergence between the declared state and what actually exists, caused by changes made outside the tool a console edit during an incident, a CLI call to unblock a demo, an automated remediation, or another tool touching the same resource. It is dangerous for three compounding reasons. The declaration becomes false, so the repository and the architecture diagram assert something untrue with authority, which is worse than having no documentation because people act on it. The retail example is the sharp version: a template declaring a security group permitting 443 from the load balancer, while the actual group had permitted SSH from 0.0.0.0/0 for eight months. The next apply may revert it, which is correct in principle and occasionally catastrophic the drift might be the emergency fix currently keeping the service up. And rollback may fail, because CloudFormation's model of what it should restore no longer matches reality, which is exactly how a stack reaches UPDATE_ROLLBACK_FAILED and becomes neither updatable nor deletable. Detection is insufficient because it is retrospective and non-corrective: it tells you drift happened, after it happened, and does nothing to stop it happening again. The structural fix is to remove the ability to cause it humans have read-only access to production infrastructure, and only the pipeline's deployment role may write, with a time-bounded, alarmed break-glass path for genuine emergencies. Every organisation I have seen eliminate drift did it that way; none did it by running detection more often.

    3. What is the relationship between CDK and CloudFormation, and what does that mean for a team adopting CDK?

    CDK is not an alternative to CloudFormation; it is a way of writing it. cdk synth executes your program to build a construct tree and emits CloudFormation templates plus assets into cdk.out; cdk deploy uploads the assets and hands the templates to CloudFormation, which does everything it always did. So every CloudFormation concept applies unchanged: change sets, stack states, automatic rollback, ROLLBACK_COMPLETE being deletion-only, drift, deletion policies, quotas. For an adopting team this has three consequences. They still need to learn CloudFormation, because when something fails the error messages, the stack states and the recovery procedures are all CloudFormation's a team that learned L3 constructs and skipped the foundation is effective until the first stuck stack and then has no mental model at all. Synthesis is a new failure mode they did not previously have: a template says exactly what it says, whereas a CDK app says whatever the program computes, so a logic bug or a library version bump can produce a valid template describing something nobody intended. That is why cdk diff in the pipeline, snapshot tests over the synthesised output, and pinned versions of both the library and the CLI are load-bearing controls rather than hygiene. And the value is abstraction and reuse, not language preference the argument for CDK is that one reviewed construct instantiated sixty times turns a new requirement into one change and one review, where sixty duplicated templates mean sixty reviews and at least one of them will be wrong.

    4. Compare CloudFormation's and Terraform's state models and explain what each trade buys.

    CloudFormation holds state inside the AWS service, per stack. Terraform holds it in a state file you host typically S3 containing the mapping from configuration to real resources along with their attributes. This single difference generates most of the practical contrasts. Operational burden: CloudFormation gives you nothing to host, protect, version or back up; Terraform makes all of that yours, and the state file contains secrets, so it is a security asset requiring KMS encryption, versioning, locking and tight access control. The startup whose state file left with a departing engineer, after which the next apply proposed building a duplicate production environment, is the cautionary version. Repairability: CloudFormation's state is opaque, so when the engine's model is wrong your options are the ones it offers ContinueUpdateRollback, resource import, skipping resources. Terraform's state is inspectable and surgically editable with state mv, state rm and import, which occasionally rescues a situation that would leave a CloudFormation stack wedged. Failure semantics: CloudFormation rolls back automatically, which is safer when it works and can trap a stack when it does not; Terraform has no rollback, so a failed apply leaves resources partly created and state reflecting what succeeded, and you recover by fixing and re-applying, relying on convergence. Neither model is strictly better. CloudFormation trades control for fewer responsibilities; Terraform trades responsibilities for control. The decision usually turns on something else entirely whether you need non-AWS providers and the state model is what you then have to live with.

    5. Why is reviewing the plan or change set a separate gate from reviewing the code?

    Because they answer different questions. The code diff shows intent: what the author meant to change, and whether that is a good idea. The plan or change set shows consequence: what will actually happen to the resources that currently exist, which depends on the current state and on how each provider handles each property change. The gap between them is where the damage lives, and the specific thing to look for is replacement. Some property changes apply in place; others require the resource to be destroyed and recreated. Changing an RDS instance identifier, a subnet CIDR, or a DynamoDB key schema all mean delete and create and for a stateless resource that is a brief interruption, while for anything holding data it is data loss. A one-word change in a diff can read as entirely trivial and appear in the change set as Replacement: True on the production database. CloudFormation labels this explicitly; Terraform prints -/+ destroy and then create replacement with # forces replacement on the offending attribute. Reading for that string is the single highest-value habit in this chapter, and it costs seconds. I would add two supporting practices: save the plan as an artefact and apply exactly that artefact, so the thing reviewed is provably the thing applied, which Terraform supports directly with plan -out; and set UpdateReplacePolicy and prevent_destroy on stateful resources, so that if the review misses it the apply fails rather than executing.

    Scenario Questions¶

    1. An organisation's production account has no IaC. Design the migration and state what you expect to go wrong.

    The instinct is to write templates for everything, and that fails because it takes months during which nothing improves and the estate keeps changing underneath you. I would sequence it to get value early. First, stop the bleeding: prevent new resources being created outside IaC, by removing write access from humans in production and routing new work through a pipeline. This is the unpopular step and it is the one that determines whether the rest is permanent or temporary. Second, inventory: use AWS Config to enumerate what actually exists, and the CloudFormation IaC generator to scan the account and generate templates from live resources. That gives you a starting artefact rather than a blank file, which matters because the hardest part of this work is discovering what is there, not writing YAML. Third, prioritise by rebuild pain: bring the foundation under management first VPC, subnets, routing, DNS, baseline IAM because those are the things that block a rebuild entirely, and because they change rarely so the risk of adopting them is low. Fourth, import rather than recreate: CloudFormation resource import and Terraform import blocks bring existing resources under management without touching them, which is essential because recreating production networking is not an option. Fifth, work outward to shared services and then applications, which change often and are therefore both higher-risk to adopt and higher-value once adopted.

    What I expect to go wrong, and this is the substance. Resources nobody owns or can explain security group rules, IAM roles referencing deleted resources, a Lambda function whose source nobody can find, exactly as in the fintech example. Each requires a decision, and the decision is often "we do not know if this is load-bearing", which is slow. Import failures on resources whose current configuration is not expressible in the template, forcing either a configuration change or an exclusion. Drift appearing immediately, because the moment you have a declaration you can compare against, you discover how far reality has moved. The 30 per cent that resists: resources created by tools you do not control, or by a vendor, or by a process nobody remembers. I would treat that residue as a tracked list with owners rather than pretending it will disappear, and I would measure IaC coverage as a dashboard metric, because "we have IaC" is meaningless and "94 per cent of production resources are managed" is a statement you can act on.

    2. A CloudFormation stack containing the production database is in UPDATE_ROLLBACK_FAILED. Walk through your response.

    First, establish what is actually serving traffic, because the stack's state and the application's health are separate questions in most of these cases the application is still up, which removes the time pressure and is worth knowing before anyone does anything hasty. Then understand why the rollback failed, from the stack events: CloudFormation attempted to restore resources to their previous state and one of those operations failed. The usual causes are that a resource was deleted or modified manually since the last successful deployment, so the rollback is trying to restore something that no longer exists in the expected form this is drift arriving as an operational emergency; a dependency preventing a restore, such as a non-empty S3 bucket; or a custom resource that fails or never signals.

    The recovery path is ContinueUpdateRollback, and the important option is ResourcesToSkip: resources whose rollback cannot succeed can be skipped, which lets the stack reach UPDATE_ROLLBACK_COMPLETE but skipping means CloudFormation's model of those resources is now knowingly wrong, so they must be reconciled afterwards, by import or by a subsequent update that brings the declaration in line with reality. I would identify the minimum set to skip rather than skipping broadly, because every skipped resource is future drift I have chosen to create.

    Two things I would not do. I would not delete the stack, because it contains the production database and this is precisely the situation DeletionPolicy: Retain exists for, so I would check whether it is set before anyone suggests deletion, and if it is not, that is the finding. And I would not make further manual changes, since manual changes are what caused this. Afterwards: verify with drift detection that the declaration matches reality, add DeletionPolicy and UpdateReplacePolicy if absent, add a stack policy protecting the database from replacement, and the actual root cause remove the human write access that allowed the original manual change. I would also split the stack, because a stack containing both a production database and whatever was being updated has a blast radius that guaranteed this incident would be serious.

    3. A team wants to adopt Terraform for an AWS-only estate. Advise them.

    I would ask what problem they are solving, because for an AWS-only estate the default answer is CloudFormation or CDK and Terraform needs a positive reason. Good reasons: they already have Terraform expertise and existing modules; they manage non-AWS resources Datadog monitors, GitHub repositories, PagerDuty schedules, Cloudflare where Terraform's provider model is a genuine and unmatched advantage; they want a saveable plan artefact so the thing reviewed is provably the thing applied; or they anticipate multi-cloud and want one workflow. Weak reasons: "CloudFormation is verbose", which CDK addresses without leaving the platform; and "Terraform is the industry standard", which is a popularity argument rather than an engineering one.

    If they proceed, the things that will hurt them are all about state, and I would make them decisions rather than discoveries. Remote state from the first commit S3 with versioning, KMS encryption and use_lockfile = true for native locking; local state is how the startup in this chapter lost its production environment. Treat state as a secret store, because it contains generated passwords and keys regardless of what they put in the configuration. Environment separation by separate state and separate credentials, not by workspaces a workspace is a mutable shell setting and it is how terraform destroy runs against production believing it is dev. Pin providers and commit the lock file. Saved plans in CI, applied exactly. And prevent_destroy on stateful resources, which fails the plan rather than warning in it.

    I would also raise the licensing question explicitly rather than leaving it implicit: the BSL change of August 2023, the OpenTofu fork now under the CNCF, IBM's acquisition of HashiCorp, and HCP Terraform's changing free-tier caps. None of these prevents an enterprise managing its own infrastructure from using Terraform, and the two codebases have now diverged enough that switching later is a project rather than a rename. So my advice would be to choose deliberately, avoid depending on features unique to either fork, and treat the choice as one they may revisit which is a reasonable position to hold about any tool, and an unusually concrete one here.

    4. Design the guardrails so that a merge to the infrastructure repository cannot escalate a developer to account administrator.

    The threat is real and specific: if the pipeline can create IAM roles and any developer can trigger the pipeline by merging, then repository write access is equivalent to the deployment role's permissions, which typically include iam:CreateRole and iam:AttachRolePolicy. A developer could merge a template creating a role with AdministratorAccess and a trust policy naming themselves. I would layer the defences.

    At review: branch protection requiring approval from someone other than the author, which is the same control as chapter 5.1 and is necessary but insufficient, because a reviewer will not reliably spot a well-disguised IAM change in a large diff.

    At policy: cfn-guard, cdk-nag or Checkov rules in the pipeline that fail the build on wildcard actions, wildcard resources in IAM policies, AdministratorAccess attachment, and trust policies naming principals outside an allowed set. This is the control that works uniformly.

    At the permission boundary: the deployment role may create IAM roles only with a mandatory permission boundary attached, enforced by an IAM condition on iam:CreateRole and iam:PutRolePolicy requiring iam:PermissionsBoundary to equal a specific policy ARN. This is the key structural control: any role the pipeline creates is capped by the boundary regardless of what policy is attached to it, so the escalation ceiling is set by something the pipeline cannot change.

    At the account boundary: a service control policy at the organisational unit denying changes to the boundary policy itself, denying the deletion of CloudTrail and Config, and denying any identity except a named break-glass role from modifying the deployment role. SCPs bound everything below them and cannot be escaped from within the account.

    At the boundary of the pipeline: production in a separate account, so the developer's own credentials cannot reach it at all, and a manual approval on the production stage scoped to an IAM group excluding the author.

    And detection: a CloudTrail alarm on CreateRole, AttachRolePolicy and PutRolePolicy by any identity, reviewed because the point of the layers is that one of them catches what the others missed, and the alarm is what tells you which.

    Architecture Questions¶

    1. Design the IaC architecture for an organisation with 40 AWS accounts, 200 engineers and a regulatory obligation to evidence every infrastructure change.

    Structure by lifecycle and ownership. A central platform team owns the foundation networking, DNS, transit, baseline IAM deployed by StackSets through AWS Organizations so every account, including new ones, receives it automatically. Application teams own their application stacks, in their own repositories, deployed by their own pipelines into their own accounts. The boundary between these is deliberate: application teams cannot change networking, and the platform team is not in the path of routine application changes.

    Tooling. CDK for application infrastructure, with shared constructs published as an internal package "a service" defined once, instantiated by each team, so that a new security requirement is one change in one construct and a version bump for consumers. CloudFormation StackSets for organisational baselines, because they apply automatically to new accounts. I would resist a second engine unless there are genuine non-AWS providers to manage, because two engines means two state models, two failure surfaces and two sets of expertise.

    Enforcement, layered. SCPs at the organisational unit as the outer boundary. CloudFormation Hooks for preventive controls a non-compliant resource cannot be created regardless of the route taken, which matters because it survives someone bypassing the pipeline. Policy as code (cdk-nag, cfn-guard) in every pipeline. AWS Config rules and conformance packs for continuous assessment of live resources independently of how they were created. Permission boundaries mandatory on every pipeline-created IAM role.

    Evidence, which is the regulatory requirement. Git history gives intent, author, reviewer and discussion. The change set or saved plan is retained as a pipeline artefact per deployment, which is the piece teams forget and the piece an auditor actually wants: the record of what the change was going to do, approved before it did it. CloudTrail gives the executed actions and the identity. Config gives point-in-time resource configuration history, which answers "what did this look like on 14 March" directly. Together these answer intent, authorisation, action and outcome four separate questions that no single source covers.

    The controls that make the evidence trustworthy. No human write access to production infrastructure; a time-bounded, alarmed break-glass role; a CloudTrail alarm on any infrastructure mutation by a non-deployment identity; scheduled drift detection with alarms. Without these, the evidence describes the sanctioned path while an unsanctioned one exists beside it.

    And a coverage metric, published: managed resources as a proportion of the Config inventory, per account. It is the only honest measure of whether any of the above is actually true.

    2. Design the split of stacks or modules for a platform with a shared VPC, three EKS clusters, twelve services and per-service databases. Justify every boundary.

    The principle is split by lifecycle and blast radius, not by resource type, and every boundary below is justified by one of those two.

    Foundation stack, per account. VPC, subnets, route tables, NAT, transit gateway attachments, DNS zones, VPC endpoints. Changes rarely; every change is high-risk; termination protection on; stack policy denying updates to the VPC and subnets. It is separate from everything else because the alternative a shared stack containing the VPC and anything that changes weekly means every routine change carries network risk.

    Cluster stack, one per EKS cluster. The control plane, node groups or Karpenter configuration, cluster-level IAM, add-ons. Changes monthly, at cluster-upgrade cadence. Separate per cluster so upgrading one does not risk the others the blast-radius argument.

    Shared services stack. Shared load balancers, the ECR registry, shared observability, the shared secrets hierarchy. Changes occasionally. Separate because its consumers are all twelve services and its lifecycle matches none of them.

    Per-service application stacks, twelve of them. Kubernetes resources or ECS services, task definitions, scaling policies, alarms, service-specific IAM. Changes constantly several times a day. One per service so that a bad deployment of one cannot affect another, which is the bulkhead argument from chapter 4.3 applied to provisioning.

    Per-service database stacks, twelve of them, separate from the application stacks. This is the boundary people most often get wrong, and the justification is the strongest of the lot: databases have a completely different lifecycle from application code, and separating them means a routine application change cannot produce a change set touching the database. With DeletionPolicy: Snapshot, UpdateReplacePolicy: Snapshot and a stack policy denying replacement, the database is protected by structure rather than by attention.

    Coupling between them. I would prefer Parameter Store lookups over CloudFormation exports for cross-stack values. Exports create a hard dependency an exported value cannot change while it is imported, and the exporting stack cannot be deleted which in practice is how estates become undeletable. A Parameter Store value read at deployment is looser, at the cost of the engine not knowing about the dependency, which means ordering becomes the pipeline's responsibility. That is a trade I would make deliberately and document, because it is the kind of decision that looks arbitrary six months later.

    3. Your organisation uses CDK and a team proposes switching to Terraform. Structure the decision.

    I would push past the stated reasons to the underlying one, because in my experience this proposal usually comes from one of three places and the right answer differs.

    If the driver is non-AWS resources Datadog, GitHub, Cloudflare, a SaaS vendor's configuration that is a genuine, unmatched Terraform advantage and the discussion is about scope rather than replacement. My recommendation would be to use Terraform for those providers specifically and keep CDK for AWS, accepting two tools with a clear boundary rather than migrating an entire estate to solve a peripheral problem.

    If the driver is multi-cloud a real second cloud, funded, with workloads planned then Terraform is the right engine and the migration is justified. But I would test whether it is real, because "we might go multi-cloud" has justified more premature abstraction than any other phrase in this field, and abstraction over clouds usually costs access to the best of each.

    If the driver is preference or frustration HCL over TypeScript, or a bad experience with a stuck stack then I would resist, because the migration cost is large and the frustration usually has a cheaper fix. A stuck stack is a CloudFormation lesson, not a reason to change engine; verbosity is what CDK already addresses.

    The costs I would put on the table explicitly. Re-implementing every construct as a module, and losing the shared-construct leverage that a mature CDK estate has accumulated. Taking on state as an operational and security responsibility remote backend, locking, versioning, encryption, backup, and the fact that state contains secrets. Retraining 200 engineers. Running both during a migration, with the attendant risk of two tools managing overlapping resources, which is its own category of incident. And the licensing dimension: the BSL, the OpenTofu fork, IBM's ownership, and HCP's changing terms not disqualifying, but a commercial variable that CDK does not carry.

    What I would propose instead of a yes or a no: a bounded trial. One non-critical workload, in Terraform, for a quarter, with agreed criteria plan quality, incident count, onboarding time, the actual experience of state management. That converts an argument about preference into evidence, and it is cheap relative to either a migration or a permanently unresolved disagreement.

    Troubleshooting Questions¶

    1. A stack update failed and the stack is now in ROLLBACK_COMPLETE. The team wants to fix the template and update. What do you tell them?

    That they cannot, and this is a specific CloudFormation behaviour worth knowing precisely. ROLLBACK_COMPLETE is reached when the initial creation of a stack fails and is rolled back; the stack exists as a record but contains no successfully created resources, and CloudFormation will not accept an update to it. The only permitted operation is delete. So the sequence is: delete the stack, fix the template, create it again. The distinction that catches people is that this applies to a failed create, not a failed update a failed update leaves UPDATE_ROLLBACK_COMPLETE, which is updatable, and confusing the two states leads to a lot of wasted time. I would then ask why the creation failed, because that is the actual problem: usually an IAM permission the deploying identity lacks, a resource limit, a name collision with something that already exists, or a dependency on something outside the stack that is absent. The stack events name the first resource that failed and the reason, and reading the first failure rather than the last is the trick everything after it is a consequence. Two preventive notes: use --disable-rollback or --on-failure DO_NOTHING during development so a failed creation leaves the resources in place for inspection rather than deleting the evidence, and test template changes in a non-production account first so a failed create is never a production event.

    2. terraform plan shows changes even though nobody has modified the configuration. Diagnose.

    A plan showing changes against an unmodified configuration is drift, revealed by the refresh step and that is Terraform working correctly, so the question is what caused it. The candidates, in the order I would check them. Someone changed the resource outside Terraform: a console edit, a CLI call, or an incident fix. The plan shows the attribute reverting, and I would resist applying reflexively until I know whether that change was load-bearing. An automated process changed it: an autoscaling action, a security-remediation tool, a service that mutates its own tags, or AWS itself updating a default. A provider version changed, and the new version reads or defaults an attribute differently this produces a plan on code nobody touched and is the one people find most confusing; the .terraform.lock.hcl file exists to prevent it and is frequently not committed. A computed attribute is genuinely unstable, such as a policy document AWS normalises, or an ordering difference in a list that Terraform treats as significant and the API does not. Another IaC tool or another state manages the same resource, so two systems are fighting this is the worst case and shows up as a plan that reverts the same attribute every time, forever. The diagnostics: terraform plan output names the attribute, terraform state show gives the recorded value, and CloudTrail tells you who or what changed it and when. The remedies differ by cause accept the change into the configuration, add ignore_changes if the attribute is legitimately managed elsewhere, pin the provider and commit the lock file, or resolve the dual ownership. The structural remedy is the same as always: remove the write access that let it happen.

    3. A CDK deployment produced infrastructure nobody intended, and the code review approved the change. What went wrong and how do you prevent recurrence?

    The review approved the code, and with CDK the code is a program whose output is the infrastructure so a review that reads the program without seeing the synthesised result is reviewing intent rather than consequence, which is the same gap as approving a Terraform change without reading the plan, made wider by abstraction. The likely mechanisms: a logic error a loop, a conditional, a context value that evaluates differently in CI than on a laptop producing a valid template describing something nobody meant; an L3 construct's defaults creating more or different resources than the author expected, which is exactly the trade L3 makes; a library version bump changing synthesised output with no change to the code at all, which is the one that surprises people most; or a context lookup (AZs, AMIs, VPC) resolving differently because cdk.context.json was not committed, making synthesis non-deterministic across environments. The preventions are specific and cheap. cdk diff as a mandatory pipeline step whose output is attached to the approval, so the approver sees the change set and not only the code. Snapshot tests over the synthesised template, so any unintended change in output fails the build and must be explicitly accepted. Fine-grained assertions on security-relevant properties encryption enabled, no public access, the expected IAM principals so those cannot drift silently. Pinned versions of both aws-cdk-lib and the CLI, with a version bump treated as an infrastructure change requiring its own diff. cdk.context.json committed, so lookups are deterministic. And cdk-nag in the pipeline, which would have caught an entire class of unintended resource regardless of why it appeared. The general lesson is that abstraction moves the risk rather than removing it: CDK eliminates boilerplate errors and introduces synthesis errors, and the controls have to move with it.

    Certification-style Questions¶

    1. A CloudFormation stack contains an Amazon RDS instance. A developer changes the DBInstanceIdentifier property and applies the update. What happens, and what would have prevented data loss?

    A. The instance is renamed in place; no data is affected B. The change forces replacement the instance is deleted and recreated and UpdateReplacePolicy: Snapshot would have preserved the data C. CloudFormation rejects the change D. DeletionPolicy: Retain alone would have prevented the loss

    Answer: B. Changing the identifier forces replacement. DeletionPolicy covers removal from the stack, not replacement during an update which is why UpdateReplacePolicy must be set separately, and why it is the one teams omit.

    2. Which statement about AWS CDK is correct?

    A. CDK replaces CloudFormation with its own provisioning engine B. CDK synthesises CloudFormation templates, which CloudFormation then deploys; all CloudFormation semantics apply C. CDK maintains its own state file that must be stored in S3 D. CDK does not support rollback

    Answer: B. cdk synth produces templates; cdk deploy hands them to CloudFormation. C describes Terraform. D is false rollback is CloudFormation's and applies unchanged.

    3. A team stores Terraform state in an S3 bucket. Which configuration prevents two concurrent applies from corrupting it, without a DynamoDB table?

    A. Enabling S3 versioning B. Setting use_lockfile = true on the S3 backend C. Setting sensitive = true on outputs D. Using separate workspaces

    Answer: B. Native S3 state locking uses a .tflock object and removes the DynamoDB requirement. A protects against loss, not concurrency. C affects output redaction. D separates state, not concurrent access to the same state.

    4. A CloudFormation stack's creation failed and it is in ROLLBACK_COMPLETE. What can the team do?

    A. Update the stack with a corrected template B. Continue the rollback C. Only delete the stack, then create it again D. Detect drift and remediate

    Answer: C. ROLLBACK_COMPLETE follows a failed create and permits only deletion. B applies to UPDATE_ROLLBACK_FAILED, which is a different state after a failed update.

    5. An organisation must apply the same logging and guardrail configuration to every account in its AWS Organization, including accounts created in future. Which is most appropriate?

    A. Nested stacks B. CloudFormation StackSets with service-managed permissions C. A CDK app deployed manually per account D. Cross-stack exports

    Answer: B. StackSets with service-managed permissions deploy across an organisation and apply automatically to new accounts. A decomposes one deployment. C does not scale and misses new accounts. D shares values within a Region and account.

    6. A security review finds that a production security group permits SSH from 0.0.0.0/0, although the CloudFormation template declares only port 443 from the load balancer. What is the finding and what is the structural remedy?

    A. The template is wrong and should be corrected B. Drift: the resource was changed outside CloudFormation. Drift detection identifies it; removing human write access to production infrastructure prevents recurrence C. CloudFormation failed to apply the template D. The stack must be deleted and recreated

    Answer: B. The declaration is correct and reality diverged. Detection finds it after the fact; the only structural prevention is that humans cannot write to production infrastructure, leaving the pipeline's deployment role as the sole path.
