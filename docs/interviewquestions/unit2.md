## Interview Questions

### 2.1 Conceptual Questions

**1. Explain what a container actually is, and state precisely how it differs from a virtual machine.**

A container is one or more ordinary processes running on the host's kernel with a restricted view of the system. Three kernel mechanisms produce that restriction: **namespaces** partition kernel resources so the process sees only its own PID tree, mount table, network stack, hostname, and IPC objects; **cgroups** account for and cap the CPU, memory, I/O, and process count it may consume; and a **union filesystem** presents stacked read-only image layers under a thin writable layer. A virtual machine, by contrast, runs its own kernel on hardware virtualised by a hypervisor. Every practical difference follows from that one distinction. Containers start in milliseconds because no kernel boots; they are dense because no operating system is duplicated per workload; and their isolation is weaker, because a kernel vulnerability is shared by everything on the host. The architecturally important consequence is that containers are an appropriate boundary between workloads you trust to the same degree, and an insufficient boundary between mutually hostile ones — which is exactly the gap AWS Fargate closes by giving each task its own lightweight VM while preserving the container interface.

**2. Why is deploying by tag unsafe, and what does pinning by digest actually guarantee?**

A tag is a mutable label in a repository that points at a manifest digest; anyone with push permission can repoint it. This breaks three things at once. Reproducibility fails, because two tasks launched from the same tag ten minutes apart can run different bytes. Rollback fails, because redeploying the previous tag may retrieve bytes that are not the bytes that tag held when it was healthy — so the rollback is itself an untested deployment. And assurance fails, because a scan result or an approval attached to a tag says nothing about what is currently under it. A digest is the SHA-256 of the image manifest, so referencing `repo@sha256:...` names exactly one immutable set of bytes: retrieving it either returns that image or fails, and it can never silently return something else. The complete practice is therefore threefold: enable tag immutability on the repository so tags cannot be repointed, tag with the commit SHA so the artefact is traceable to source, and pin the digest in the task definition so the deployed specification names exact bytes.

**3. Distinguish the ECS task execution role from the task role, and explain what the container instance role adds on EC2 capacity.**

They are three different principals acting at three different times. The **execution role** is assumed by the ECS or Fargate agent on behalf of a task *before your code runs*: it authenticates to ECR and pulls the image, creates the CloudWatch log stream, and decrypts secrets from Secrets Manager or Parameter Store through KMS. The **task role** is assumed by your application code, which obtains its credentials from the task metadata endpoint that the AWS SDKs discover automatically; it holds the permissions the application needs, such as reading one DynamoDB table. The **container instance role** exists only on EC2 capacity and is the instance profile the ECS agent uses to register the instance with the cluster, pull images, and write logs. Conflating them destroys a boundary that costs nothing to maintain: giving the execution role your application's data permissions means the image-pull identity also holds database access, and giving the container instance role application permissions means every container on that host inherits them through the instance metadata service — including a compromised one. The complete posture is three narrow roles plus IMDSv2 with a hop limit of one, so that application code cannot reach the instance profile at all.

**4. Why does a file deleted in a later Dockerfile layer still consume space, and what follows for secrets?**

Layers are additive filesystem diffs stacked by a union filesystem. Deleting a file in layer 5 records a whiteout entry in layer 5; the bytes remain in layer 3 where they were written, and layer 3 is still part of the image, still transferred on pull, and still readable by anyone who can extract the layer. Two practical consequences follow. First, size: `RUN apt-get install ...` followed by a separate `RUN rm -rf /var/lib/apt/lists/*` does not reduce the image, whereas chaining both into one `RUN` does, because then the cleanup happens before the layer is captured. Second, and far more seriously, secrets: a credential written into an early layer — through `COPY`, through `ARG`, or by a `RUN` that echoes it into a file — is permanently present in the image regardless of later deletion, and `docker history` on a pulled image exposes it to anyone with pull access. The correct mechanism is BuildKit's `--mount=type=secret`, which makes the secret available to a single `RUN` instruction without ever committing it to a layer.

**5. Why does an orchestrator exist? Answer in terms of what fails when you run containers manually on EC2.**

Because keeping containers running is a control-loop problem, and a shell script is not a control loop. Running `docker run` under `systemd` on one instance handles exactly two failures: the process crashing and the host rebooting. Everything else is unhandled. When the instance fails, its containers are gone and nothing places them elsewhere. When you add a second instance, deciding which containers run where becomes a human decision recorded nowhere. When you deploy, you must stop the old container before the new one is proven healthy, which is downtime, and you must register the new container's port with the load balancer by hand — and in bridge mode with dynamic ports you must first discover what that port is. When three containers want port 8080, you allocate ports manually and track them in a wiki. When load doubles, you launch instances and place containers by hand. When a container needs a database password, your only mechanism is a file on disk. And when someone asks what is running, the answer exists only in `docker ps` output across every host. ECS replaces all of that with a reconciliation loop over a declared desired state — which is why the honest way to teach it is to make students do the manual version once.

### Scenario Questions

**1. A team reports that their service works in staging and fails in production with `CannotPullContainerError`, using the same image tag in both. How do you diagnose it?**

I would start from the fact that the same *tag* in both environments does not mean the same *image*, and check the digest each environment actually resolved — which is itself an argument for pinning digests rather than tags. Assuming the image is genuinely the same, `CannotPullContainerError` has a small set of causes and the task's `stoppedReason` usually names which. The first is **networking**: a production task in a private subnet with no NAT gateway and incomplete VPC endpoints cannot reach ECR. The classic version of this is having the `ecr.api` and `ecr.dkr` interface endpoints but no S3 **gateway** endpoint, so authentication succeeds and the layer fetch fails — which produces a confusing partial failure rather than a clean authorisation error. The second is **permissions**: the production task's execution role may lack `ecr:GetAuthorizationToken`, `ecr:BatchCheckLayerAvailability`, `ecr:GetDownloadUrlForLayer`, or `ecr:BatchGetImage`, or the repository policy may not grant the production account access if builds are centralised in a shared account. The third is **Region and repository**: the production task definition may reference a repository in the staging Region, and ECR is regional. The fourth is **KMS**: if the repository is encrypted with a customer-managed key, the execution role needs `kms:Decrypt` on it. I would read the `stoppedReason` string first, since it distinguishes an authorisation failure from a network timeout, then check endpoints, then the execution role, then the repository policy — in that order, because that is the order of decreasing frequency.

**2. A developer's image runs perfectly on their laptop but every ECS task fails immediately with `exec format error`. What happened and what is the fix?**

The image was built for a different CPU architecture than the capacity is running. The overwhelmingly common case in 2026 is a developer on an ARM-based laptop building `linux/arm64` and pushing it, while the ECS task definition's `runtimePlatform` is x86_64 — the default. It is unreproducible locally precisely because the laptop's architecture matches the image's. The immediate fix is to rebuild for the target with `docker buildx build --platform linux/amd64`, or to publish a multi-architecture image with `--platform linux/amd64,linux/arm64` so one tag serves both. The durable fixes are three. First, **build in CI**, not on workstations, so the build platform is controlled rather than incidental. Second, **set `runtimePlatform` explicitly** in the task definition rather than relying on the default, so the intended architecture is stated in the specification and a mismatch is visible in review. Third, if the organisation wants Graviton's price-performance, adopt multi-architecture images deliberately and choose ARM64 capacity, rather than discovering architecture as a bug. I would also note that this is a good illustration of a general principle: "works on my machine" did not disappear with containers, it narrowed to the one property the image does not carry, which is the instruction set.

**3. Your ECR bill has grown to a significant line item and nobody knows why. Walk through your investigation and remediation.**

I would expect the cause to be accumulated images from CI rather than anything about the production images themselves, and I would confirm rather than assume. The investigation is: list repositories with their sizes; within the largest, count tagged versus untagged images; and check whether any lifecycle policy exists. The typical finding is a pipeline pushing an image per commit across every branch, with tag mutability enabled so that overwritten tags leave orphaned untagged manifests behind, and no lifecycle policy at all — which in an active organisation accumulates hundreds of gigabytes within a year. The remediation is a lifecycle policy per repository with two rules: expire untagged images after one to seven days, and retain the last N images per tag prefix, with a longer retention for release-tagged images than for CI-tagged ones. I would also check three adjacent costs that usually appear in the same investigation: whether enhanced scanning is running on every feature-branch build rather than only on images that can reach an environment; whether tasks are pulling across Regions, since same-Region pulls to ECS and EKS are not charged for data transfer while cross-Region pulls are; and whether VPC endpoints exist, since without them every pull is also paying NAT gateway data processing. Finally I would set a lifecycle policy as a required property in the repository module in Terraform or CDK, so that a repository created without one cannot exist.

**4. A service deploys successfully but users see errors for about thirty seconds during every deployment. Diagnose and fix.**

The symptom is in-flight requests being terminated on tasks that were stopped before they finished serving, and four settings interact to produce it. First, the target group's **deregistration delay**: if it is very short, the ALB stops considering the target but connections already in flight are cut; it should be set just above the service's measured p99 request duration. Second, the application's **`SIGTERM` handling**: ECS sends `SIGTERM` and then `SIGKILL` after `stopTimeout`, and an application that does not trap `SIGTERM` to stop accepting new connections and drain existing ones simply dies mid-request. A very common root cause here is an `ENTRYPOINT` in shell form, which makes `/bin/sh` PID 1 and prevents the signal reaching the application at all — so I would check the exec form before checking the application code. Third, **`stopTimeout`** must be long enough for that drain to complete. Fourth, the application's **keep-alive idle timeout** must exceed the ALB's, or the ALB will reuse a connection the backend has just closed, which produces sporadic 502s continuously rather than only during deployments. I would also verify that the deployment configuration uses a minimum healthy percent of 100 so capacity is not reduced during the rollout, and that the health-check grace period exceeds the application's cold start so slow-starting tasks are not killed and replaced in a loop.

### Architecture Questions

**1. Design the image supply chain for an organisation of forty engineers across six teams shipping twenty services. State what is centralised and what is delegated.**

I would centralise three things and delegate everything else. **Base images** are centralised: a platform team maintains a small set of hardened bases, one per supported language runtime, built from pinned upstream digests pulled through an ECR pull-through cache, scanned continuously, and rebuilt on a schedule and on CVE disclosure. Application teams build `FROM` those, which turns a base-image CVE into one platform change plus twenty automatic rebuilds rather than twenty independent investigations. **Registry policy** is centralised: tag immutability and enhanced scanning enforced on every repository by an organisation-wide guardrail, a lifecycle policy required by the infrastructure module that creates repositories, push permission granted only to CI roles, and pull-only repository policies granting workload accounts access. **Pipeline shape** is centralised as a shared template: build with BuildKit for the target architecture, run tests, push tagged with the commit SHA, scan, fail on critical findings, register a task definition pinned to the returned digest, and promote that digest through environments without rebuilding. What is delegated is everything inside the Dockerfile above the base, the service's own resource sizing, its own release cadence, and its own decision to adopt ARM64 — because those are exactly the decisions a team must own for the microservices argument in 1.3.2 to hold. I would place the registry in a shared services account with cross-account pull, so that a compromised workload account cannot alter artefacts, and I would enable signing with verification before deployment once the basics are in place, because signing without immutability and scanning is theatre.

**2. Design the migration of a stateful legacy application, currently running on a single EC2 instance with local disk, into containers. What is the actual work?**

The containerisation is the last step, not the first, and saying so plainly is the substance of the answer. The actual work is **externalising state**, and it decomposes into four distinct problems. First, **data written to local disk**: identify every path the application writes to, then classify each as durable data, cache, or scratch. Durable data moves to RDS or DynamoDB if it is structured, to S3 if it is objects, and to EFS only if the application genuinely requires a POSIX filesystem shared across instances — EFS being the escape hatch that lets a stubborn application be containerised without rewriting it, at the cost of latency and expense. Cache and scratch can stay in the container's writable layer or move to ElastiCache. Second, **session state**: if the application keeps sessions in memory, either move them to ElastiCache or accept sticky sessions at the ALB as a transitional measure with a ticket to remove it. Third, **configuration**: hard-coded paths, hostnames, and credentials become environment variables and `secrets` entries, which is usually more code change than teams expect. Fourth, **lifecycle**: the application must handle `SIGTERM` and must tolerate being started before its dependencies are ready, retrying rather than crashing. Only then do I write the Dockerfile — multi-stage, non-root, minimal base — and only then the task definition. I would run it first as a single-task ECS service behind an ALB, matching the current topology exactly so that the migration changes one variable, and increase the desired count only once the state externalisation is proven. If the application cannot be made to tolerate two concurrent instances, that is a finding to surface early rather than at cutover.

**3. An organisation wants "no container may run in production unless it has been scanned and approved". Design the enforcement, and be honest about what each layer does and does not achieve.**

Enforcement has to exist at several points because no single one is sufficient. At **build time**, the pipeline runs the scan and fails on critical findings — this is the cheapest gate and catches the majority, but it only constrains images that go through that pipeline. At the **registry**, tag immutability prevents an approved tag being repointed to different bytes, enhanced scanning continues to evaluate images after the push, and push permission restricted to CI roles means an engineer cannot upload an unscanned image at all — this is the strongest single control, because it constrains what can exist rather than what can be deployed. At **deployment**, task definitions pin digests, so the specification names exactly the bytes that were scanned, and a pipeline step can verify that the digest's latest scan result is clean before calling `UpdateService`. For genuine enforcement rather than convention, **signing** with AWS Signer plus verification before deployment closes the remaining gap, because it makes provenance cryptographic rather than procedural. What none of this achieves is honest to state: a vulnerability disclosed after deployment is not caught by any build-time gate, which is why continuous scanning with findings routed to Security Hub and a rebuild cadence matter more than the gate itself; and a scanner reports known CVEs in known packages, so it says nothing about the application's own code, which is what SAST and code review are for. I would also note that ECS has no admission-controller equivalent to Kubernetes', so on ECS the enforcement is genuinely in the pipeline and the registry rather than at the cluster — and if the organisation requires cluster-level admission control, that requirement points at EKS and should be stated as such rather than discovered later.

### Troubleshooting Questions

**1. A task starts, runs for a few minutes under load, and stops with exit code 137. What happened and what do you check?**

Exit code 137 is 128 plus 9, meaning the process received `SIGKILL`. Under load, in a container, the overwhelmingly likely cause is the kernel OOM killer terminating the process because it exceeded its memory cgroup limit, which ECS reports as `OutOfMemoryError` in the task's `stoppedReason`. I would confirm that first, because the alternative causes — an operator or the agent sending `SIGKILL` after `stopTimeout` expired during a deployment — have different fixes and are distinguishable from the stopped reason and the timing. Assuming OOM, the investigation has two branches. If memory usage rises steadily and never falls, it is a **leak**, and raising the limit only postpones the failure; the fix is in the application, and the interim mitigation is an alarm on memory utilisation approaching the limit so the failure is predicted rather than discovered. If memory rises only under load and plateaus, the limit is simply **too low** for the workload, and the fix is to size it from measured p99 usage plus headroom. Two container-specific causes are worth checking explicitly because they surprise people: a JVM or other runtime that sizes its heap from the *host's* memory rather than the cgroup limit will happily allocate past the container's ceiling unless it is container-aware or explicitly configured; and a container-level `memory` value lower than the task-level allocation will kill the container even though the task as a whole has room, which looks inexplicable if you only look at task-level metrics.

**2. `RunningTaskCount` sits at 3 while `DesiredTaskCount` is 6, and nothing changes for twenty minutes. Diagnose.**

A persistent gap between desired and running is a placement failure, and the ECS service events almost always name the cause outright — so I would read `describe-services --query 'services[0].events'` before forming any hypothesis. The candidates, in rough order of frequency: on EC2 capacity, **insufficient resources**, where no container instance has enough remaining CPU, memory, or ports, which means the service scaled but the cluster capacity layer did not, and the fix is managed scaling on the capacity provider or a move to Fargate. On any capacity with `awsvpc` mode, **exhausted subnet IP addresses**, since every task consumes a private IP and a small subnet runs out well before compute does — this presents identically and is diagnosed by checking `AvailableIpAddressCount` on the task subnets. On Fargate, an **account quota** on concurrent tasks or a task launch rate limit. And in all cases, **tasks that start and immediately fail**, which produces the same steady-state gap while the scheduler retries; here `RunningTaskCount` is not stuck so much as churning, and the distinguishing evidence is a stream of stopped tasks visible in `list-tasks --desired-status STOPPED`, whose `stoppedReason` names the real problem. The general lesson is that the gap itself is a symptom shared by several causes, and the service event log is the field that discriminates between them.

**3. An image is 1.4 GB and scale-out is visibly slow. Walk through reducing it.**

First I would measure rather than assume, using `pullStartedAt` and `pullStoppedAt` from `DescribeTasks` to establish how much of the start latency is actually the pull — because if the pull is four seconds and the application takes forty to warm up, shrinking the image is the wrong work. Assuming the pull dominates, the reductions in order of value are: **multi-stage build**, moving compilers, headers, package managers, and test dependencies out of the shipped stage, which for a compiled language typically removes 90 per cent of the image on its own; **a minimal runtime base**, replacing a full distribution with a slim variant or a distroless image; **layer hygiene**, chaining `RUN` instructions so that package-manager caches are removed in the same layer that created them rather than a later one; **a `.dockerignore`**, so that `.git`, local dependency directories, and test fixtures never enter the build context; and **dependency pruning**, installing production dependencies only. Alongside the image itself I would check the network path, because a large image pulled through a NAT gateway is slower and more expensive than the same image pulled through VPC endpoints, and I would confirm the repository is in the same Region as the tasks. On EC2 capacity, longer-lived instances give a warm layer cache that removes most of the pull entirely for subsequent tasks. I would expect a Go or Rust service to end below 30 MB, a Node or Python service somewhere between 100 and 250 MB, and a JVM service between 200 and 400 MB with a trimmed runtime — and I would treat anything far above those as evidence that build artefacts are still being shipped.

### Certification-style Questions

**1. A company must ensure that a container image deployed to production is exactly the image that was tested, and must be able to prove it to an auditor. Which combination is most appropriate?**

A. Tag images with `latest` and enable versioning on the repository
B. Enable ECR tag immutability, tag with the commit SHA, and reference the image digest in the task definition
C. Rebuild the image in each environment from the same Dockerfile
D. Store images in Amazon S3 and download them at task start

**Answer: B.** Tag immutability prevents a tag being repointed, the commit SHA ties the artefact to source, and the digest reference makes the deployed bytes cryptographically exact. A is wrong because `latest` is a mutable pointer and ECR does not offer S3-style object versioning of tags. C is the classic error: identical Dockerfiles do not produce identical images, because base images and transitive dependencies move. D discards the registry's authorisation, scanning, and lifecycle features and is not how container runtimes fetch images.

**2. ECS tasks in a private subnet with no NAT gateway fail with `CannotPullContainerError`. Interface VPC endpoints for `ecr.api` and `ecr.dkr` already exist. What else is required?**

A. An interface endpoint for Amazon EC2
B. A gateway endpoint for Amazon S3
C. A NAT gateway in each Availability Zone
D. A public IP address assigned to each task

**Answer: B.** ECR stores image layer blobs in Amazon S3, so the pull needs an S3 route; a gateway endpoint provides it at no hourly charge. A is unrelated. C would work but reintroduces the cost and internet dependency the endpoints were adopted to remove. D exposes tasks publicly and is the opposite of the intended design.

**3. An application container must read a database password at start-up without the password being visible to anyone who can describe the task definition. Which approach is correct?**

A. Add the password to the `environment` block of the container definition
B. Bake the password into the image with a Dockerfile `ARG`
C. Reference an AWS Secrets Manager secret in the `secrets` block of the container definition
D. Store the password in the container's writable layer at build time

**Answer: C.** The `secrets` block causes the ECS agent to retrieve and inject the value at task start using the **execution role**, so the plaintext never appears in the task definition. A is readable by anyone with `ecs:DescribeTaskDefinition` and appears in templates and Git history. B persists the value in image history, readable by anyone who can pull. D is B with extra steps.

**4. A team's images are built on ARM-based laptops and fail on x86_64 Fargate with `exec format error`. Which is the most appropriate durable fix?**

A. Increase the task's CPU and memory allocation
B. Build in CI for `linux/amd64`, or publish a multi-architecture image, and set `runtimePlatform` explicitly
C. Switch the task definition to `bridge` network mode
D. Enable enhanced scanning on the repository

**Answer: B.** The image's instruction set must match the capacity's. Building in CI removes the workstation architecture from the equation, a multi-architecture image serves both, and setting `runtimePlatform` makes the intended target explicit in the specification rather than defaulted. A, C, and D address unrelated concerns.

**5. Which statement about ECS task definitions is correct?**

A. A task definition can be edited in place, and running tasks pick up the change
B. Registering a change creates a new revision; running tasks continue on their existing revision until the service is updated
C. A task definition can contain at most one container
D. Task definitions are global across all AWS Regions

**Answer: B.** Task definitions are immutable and versioned by revision, which is precisely what makes rollback a pointer change to an earlier revision. A describes mutable configuration, which ECS deliberately does not offer. C is wrong; a task definition may contain up to ten containers, which is what makes the sidecar pattern possible. D is wrong; task definitions are regional, like ECR repositories.

**6. A company wants to eliminate a public container registry from its deployment path while continuing to use community base images. Which ECR feature addresses this?**

A. Cross-Region replication
B. Lifecycle policies
C. Pull-through cache
D. Enhanced scanning

**Answer: C.** A pull-through cache rule creates an ECR repository that transparently caches images from a supported upstream public registry, so subsequent pulls are served from ECR — removing the external availability dependency and the rate limits, and bringing the third-party content under your own scanning and retention policy. A addresses multi-Region latency, B addresses storage cost, and D addresses vulnerability detection.

## Interview Questions

### Conceptual Questions

**1. What is an ECS cluster, and on what basis should cluster boundaries be drawn?**

An ECS cluster is a logical grouping of services, tasks, and container instances. It is not a machine, not a control plane you operate, and not something you pay for: there is no cluster endpoint, no version, nothing to patch, and no hourly charge. What it actually provides is four boundaries. It is a **namespace**, since service names are unique within a cluster rather than within an account. It is a **capacity boundary**, since container instances register with exactly one cluster and tasks are only placed on capacity in their own cluster. It is a **permissions boundary**, since `ecs:*` actions can be scoped to a cluster ARN, which is how "this pipeline may deploy to staging and nowhere else" is expressed. And it is an **observability boundary**, since Container Insights and most dashboards are naturally cluster-scoped. Boundaries should therefore be drawn by asking three questions: who should be able to deploy here, what should fail together, and what should be observed together. If two workloads have the same answers, they belong together. On EC2 capacity there is a fourth question — should these workloads share instances — because sharing improves bin packing and weakens isolation. The common correct answer at moderate scale is a cluster per team per environment; cluster per service is almost always wrong, because clusters are free but not costless and every cross-cutting change becomes N changes.

**2. Explain the two scaling layers on ECS with EC2 capacity, and describe the failure that results from configuring only one.**

The first layer is **service auto scaling**, implemented by Application Auto Scaling, which changes a service's `desiredCount` in response to a metric such as requests per target or CPU. The second is **cluster capacity scaling**, implemented by an Auto Scaling group capacity provider with managed scaling enabled, which changes the number of EC2 instances so that tasks have somewhere to be placed. ECS publishes a `CapacityProviderReservation` metric expressing how much capacity is needed relative to what exists, and managed scaling drives the ASG towards the configured target capacity. If only the first layer is configured, the failure is characteristic and confusing: under load the service raises its desired count to, say, forty, twelve tasks run, and twenty-eight sit in `PROVISIONING` indefinitely, while the CPU graphs of the existing instances look entirely healthy because those instances are simply full. The diagnosis is in the service events, which state that no container instance had sufficient CPU, memory, or ports. The remedy is to enable managed scaling with a target capacity below 100 per cent so there is headroom for immediate placement, together with managed termination protection so scale-in does not kill running tasks and managed draining so terminations relocate work first. On Fargate this entire layer does not exist, which removes a whole class of misconfiguration and is one of the strongest practical arguments for Fargate for teams without a platform function.

**3. Compare the mechanisms by which one ECS service can reach another, and state the axis on which they actually differ.**

The axis is **where the routing decision is made**, and everything else follows from it. An **internal load balancer** decides at the load balancer: this adds a network hop, an hourly charge, and a tail-latency contribution, but works across VPCs and accounts and handles protocol translation. **AWS Cloud Map DNS** decides in the client after resolution: no extra hop and protocol-agnostic, but it inherits DNS caching semantics, and some client runtimes cache resolutions well beyond the TTL, so a caller can hold the address of a task that stopped minutes ago — a failure that appears only during deployments and scale-in. **ECS Service Connect** decides in an AWS-managed, Envoy-based proxy running inside the task: the application calls a name on localhost, and the proxy performs endpoint discovery in the background, client-side load balancing, connection pooling, outlier ejection, and per-call telemetry broken down by client and server. It adds no network hop and makes no control-plane call on the request path, which is why it survives both control-plane impairment and DNS caching problems. **Amazon VPC Lattice** decides in the VPC data plane and is the answer for connectivity across VPCs, accounts, and compute types with IAM auth policies, without sidecars. The practical guidance is Service Connect for ECS-to-ECS HTTP and gRPC, Cloud Map for non-HTTP, and Lattice when crossing a boundary Service Connect does not span. AWS App Mesh should not be chosen for new work.

**4. What survives an ECS control-plane impairment, and what design error does that fact expose?**

Running traffic survives. Existing tasks keep serving requests, the load balancer keeps routing to targets it already knows are healthy, established connections are unaffected, and Service Connect proxies keep using their existing endpoint lists. What is lost is the ability to *change* anything: no new deployments, no replacement of a task that fails during the impairment, no scaling. That bounds a control-plane incident to "serious but survivable" rather than "outage" — provided nothing in the request path depends on a control-plane call. The design error the fact exposes is exactly that: a service that calls `ecs:DescribeTasks` or `ecs:ListTasks` to discover a peer on each request has coupled its own availability to the control plane's and discarded the isolation the architecture provided. It will also encounter API throttling, which manifests as a latency cliff under precisely the load you least want it. Peer discovery belongs in the Service Connect proxy or in DNS resolved from a local cache, both of which continue to function when the control plane does not.

**5. Explain what a capacity provider strategy's `base` and `weight` actually do, and how you would choose values.**

A capacity provider strategy is a list of providers, each with a `base` and a `weight`. The `base` is an **absolute number of tasks** placed on that provider before any weighting is applied, and at most one provider in a strategy may have a non-zero base. The `weight` governs how tasks **beyond the bases** are distributed proportionally. With `FARGATE` at `base=2, weight=1` and `FARGATE_SPOT` at `weight=4`, a desired count of twelve produces two tasks on On-Demand to satisfy the base, then the remaining ten split one-to-four, giving four On-Demand and eight Spot in total. Choosing the values is a reliability decision rather than a cost one. The `base` should be the number of tasks that can carry minimum viable traffic on their own, because that is what survives a total Spot reclamation event — if two tasks cannot serve your floor traffic, the base is wrong. The weight then expresses the steady-state economics, and one-to-four is a reasonable starting point for a service that tolerates interruption. For a synchronous user-facing path I would want a base sized to real traffic; for an asynchronous worker I would often run entirely on Spot with a base of zero, because a delayed message is not a failed request.

### Scenario Questions

**1. A team runs twelve services on ECS with EC2 capacity and reports that scale-out during traffic peaks takes several minutes, during which users see errors. Diagnose and design the fix.**

The several-minute delay is almost certainly instance launch time on the critical path, and I would confirm it by checking whether tasks are entering `PROVISIONING` and waiting, and whether the ASG desired capacity is increasing at the same moment. If so, the cluster capacity layer is reacting *after* the service scaling layer has already run out of room, which means the sequence is: load arrives, service raises desired count, no instance fits, capacity provider notices, ASG launches an instance, the instance boots and registers, the agent pulls the image, and only then does a task start serving. That is easily two to three minutes even when everything works. The fixes are cumulative. First, set **target capacity below 100 per cent** — 80 to 90 for a user-facing service — so there is always room for a task to place immediately while the instance launch happens behind it; this trades a modest amount of idle cost for the entire instance-launch delay. Second, **scale earlier**: use `ALBRequestCountPerTarget` with a target below saturation rather than CPU, and set a short scale-out cooldown with a long scale-in cooldown, so the service adds capacity before it is saturated. Third, **shrink the image**, because on a cold instance the pull is on the critical path. Fourth, if the peak is calendar-driven, **pre-scale on a schedule** and let target tracking handle the variance above that floor, because reactive scaling cannot outrun a step change in load. Fifth, consider whether these services should be on **Fargate** at all: it removes the instance-launch layer entirely, and for twelve services on a small team the premium may well be cheaper than the engineering attention this problem is consuming.

**2. During deployments, one service returns intermittent 502 errors for about thirty seconds. Nothing appears in the application logs. Walk through the diagnosis.**

The absence of application log entries is itself the strongest clue: the errors are being generated by the load balancer rather than by the application, which points at connection handling rather than at application logic. I would check four settings, all of which interact. First, the target group's **deregistration delay**: if it is very low, the ALB removes the target and cuts connections that are still in flight; it should exceed the p99 request duration. Second, the application's **`SIGTERM` handling**: ECS sends `SIGTERM` and then `SIGKILL` after `stopTimeout`, so an application that does not trap the signal to stop accepting new work and drain existing work simply dies mid-request. A very common root cause here is an `ENTRYPOINT` in shell form, which makes `/bin/sh` PID 1 and prevents the signal reaching the application at all — so I would check the image's entrypoint form before reading any application code. Third, **`stopTimeout`** must be long enough for the drain to complete. Fourth, and the one that explains errors *outside* deployments as well, the application's **keep-alive idle timeout** must exceed the ALB's, or the ALB will occasionally reuse a connection the backend has just closed. I would also distinguish `HTTPCode_ELB_5XX_Count` from `HTTPCode_Target_5XX_Count` in CloudWatch, because the former means the ALB had no healthy target or could not reach one, and the latter means the application returned an error — and only the first is consistent with silent application logs.

**3. A start-up asks whether to run their eight services on Fargate or on EC2 capacity, having read that Fargate is "more expensive". How do you respond?**

I would say that the unit-price comparison is real but almost never the decisive one, and then make the comparison they have not made. Fargate does carry a per-vCPU premium over equivalent EC2 capacity. That premium matters when utilisation is sustained and high, because you are paying more for compute you are fully using. It is irrelevant when utilisation is spiky or low, because EC2's advantage is per-vCPU and its disadvantage is that you pay for the whole instance whether tasks use it or not — and eight services on a small team almost never bin-pack into full instances. Then there is the cost that does not appear on the invoice: with EC2 capacity they acquire AMI patching, ASG management, capacity provider tuning, bin packing, instance draining, the IMDS hazard, and a second scaling layer to understand and monitor. For a small team that is a meaningful fraction of one engineer, permanently, and it is drawn from the same budget as product work. My recommendation would be Fargate as the default, with a specific and testable condition for revisiting it: if a workload shows sustained utilisation above roughly 60 to 70 per cent around the clock, or needs a GPU, a host daemon, privileged mode, or local NVMe, move that workload — and only that workload — to EC2 capacity, with Savings Plans and Spot. I would also point out that the same task definition runs on both, so this is a reversible decision rather than a commitment, and that Fargate additionally gives a microVM isolation boundary per task that EC2 capacity cannot match at any price.

**4. Two ECS services need to communicate. A colleague proposes an internal ALB between them. Evaluate the proposal and offer alternatives.**

The proposal works and I would not call it wrong, but it is usually the most expensive of the available options on three axes at once. It adds a network hop, which contributes to tail latency on every call; it adds an hourly charge plus LCU charges per service pair; and it gives only coarse health-based routing with no retries, no outlier ejection, and no per-caller telemetry. For two ECS services in the same VPC, **ECS Service Connect** does the same job better: the managed proxy runs inside the task, so the call goes over localhost to a pooled connection, endpoint discovery happens in the background rather than per request, failing endpoints are ejected automatically, and CloudWatch receives request counts and error rates broken down by client and server — which answers "which caller is causing this callee's errors" with no application instrumentation. The cost is the proxy's resource overhead in every task, which is real but small. I would recommend the internal ALB only in specific circumstances: when the caller is outside the Service Connect namespace, when it is in a different VPC or account and VPC Lattice is not in play, when protocol translation is needed, or when the callee is not on ECS at all. And I would note that whichever mechanism is chosen, the more important question is whether this call needs to be synchronous — because if the caller does not need the answer to serve its own caller, an event through EventBridge removes the availability coupling entirely, which is worth more than any optimisation of the call itself.

### Architecture Questions

**1. Design the ECS topology for an organisation with four teams, three environments, and twenty-two services, and justify every boundary you draw.**

I would use **one AWS account per environment** — development, staging, production — because the account is the strongest available boundary and it makes "a mistake in staging cannot affect production" a structural fact rather than an IAM claim. Within each account I would create **one cluster per team**, giving twelve clusters in total, which costs nothing on ECS and yields four benefits: IAM policies scope `ecs:*` to a cluster ARN so each team's pipeline can deploy only to its own cluster; capacity exhaustion by one team's workload cannot starve another's; Container Insights dashboards are naturally per team; and cost attribution follows the cluster without relying on tag discipline alone. Within each cluster, each service is a service, and all of a team's services share **one Application Load Balancer** with path- or host-based listener rules, so adding a service costs a rule rather than a load balancer. East-west traffic uses **Service Connect with one Cloud Map namespace per environment**, so `http://catalog:8080` means the right thing in every environment and a staging service cannot resolve a production peer. Cross-team calls within an environment also use Service Connect if the namespace is shared at the environment level, or VPC Lattice if teams end up in separate VPCs. Capacity is **Fargate by default**, with a capacity provider strategy of an On-Demand base plus Spot for asynchronous workers, and EC2 capacity introduced only for a workload that demonstrates a hardware or sustained-utilisation requirement. What I would explicitly avoid is a cluster per service, which at twenty-two services turns every cross-cutting change into twenty-two changes and leaves no estate-wide view.

**2. Design the north-south and east-west paths for a system with a public web API, an internal admin API, a partner API, and six internal services.**

The three external surfaces have genuinely different requirements, and forcing them through one mechanism is the mistake to avoid. The **public web API** goes behind CloudFront with AWS WAF for edge TLS termination, caching, and rate-based filtering, then to a shared internet-facing ALB with a listener rule per service and `ip` target groups. The **internal admin API** goes behind an internal ALB reachable only from the corporate network via VPN or AWS Direct Connect, or is exposed through the same ALB with an authentication requirement — my preference is a separate internal ALB, because keeping the admin surface off the internet entirely is worth an extra load balancer. The **partner API** goes behind **Amazon API Gateway**, because that is where per-consumer API keys, usage plans, request validation, and per-partner throttling exist, and building those on an ALB means building them in application code in every service. Behind API Gateway I would use a VPC link to an internal ALB rather than exposing services directly. **East-west** among the six internal services uses Service Connect within one namespace, and I would keep the synchronous call graph deliberately shallow — ideally no more than two hops on any user-facing path — with everything else moved onto EventBridge and SQS, because availability multiplies down a synchronous chain and latency adds up it. All services sit in private subnets with no public IPs and a full VPC endpoint set, so the only publicly reachable resources in the account are the load balancers and the CloudFront distribution.

**3. A workload must run partly on Spot for cost and partly on guaranteed capacity for availability, and must survive a total Spot reclamation event without user-visible failure. Design it and state what you are assuming.**

I would express this as a capacity provider strategy with a non-zero `base` on the On-Demand provider, and the sizing of that base is the entire design. The base must be the number of tasks that can carry **minimum viable traffic** unaided — not a token number, but the count you would run if Spot did not exist and you were willing to degrade. I would establish that number from measurement rather than intuition: requests per second at the traffic floor divided by measured requests per task at an acceptable latency, plus a margin for the loss of one Availability Zone. Above that base, the weight distributes the remainder, and one-to-four On-Demand to Spot is a reasonable starting ratio. Three further mechanisms are required for the "without user-visible failure" clause to hold. First, **graceful handling of reclamation**: Fargate Spot gives two minutes' notice via a `SIGTERM`, so the application must drain, and on EC2 Spot the capacity provider's managed draining must be enabled so the instance is drained rather than killed. Second, **fast replacement**: small images and, on EC2, target capacity below 100 per cent so replacement tasks place immediately. Third, **an alarm on the gap** between running and desired task count, so a sustained shortfall pages someone rather than silently degrading. The assumptions I am making and would state explicitly: that a brief period at base capacity is acceptable rather than catastrophic; that Spot capacity for the chosen configuration is generally available in the Region, which on EC2 argues for a mixed-instances policy across several compatible types; and that the workload is genuinely stateless, because a reclaimed task that was holding state loses it.

### Troubleshooting Questions

**1. `RunningTaskCount` is 6 and `DesiredTaskCount` is 20, and has been for fifteen minutes. Diagnose systematically.**

I would read the **service events** first, because a persistent desired-versus-running gap is a placement failure and the events almost always name the reason outright. The candidates, in order of frequency: on EC2 capacity, **insufficient resources** on every container instance, meaning the service scaled but the capacity layer did not, which is fixed by enabling managed scaling with headroom or by moving to Fargate; on any capacity in `awsvpc` mode, **exhausted subnet IP addresses**, which presents identically and is confirmed by checking `AvailableIpAddressCount` on the task subnets; on Fargate, an **account quota** on concurrent tasks or a task launch rate limit; a **placement constraint** that no instance satisfies, such as an attribute expression referencing an instance type that no longer exists in the ASG; and finally **tasks that start and immediately fail**, which produces the same steady-state gap while the scheduler retries. That last case is distinguishable because `RunningTaskCount` is churning rather than static, and it is confirmed by listing stopped tasks and reading their `stoppedReason` — which will name an image pull failure, an OOM kill, or an application exit. The general point is that the gap is a symptom shared by several causes, and the service event log is the field that discriminates between them, so reading it first saves most of the investigation.

**2. Tasks reach `RUNNING` but the target group reports them unhealthy, and the service never stabilises. Work through the causes.**

The task is running and the network health check is failing, so the fault is between the load balancer and the application rather than in the application's ability to start. I would check five things in order. First, the **security group**: the task's security group must allow the health-check port *from the load balancer's security group*, and a rule written as a CIDR that no longer matches, or a missing rule entirely, is the most common cause. Second, the **port**: the target group's port and the container port must agree, and with `ip` targets the traffic goes to the container port directly rather than to a host port. Third, the **path**: a health-check path that requires authentication, redirects, or returns a status outside the expected matcher range will fail even though the application is fine — a `/health` endpoint that returns 302 to a login page is a classic. Fourth, the **grace period**: if the application takes 45 seconds to warm up and `healthCheckGracePeriodSeconds` is 0, the ALB marks it unhealthy and the service kills and replaces it in a loop, producing exactly "never stabilises" while the logs show normal start-up every time. Fifth, the **subnets**: the load balancer and the tasks must be in subnets that can reach each other, which in practice means the ALB in public subnets and tasks in private subnets in the same VPC and AZs. I would read the `TargetHealth.Reason` string from `describe-target-health`, because it distinguishes `Target.Timeout` — a networking or security group problem — from `Target.ResponseCodeMismatch`, which is an application or path problem, and that single field usually halves the search.

**3. After enabling ECS Service Connect, one service can no longer reach another, and the client receives connection refused. Diagnose.**

I would check the mechanics in the order in which they can silently be wrong. First, the **`portMappings.name`**: Service Connect advertises a named port mapping, and a mapping without a `name` cannot be advertised, so the server side may have deployed successfully while advertising nothing. Second, the **client alias and discovery name**: the caller must use the hostname and port declared in the client alias, and a mismatch between what the application calls and what was advertised produces exactly this symptom. Third, whether the **client side is enabled** on the calling service — a service that is only configured as a server does not get a proxy able to resolve names. Fourth, whether both services are in the **same Cloud Map namespace**, since a namespace per environment is good practice but a caller in the wrong namespace will resolve nothing. Fifth, whether the calling service was **redeployed after** Service Connect was enabled, because the proxy is injected at task start and an existing task has no proxy. And sixth, **security groups**: Service Connect removes the load balancer but not the network, so the callee's security group must still permit the caller's on the container port. I would confirm from inside the caller with ECS Exec, resolving the alias and issuing a request, because that distinguishes a name-resolution failure from a connectivity failure in one step — and I would look at the `ECS/ServiceConnect` CloudWatch metrics, which will show zero requests reaching the server if discovery is the problem and non-zero requests with errors if connectivity is.

### Certification-style Questions

**1. A company runs an ECS service on EC2 capacity. During peak traffic the service's desired count increases but many tasks remain in `PROVISIONING`. Instances show adequate CPU. What is the most likely cause?**

A. The task definition requests too much memory
B. Capacity provider managed scaling is not enabled, so no instances are being added
C. The Application Load Balancer health check is failing
D. The tasks are using `awsvpc` mode

**Answer: B.** Service auto scaling changes task count; capacity provider managed scaling changes instance count. Without the second layer, tasks queue in `PROVISIONING` with nowhere to be placed. A would prevent placement but would show in service events as a resource message and would not be peak-specific. C would produce unhealthy targets, not `PROVISIONING`. D is a normal configuration, though IP exhaustion in `awsvpc` mode is a separate cause worth checking.

**2. Which combination is required for an ECS service using `awsvpc` network mode behind an Application Load Balancer?**

A. Target type `instance` and dynamic port mapping
B. Target type `ip` and a security group on the task permitting the ALB's security group
C. Target type `instance` and a public IP address on each task
D. An internal Network Load Balancer in front of the ALB

**Answer: B.** `awsvpc` gives each task its own ENI and IP, so targets are registered by IP, and the task's own security group must permit the load balancer. A and C describe `bridge`-mode patterns and `instance` targets are incompatible with `awsvpc`. D adds an unnecessary component.

**3. A workload requires GPU acceleration and runs continuously at high utilisation. Which capacity option is appropriate?**

A. AWS Fargate with increased task CPU
B. AWS Fargate Spot
C. Amazon EC2 capacity with GPU instance types and Compute Savings Plans
D. AWS Lambda with a container image

**Answer: C.** Fargate offers no GPU support at all, which eliminates A and B regardless of cost; sustained high utilisation additionally favours EC2 with commitments. D has no GPU support and a short execution ceiling unsuited to continuous work.

**4. Two ECS services in the same VPC must communicate over HTTP with client-side load balancing, automatic removal of failing endpoints, and per-caller metrics, without adding a network hop. Which should be used?**

A. An internal Application Load Balancer between them
B. ECS Service Connect
C. AWS Cloud Map DNS-based service discovery
D. AWS App Mesh

**Answer: B.** Service Connect injects an AWS-managed, Envoy-based proxy inside each task, giving client-side load balancing, outlier ejection, retries, and per-client and per-server metrics with no extra network hop and no load balancer. A adds a hop and an hourly charge and offers only coarse routing. C provides discovery only, with DNS caching problems and no retries. D is on a deprecation trajectory and should not be chosen for new work.

**5. Which statement about ECS capacity provider strategies is correct?**

A. `weight` specifies an absolute number of tasks and `base` a percentage
B. `base` specifies an absolute number of tasks placed first; `weight` distributes the remainder proportionally
C. Multiple capacity providers in one strategy may each have a non-zero `base`
D. A capacity provider strategy can only reference one provider

**Answer: B.** The base is satisfied first as an absolute count and only the remainder is distributed by weight. C is wrong: at most one provider in a strategy may have a non-zero base. D is wrong, and mixing providers is the main reason strategies exist.

**6. A team must guarantee that a compromised container cannot obtain credentials belonging to other workloads on the same host. Which approach most directly achieves this?**

A. Use `bridge` network mode with dynamic port mapping
B. Run the workload on AWS Fargate
C. Increase the task's memory limit
D. Enable Container Insights

**Answer: B.** Fargate runs each task in its own microVM with no shared host, so there is no container instance role to obtain and no co-tenant workload on the same kernel. On EC2 capacity the equivalent mitigation is IMDSv2 with a hop limit of 1 plus a minimal container instance role, but that is a configuration you must apply correctly rather than a property of the platform. A weakens isolation by making tasks share the instance's security group. C and D are unrelated.

## Interview Questions

### Conceptual Questions

**1. Explain the difference between a placement constraint and a placement strategy, and why the distinction matters operationally.**

They act at different stages of the scheduler's pipeline and have different failure modes. A **constraint** is a filter: `distinctInstance` and `memberOf` expressions remove candidate container instances from consideration before any sorting happens. A **strategy** is a sort key: `spread`, `binpack`, and `random` order the candidates that survived filtering, and strategies are applied as an ordered list so that later ones break ties left by earlier ones. The operational consequence is that a constraint can make placement **impossible** — if no instance satisfies it, the task stays in `PROVISIONING` indefinitely and the service event states that no container instance met the requirements — whereas a strategy can never make placement impossible, only suboptimal. This is why a stale `memberOf` expression referencing an instance type that has since left the Auto Scaling group produces a service that will not run at all on a cluster with abundant free capacity, and why a badly ordered strategy produces a service that runs but is concentrated in one Availability Zone. Both are configuration errors; only one is visible as a failure. The second consequence is that constraints silently cap scaling: `distinctInstance` limits a service to as many tasks as there are instances, and nothing reports the cap as an error.

**2. Why is `ALBRequestCountPerTarget` usually a better scaling signal than CPU utilisation, and what property must any target-tracking metric have?**

The required property is that the metric must be **load per unit of capacity**, so that adding tasks reduces it roughly proportionally. Target tracking computes a new desired count as approximately the current count multiplied by the ratio of the current metric value to the target, which only converges if that assumption holds. `ALBRequestCountPerTarget` has the property by construction: it is requests divided by the number of targets, so doubling the targets halves it. CPU utilisation has the property too, but only when the work is CPU-bound; for an I/O-bound service waiting on a database, CPU stays low while requests queue behind an exhausted connection pool, so the metric never approaches the target and the policy never fires while p99 latency climbs. Raw queue depth fails the property entirely, because it has no denominator: adding consumers does not change the depth measurement, so the controller multiplies capacity by a ratio that its own action does not affect, and the loop oscillates. The correct queue signal is backlog per task, which restores the denominator. The general rule worth carrying is that a scaling metric is a proxy for arriving work relative to available capacity, and any metric that ignores capacity will make the controller unstable.

**3. What does the deployment circuit breaker detect, what can it not detect, and what covers the gap?**

The circuit breaker monitors a rolling deployment and, when new tasks repeatedly fail to reach a healthy state, marks the deployment failed and — with rollback enabled — redeploys the previous revision automatically. It detects tasks that fail to start, containers that exit immediately, images that cannot be pulled, containers failing their `healthCheck`, and targets that never become healthy at the load balancer. What it cannot detect is a version that starts cleanly, passes `/health`, registers successfully, and behaves incorrectly — returning wrong answers, calculating something subtly wrong, or running substantially slower. From the circuit breaker's point of view that deployment is a complete success. The gap is covered by **CloudWatch alarm-based rollback**, configured alongside the deployment, which rolls back when a named alarm on 5xx rate, p99 latency, or a business metric enters `ALARM` during the bake period; and, more thoroughly, by **CodeDeploy canary shifting with lifecycle hooks**, where an `AfterAllowTestTraffic` Lambda can run an actual test suite against the green task set before production traffic reaches it. The framing I would use is that the circuit breaker asks "did it start", the alarm asks "is it harming users", and only the hook asks "is it correct" — and a service configured with only the first is protected against roughly half the realistic failure space.

**4. Explain what `minimumHealthyPercent` and `maximumPercent` actually do, and describe a legitimate use of the configuration most people would call wrong.**

They bound the rolling update. `minimumHealthyPercent` is the floor, as a percentage of desired count, below which the number of **healthy** tasks must not fall; `maximumPercent` is the ceiling on total tasks, old plus new, during the transition. With a desired count of 10, `min 100 / max 200` means the scheduler may start up to 10 new tasks and may only stop an old task once a new healthy one exists, so capacity never dips — this is the production default. `min 100 / max 150` does the same in smaller batches when capacity is constrained. `min 50 / max 100` stops old tasks first and therefore deliberately halves serving capacity during the deployment. The configuration most people would call wrong is **`min 0 / max 100`**, which stops every old task before starting any new one and accepts a gap in service. It is nonetheless correct for a **singleton** workload — a scheduler, a leader process, or anything holding an exclusive lock — where two concurrent instances would be a correctness bug rather than merely wasteful. Applying the usual advice of `min 100` to such a workload guarantees a period where two instances run simultaneously, which is exactly what must not happen. This is a good example of why the reasoning matters more than the recommendation.

**5. Why is placement an availability decision, and how would you verify that your placement is actually working?**

Because an Availability Zone is a **correlated failure domain**: every task in a zone fails together when that zone fails, which is the specific event multi-AZ architecture exists to survive. A service with six tasks spread evenly across three zones loses a third of its capacity in a zone event and continues serving; the same service with five of six tasks in one zone loses essentially everything. The configuration that produces the first outcome is a `spread` strategy on `attribute:ecs.availability-zone` as the **first** entry in the strategy list, with `binpack` second so density is achieved within the zone rather than across it. What makes this a trap is that supplying three subnets **permits** even distribution without **guaranteeing** it — the default behaviour is not a promise, and an unevenly sized fleet across zones will produce an uneven task distribution. Verification is therefore part of the design, not an optional extra: I would build a dashboard showing running task count per Availability Zone per service, derived from Container Insights or a Logs Insights query over task metadata, and check it after every capacity or fleet change. On Fargate the equivalent verification still applies even though the strategy does not, because distribution follows the subnets supplied and a service configured with two subnets instead of three is a quieter version of the same problem.

### Scenario Questions

**1. A service scales out during peak but users still see elevated latency for the first three minutes of every peak. Diagnose and fix.**

Three minutes is the scaling pipeline's end-to-end latency, so the fix is either to shorten it or to stop relying on it. I would first decompose the interval, because the levers differ per phase: metric publication and alarm evaluation (typically 60 to 120 seconds), capacity acquisition if this is EC2 and the cluster has no headroom (60 to 180 seconds), image pull and container start, and the target group's healthy threshold. `pullStartedAt` and `pullStoppedAt` from `DescribeTasks` isolate the pull, and service event timestamps isolate the rest. The remedies, in order of effect: **lower the scaling target value** so the policy fires before saturation rather than after — this usually helps more than any other single change, because it starts the pipeline earlier rather than trying to shorten steps that are mostly fixed; **maintain capacity headroom** by setting the capacity provider's target capacity to 80 to 90 per cent, so tasks place immediately instead of waiting for an instance; **shrink the image**, since on Fargate every task pays a full pull; **shorten the health-check interval and healthy threshold** within reason; and **shorten the alarm evaluation period**, accepting more sensitivity to noise. But if the peak is predictable — and a peak that happens every day at the same time is predictable — the correct answer is **scheduled scaling** that raises the minimum capacity before it arrives, with target tracking handling only the variance above that floor. Reactive scaling cannot outrun a step change in load, and no amount of tuning will make it do so.

**2. A queue consumer service oscillates between 2 and 40 tasks continuously. Explain the mechanism and fix it.**

The oscillation is almost certainly caused by scaling on `ApproximateNumberOfMessagesVisible` directly. Target tracking computes new capacity as current capacity times the ratio of the metric to the target, which requires the metric to fall as capacity rises. Raw queue depth does not: adding consumers drains the queue, so the metric collapses to near zero, so the controller scales in hard, so the queue rebuilds, so it scales out hard again. The controller is chasing a signal that does not reflect its own actions in a proportional way. The fix is to scale on **backlog per task** — `ApproximateNumberOfMessagesVisible` divided by `RunningTaskCount`, expressed as a CloudWatch metric math expression and used as a customised metric specification. That metric halves when you double the consumers, which is exactly what target tracking needs. The target value should be derived rather than guessed: if a task processes a message every 0.2 seconds and the business promise is that a message is handled within 60 seconds, the target is 60 / 0.2 = 300 messages per task. Alongside that I would lengthen the scale-in cooldown to at least 300 seconds so brief lulls do not trigger scale-in, and alarm separately on `ApproximateAgeOfOldestMessage`, because that measures whether the promise is actually being kept and is a different question from how the service scales. I would also check that the consumer's batch size and visibility timeout are sane, since a very small batch size makes per-message overhead dominate and distorts the processing rate the target was derived from.

**3. During an Availability Zone impairment, a service configured with three subnets and six tasks went down completely. Explain how this is possible and what you would change.**

It is possible because three subnets permit distribution across three zones but do not guarantee it. On EC2 capacity, if the cluster's instances are unevenly distributed — because the Auto Scaling group scaled in a way that concentrated instances, or because one zone had capacity constraints at launch time — and the service has no `spread` strategy on `attribute:ecs.availability-zone`, tasks follow whatever the default placement produces, which can be heavily skewed. The team believed they were multi-AZ because the configuration mentioned three subnets, and never verified the actual distribution. The changes I would make are cumulative. First, add `spread` on `attribute:ecs.availability-zone` as the **first** placement strategy, with `binpack` on memory second. Second, ensure the Auto Scaling group itself spans three zones and is balanced, since the scheduler cannot spread across zones that have no instances. Third, build a dashboard showing running tasks per zone per service and check it after every fleet change — this is the control that would have caught the problem before the incident. Fourth, raise the service's minimum capacity to at least three so that even distribution is achievable. Fifth, review whether the ALB has cross-zone load balancing enabled, because with an uneven distribution and cross-zone disabled, traffic distribution compounds the problem. And I would note that on Fargate the same class of error appears as a service configured with two subnets instead of three, which is quieter but has the same consequence.

**4. A team wants to adopt blue/green deployment for all twenty of their services because "it is safer". Evaluate the proposal.**

Blue/green is safer **if the validation hooks are written**, and considerably more expensive if they are not — so my response would depend on whether the team intends to write them. What blue/green genuinely provides over a rolling update is threefold: a complete second task set validated in the production environment before any user traffic reaches it, percentage-based traffic shifting rather than shifting by task count, and rollback as a routing change measured in seconds rather than a redeployment measured in minutes. What it costs is double capacity for the duration of the deployment and bake period, two target groups and possibly a test listener designed in from the start, Lambda hook functions to write and maintain as production-critical code, and a longer deployment. If the team adopts the topology and never writes a hook, they have paid all of that for faster rollback alone — which is a real benefit but a poor return. My recommendation would be to apply blue/green selectively: to the services where a bad release is expensive and where someone will actually write and maintain the smoke suite — typically the user-facing revenue path and anything regulated — and to use rolling updates with the circuit breaker and alarm-based rollback everywhere else. I would also point out that the cheapest and most effective safety improvement available to all twenty services is not a deployment mechanism at all: it is **separating deploy from release with feature flags**, which makes deployment boring, makes exposure gradual, and makes reverting instantaneous, and which works with either controller.

### Architecture Questions

**1. Design the complete orchestration configuration for a checkout service with a strict availability requirement, a daily traffic peak, and a business that cannot tolerate a bad release reaching all users.**

I would treat the three requirements as three separate loops and configure each explicitly. For **availability**: minimum capacity of at least three so all zones can be covered, subnets in three Availability Zones, and on EC2 capacity a placement strategy of `spread` on `attribute:ecs.availability-zone` followed by `binpack` on memory, with a dashboard showing tasks per zone that is checked after every fleet change. Capacity comes from an On-Demand base sized to carry floor traffic unaided, with Spot only above that base, because this is a synchronous revenue path. For the **daily peak**: a scheduled action raising the minimum capacity fifteen to thirty minutes before the peak and lowering it afterwards, with target tracking on `ALBRequestCountPerTarget` handling variance above that floor. The target value would come from a load test — the requests per task at which p99 latency starts to rise, times about 0.65 — not from a round number. Scale-out cooldown 60 seconds, scale-in 300. On EC2 the capacity provider would run at 85 per cent target capacity so placement is immediate. For **release safety**: `minimumHealthyPercent: 100` and `maximumPercent: 200` so a deployment never reduces capacity, the circuit breaker enabled with rollback, alarm-based rollback on 5xx rate and p99 latency with a bake period, and CodeDeploy canary shifting with an `AfterAllowTestTraffic` hook running a checkout smoke suite against the green task set before any customer sees it. Above all of that, feature flags in AppConfig so that new checkout behaviour is deployed dark and exposed progressively, which is the control that actually prevents a bad release reaching all users — the deployment mechanisms bound the damage, but the flag prevents the exposure.

**2. You inherit twenty-two ECS services with no placement strategies, scaling on CPU, and default deployment configuration. Prioritise the remediation and justify the order.**

I would order by the product of likelihood and harm, and start with the changes that require no measurement. **First, deployment configuration**, because it is one setting, applies to every service, and there is no scenario where you want its current state: enable the deployment circuit breaker with rollback everywhere, and set `minimumHealthyPercent: 100` with `maximumPercent: 200`. This is an afternoon's work in a shared IaC module and immediately removes the worst failure — a bad release draining healthy capacity — and the most frequent self-inflicted availability dip. **Second, placement**, because an AZ event is the single largest correlated risk and the fix is again configuration rather than measurement: `spread` on availability zone then `binpack` on memory, plus a dashboard showing tasks per zone so the fix is verifiable. I would also raise any service with a minimum capacity below two. **Third, alarm-based rollback** on 5xx rate and p99 latency, since the circuit breaker alone covers only half the failure space; this requires the alarms to exist, which is real work but bounded. **Fourth, scaling signals**, which I put last despite it being the most-discussed item, because it requires per-service measurement: for each service, determine whether it is CPU-bound or I/O-bound, load test to find the degradation point, and move the I/O-bound ones to `ALBRequestCountPerTarget` and the queue consumers to backlog per task with derived targets. I would sequence that service by service rather than as a big-bang change, starting with the ones whose latency graphs already show the symptom. Throughout, I would put every setting into a shared module so that service twenty-three is correct by construction, because otherwise this remediation recurs.

**3. Design the deployment pipeline and orchestration configuration for a platform where six independent supplier teams deploy into the same environment and no supplier may block another.**

The requirement is contractual independence, which is a Conway's law problem before it is a technical one, so the design must make each supplier's deployment genuinely independent while enforcing a common safety floor centrally. I would give each supplier **its own ECS cluster** — free on ECS — with IAM scoped so that a supplier's pipeline can call `UpdateService` only against its own cluster ARN, and `iam:PassRole` restricted to that supplier's execution and task roles. All suppliers share one Application Load Balancer with a listener rule per supplier path, since the alternative multiplies edge cost, but the listener rules are managed centrally in the platform's IaC rather than by suppliers, so one supplier cannot alter another's routing. The **safety floor is enforced centrally** as a mandatory deployment configuration: circuit breaker with rollback, `minimumHealthyPercent: 100`, alarm-based rollback on 5xx and latency for that supplier's target group, and a required health-check contract at a standard path. Suppliers choose their own scaling policies and target values, because those are workload-specific and are exactly the decision a supplier should own. Deployment events go to EventBridge and fan out to each supplier's channel plus a platform channel, so the platform team sees the estate without gating any individual release. What I would explicitly avoid is a shared pipeline or a shared release train, because either would recreate precisely the coordination cost the independence requirement exists to remove — and a platform team that becomes a deployment bottleneck has defeated the architecture regardless of how good the configuration is.

### Troubleshooting Questions

**1. A service's scaling policy is configured correctly but `desiredCount` never rises above 12, while the metric stays well above target. Diagnose.**

A metric persistently above target with a static desired count means something is capping the capacity, and the policy is doing its job. I would check the caps in order of likelihood. First, the **scalable target's maximum capacity** — if it is 12, the policy is being clamped and `describe-scaling-activities` will say so explicitly in its status messages, which is why that call is the first thing to run. Second, a **placement constraint**: `distinctInstance` limits the service to one task per container instance, so a 12-instance cluster caps the service at 12 tasks regardless of what scaling asks for, and nothing reports this as an error — the symptom is `desiredCount` above `runningCount` with placement failures in the service events. Third, **subnet IP exhaustion** in `awsvpc` mode, since every task consumes an address and a small subnet runs out long before compute does. Fourth, on EC2 capacity, **insufficient instances** because managed scaling is disabled or the ASG is at its own maximum. Fifth, a **Fargate account quota** on concurrent tasks. The distinguishing evidence is straightforward: if `desiredCount` itself is stuck at 12, the cap is in the scaling layer — the maximum capacity or the policy; if `desiredCount` is rising above 12 while `runningCount` sits at 12, the cap is in placement, and the service events name which of the placement causes it is. That single comparison halves the search space, which is why the diagnostic order in this chapter starts with desired versus running.

**2. A deployment has been `IN_PROGRESS` for forty minutes with no progress and no rollback. Explain what is happening.**

The rolling update is stalled rather than failed, and understanding why requires knowing that the scheduler is permitted to stop old tasks only once new **healthy** tasks exist. If new tasks never become healthy, none are stopped, the service continues serving on the old revision, and the deployment sits indefinitely — which is actually the safe behaviour, since the alternative would be draining working capacity in favour of broken tasks. The absence of a rollback means the deployment circuit breaker is not enabled, which is the first thing I would fix regardless of the immediate cause. To find the cause I would read `rolloutStateReason` and the service events, then list stopped tasks and read `stoppedReason` and `exitCode`. The usual candidates: the image cannot be pulled, so tasks reach `PENDING` and stop; the container health check fails because `startPeriod` is shorter than the application's cold start; the target group health check fails because of a security group rule, a wrong port, or a path that returns a redirect; the new revision's task size does not fit any remaining capacity; or the application is crashing on start-up because of a missing environment variable or secret. `TargetHealth.Reason` distinguishes the network causes (`Target.Timeout`) from the application causes (`Target.ResponseCodeMismatch`), which is usually the fastest single discriminator. Once identified, I would fix forward or roll back explicitly by updating the service to the previous revision, and then enable the circuit breaker so the next occurrence resolves itself.

**3. After a deployment completes successfully, error rates rise 20 minutes later and nothing rolls back. What went wrong and what would you change?**

Two things went wrong, and they are worth separating. The **detection** failed: either no alarm-based rollback was configured, so nothing was watching behavioural metrics at all, or an alarm existed but its bake period had already elapsed by the time the errors appeared. Twenty minutes is a long tail, and it points at a failure mode that only manifests under conditions that take time to arise — a cache filling, a connection pool exhausting, a scheduled job firing, a memory leak reaching the limit, or simply a code path that only some requests take. The **mechanism** also failed in the sense that the circuit breaker was never going to catch this: the tasks were healthy the whole time. The changes I would make: configure alarm-based rollback on 5xx rate and p99 latency with a bake period long enough to cover realistic manifestation time, accepting that this lengthens deployments; add a memory-utilisation alarm if the pattern suggests a leak, since `OOMKilled` events twenty minutes in are a classic version of this; and, more fundamentally, adopt **feature flags** so that new behaviour is exposed progressively after the deployment is confirmed healthy, which converts a twenty-minute-delayed rollback into an instant flag flip. I would also note the honest limit: no bake period is long enough to catch every delayed regression, which is why the ability to roll back or flag off quickly matters more than the ambition to detect everything before promotion, and why an alarm that pages a human is not a failure of automation but a necessary complement to it.

### Certification-style Questions

**1. A company needs its ECS service on EC2 capacity to remain available during an Availability Zone failure while minimising the number of instances used. Which placement configuration is most appropriate?**

A. `binpack` on memory only
B. `spread` on `attribute:ecs.availability-zone`, then `binpack` on memory
C. `binpack` on memory, then `spread` on `attribute:ecs.availability-zone`
D. `random`

**Answer: B.** Spreading across zones first distributes replicas across the correlated failure domain; bin packing second achieves density within each zone. A optimises only for density and can concentrate every replica in one zone. C reverses the priority, filling instances before considering zones. D expresses no intent at all.

**2. An ECS service consuming from Amazon SQS oscillates between minimum and maximum capacity. Which change most directly addresses the cause?**

A. Increase the maximum capacity
B. Scale on `ApproximateNumberOfMessagesVisible` divided by `RunningTaskCount`
C. Reduce the scale-out cooldown
D. Switch from Fargate to EC2 capacity

**Answer: B.** Target tracking requires a metric that falls as capacity is added; raw queue depth does not, so the controller cannot converge. Backlog per task restores the denominator. A and C make the oscillation worse or leave it unchanged, and D is unrelated to the control loop.

**3. Which deployment configuration ensures that serving capacity never falls below the desired count during a rolling update?**

A. `minimumHealthyPercent: 50`, `maximumPercent: 100`
B. `minimumHealthyPercent: 100`, `maximumPercent: 100`
C. `minimumHealthyPercent: 100`, `maximumPercent: 200`
D. `minimumHealthyPercent: 0`, `maximumPercent: 100`

**Answer: C.** A minimum of 100 prevents healthy capacity dropping below the desired count, and a maximum of 200 provides the room to start new tasks before stopping old ones. B cannot make progress, because no new task may be started and no old task may be stopped. A halves capacity. D stops everything first and is appropriate only for singleton workloads.

**4. A release passes all health checks and deploys successfully, but returns incorrect data to users. Which mechanism would have prevented full exposure?**

A. The ECS deployment circuit breaker
B. A shorter health-check interval
C. CodeDeploy canary traffic shifting with an `AfterAllowTestTraffic` validation hook
D. Increasing `maximumPercent` to 200

**Answer: C.** The validation hook can run business assertions against the green task set before production traffic reaches it, and canary shifting limits exposure while metrics are evaluated. A detects unhealthy tasks only, and these tasks were healthy. B and D affect deployment speed and capacity, not correctness detection.

**5. Which statement about ECS placement is correct?**

A. Placement strategies can prevent a task from being placed
B. Placement constraints filter candidate instances, and strategies sort them
C. Placement strategies apply to AWS Fargate tasks at the instance level
D. `distinctInstance` guarantees tasks are spread across Availability Zones

**Answer: B.** Constraints filter and can make placement impossible; strategies only order the survivors. A is the reverse. C is wrong because Fargate has no container instances — distribution follows the subnets supplied. D is wrong: `distinctInstance` guarantees separate instances, which may all be in the same zone.

**6. A service must scale ahead of a known daily traffic peak that arrives within two minutes. Which approach is most appropriate?**

A. Reduce the target-tracking target value to 10 per cent
B. Use a scheduled scaling action to raise minimum capacity before the peak, with target tracking above it
C. Increase the maximum capacity of the scalable target
D. Switch the scaling metric from requests per target to memory utilisation

**Answer: B.** Reactive scaling has an end-to-end latency of minutes and cannot meet a two-minute step change; scheduled scaling anticipates the known component while target tracking handles the variance. A over-provisions permanently and still cannot react in time. C raises a ceiling that is not the constraint. D changes the signal to one less related to load.
