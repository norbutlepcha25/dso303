# Unit 7: Interview Questions

## 7.1 Monitoring Cloud-Native Applications

### 7.1.1 Infrastructure and Application Monitoring with Amazon CloudWatch

#### Conceptual Questions

!!! question "Why are OrderLatency with dimensions {Service=checkout} and OrderLatency with dimensions {Service=checkout, Env=prod} treated as two different metrics, and what are the consequences?"
    CloudWatch identifies a metric by its namespace, metric name and complete set of dimensions. Each unique combination is a separate time series, stored and billed separately. The consequence is that CloudWatch's standard statistics API does not aggregate across dimension combinations: to query latency for the checkout service regardless of environment, the producer must also publish the `{Service}` combination (another billed metric), or the engineer must use Metrics Insights with `GROUP BY`. It also means that dashboards and alarms must reference exactly the published combination, or they show no data.

!!! question "Explain why percentiles are preferred to averages for latency, and state when CloudWatch cannot compute percentiles."
    Latency distributions are skewed: most requests are fast, and a small fraction are very slow. The average blends the two and hides the slow tail, so a system can have an acceptable average while a meaningful share of users experience multi-second delays. Percentiles such as p99 report the experience of the slowest users directly, and percentile rank reports the fraction of requests meeting a threshold. CloudWatch cannot compute percentiles when the producer publishes only pre-aggregated statistic sets (sample count, sum, minimum, maximum), because the distribution has been discarded, or when values are negative.

!!! question "Contrast PutMetricData, the Embedded Metric Format and the CloudWatch agent as ways of publishing custom metrics."
    `PutMetricData` is a synchronous API call from code: simple, but it adds latency, costs per request, is subject to Regional rate quotas and can fail. EMF writes a structured JSON log line to standard output; CloudWatch extracts metrics during log ingestion, so there is no network call in the request path and high-cardinality context stays searchable in the log event; the cost is log ingestion. The CloudWatch agent runs on a host or as a sidecar, collects guest OS metrics that the hypervisor cannot see, receives StatsD, collectd, Prometheus and OTLP data, aggregates locally and publishes in batches. EMF suits Lambda and containers, the agent suits hosts and nodes, and `PutMetricData` suits batch jobs and scripts.

!!! question "What is metric cardinality and why is it both a technical and a financial concern?"
    Cardinality is the number of distinct time series a metric generates, equal to the product of the distinct values of its dimensions. Technically, very high cardinality makes dashboards unreadable and queries slow, and can hit ingestion quotas. Financially, each distinct time series is billed as a custom metric per month, so a dimension such as customer ID makes cost grow with the customer base. Architects bound dimensions to small sets of values and put identifiers into logs or trace annotations.

!!! question "Why does CloudWatch provide no memory utilisation metric for EC2 instances by default?"
    EC2 metrics are collected by the hypervisor, which observes the instance from outside. It can measure CPU, network and some disk activity, but it cannot see how the guest operating system uses memory or file systems. The CloudWatch agent, running inside the guest, reads operating system counters and publishes metrics such as `mem_used_percent` and `disk_used_percent`.

#### Scenario Questions

!!! question "An online retailer's internal dashboards were green for 40 minutes while customers could not reach the site because a TLS certificate on the CDN had expired. How would you redesign monitoring to detect this within five minutes?"
    Adopt outside-in monitoring. Create CloudWatch Synthetics canaries for the home page, login and checkout journeys running every minute against the public domain, ideally as multilocation canaries so a single probe location cannot cause false alarms; certificate and DNS failures make the canary fail immediately. Add CloudWatch RUM to capture real users' HTTP and JavaScript errors. Alarm on canary `SuccessPercent` (Section 7.3.1 covers alarm design) as a paging symptom alarm. Internal metrics remain for diagnosis. Optionally add a scheduled check of certificate expiry days, and use AWS Certificate Manager managed renewal where possible.

!!! question "A development team adds a customerId dimension to a latency metric in a service with 200,000 active customers and 12 operations. What will happen and what do you recommend?"
    The metric will generate up to 2.4 million time series. At classic custom metric pricing this would cost a very large amount per month, dashboards would be unusable, and `PutMetricData` calls could be throttled. Recommend removing `customerId` as a dimension, keeping bounded dimensions such as `Service`, `Operation` and perhaps `Tier`, and emitting the metric through EMF with `customerId` as a log field so that a specific customer's latency can be investigated in Logs Insights. Alternatively, record `customerId` as a trace annotation so that the traces for a complaint can be found in X-Ray.

!!! question "A company has 35 AWS accounts. During incidents, engineers waste time signing into several accounts to correlate metrics and traces. What do you propose?"
    Designate a monitoring account and configure CloudWatch cross-account observability with Observability Access Manager: a sink in the monitoring account with a sink policy restricted to the organisation, and links from each workload account sharing metrics, log groups, traces and Application Signals data. Engineers use cross-account dashboards, alarms, Logs Insights and the trace map from one place without data being copied. Deploy the links through AWS CloudFormation StackSets or Terraform across the organisation, and grant engineers read-only access in the monitoring account.

#### Architecture Questions

!!! question "Design the monitoring for a microservice on ECS Fargate behind an Application Load Balancer, from infrastructure to user experience."
    User layer: a Synthetics canary for the service's main journey and RUM on the web front end. Edge layer: ALB metrics `RequestCount`, `HTTPCode_Target_5XX_Count`, `TargetResponseTime` p99 and `UnHealthyHostCount`. Application layer: Application Signals through the ADOT SDK and a CloudWatch agent sidecar, providing per-operation latency, faults, errors and availability, an application map and SLOs; business metrics such as orders placed through EMF in the application logs. Platform layer: Container Insights with enhanced observability for task and container CPU, memory, restarts and running versus desired task counts. Dependency layer: vended metrics for DynamoDB, SQS or RDS. All resources in IaC, telemetry through VPC endpoints, and alarms defined as described in Section 7.3.1.

!!! question "Compare Application Signals with building RED dashboards by hand from custom metrics."
    Hand-built RED metrics require each team to add instrumentation to every endpoint, choose names and dimensions, publish through EMF or `PutMetricData`, and build dashboards; results differ across languages and teams, and dependency relationships are not captured. Application Signals uses OpenTelemetry auto-instrumentation to produce standard latency, fault, error and availability metrics per service and operation with consistent naming, discovers dependencies into an application map, links to traces and supports SLOs. It costs per signal and requires the ADOT agent and CloudWatch agent. Hand-built metrics remain necessary for business measurements and for runtimes or languages Application Signals does not support.

!!! question "How would you monitor a scheduled nightly batch job on ECS so that both failures and silent non-execution are detected?"
    The job publishes a heartbeat metric (for example `RecordsProcessed`, published even when the value is zero) and a `JobSucceeded` or `JobFailed` count at the end of each run, plus a duration metric. An alarm treats missing data as breaching for the heartbeat over the expected schedule window, detecting a disabled schedule or a task that never started. Failures are detected by the failure count and by ECS task stopped events through EventBridge. Duration percentiles over weeks reveal gradual degradation. Container Insights shows resource saturation of the job's tasks.

#### Troubleshooting Questions

!!! question "A Lambda function writes EMF log lines, but no metrics appear in CloudWatch. What would you check?"
    First, that the log lines are valid EMF: the `_aws` object with `Timestamp` in milliseconds and a `CloudWatchMetrics` array, and that every dimension and metric named in the directive is present as a top-level field in the same JSON object. Second, that each line is a single JSON document (a logging library that prefixes a timestamp or level to the line breaks parsing, which is why Powertools or raw `print` is used). Third, the namespace and dimension combination being queried in the console matches exactly what was published. Fourth, that the timestamp is not far in the past or future. Finally, that the function actually has permission to write to its log group.

!!! question "An Auto Scaling group scales out too slowly during traffic spikes. The scaling policy uses average CPUUtilization. Diagnose and improve."
    With basic monitoring, EC2 metrics arrive every five minutes, so the policy reacts slowly; average CPU may also be the wrong signal if the workload is I/O-bound or limited by connection pools. Enable detailed monitoring for one-minute metrics, and consider scaling on `ALBRequestCountPerTarget` or a custom high-resolution metric closer to user load. Check the instance warm-up setting and the health check grace period, which delay the effect of new instances. Predictive or scheduled scaling can be added for known daily peaks.

!!! question "Custom metrics from containers are intermittently missing during peak load, and application latency rises at the same time. What is the likely cause?"
    The application is calling `PutMetricData` synchronously per request. At peak, the account exceeds the Regional `PutMetricData` transaction quota, calls are throttled, the SDK retries with backoff inside the request path, latency rises, and some data points are dropped. Switch to EMF or send metrics to a local CloudWatch agent or ADOT collector that batches them, and ensure telemetry failures are caught and ignored rather than retried in the request path.

### 7.1.2 Distributed Tracing with AWS X-Ray

#### Conceptual Questions

!!! question "Explain the difference between a segment, a subsegment and an inferred segment in X-Ray, and map them to OpenTelemetry terms."
    A segment records the work performed by one service for a request, including its host, request, response, timing and outcome; in OpenTelemetry it corresponds to the service's entry (server or consumer) span. A subsegment records a finer-grained piece of work inside a segment, typically a downstream call or a block of code; it corresponds to a child span, often a client span. An inferred segment is a node that X-Ray creates on the trace map for a downstream resource that did not send its own segment, such as DynamoDB or an external API, based on the caller's subsegment; in OpenTelemetry the backend derives the remote node from client span attributes.

!!! question "Why is context propagation essential, and how does it work across an SQS queue?"
    A trace is assembled from spans that share a trace ID and point to their parents. Each service must receive the trace ID, parent ID and sampling decision from its caller and pass them on; otherwise the trace fragments into disconnected pieces. Over HTTP this uses the `X-Amzn-Trace-Id` or W3C `traceparent` headers. Over SQS, the instrumented producer's SDK sets the `AWSTraceHeader` message system attribute; the Lambda event source mapping continues the trace automatically, while a custom consumer must request the attribute in `ReceiveMessage` and extract the context, using span links when one batch span processes messages from several traces.

!!! question "Compare head-based, adaptive and tail-based sampling."
    Head-based sampling decides at the start of a trace and propagates the decision, which is cheap and consistent but blind to the request's eventual outcome, so errors and slow requests are captured only at the sampling rate. Adaptive sampling in X-Ray raises the sampling rate temporarily when anomalies such as 5xx responses are detected and can capture anomalous spans even from unsampled traces, improving evidence during incidents at low baseline cost. Tail-based sampling decides after all spans have arrived in a collector, so it can keep every error and slow trace, but it requires 100 per cent head sampling, buffering memory and trace-ID-aware routing to collectors.

!!! question "When should a value be an annotation and when metadata?"
    Use an annotation for a simple value that you will search or group by, such as an order ID, tenant tier, application version or payment provider, because annotations are indexed and usable in filter expressions and groups (up to 50 per trace). Use metadata for richer, non-searchable diagnostic data such as objects, lists or sanitised request details. Neither may contain secrets or personal data.

!!! question "What changed about the X-Ray SDKs and daemon in 2026, and what does it mean for new projects?"
    The X-Ray SDKs and daemon entered maintenance mode on 25 February 2026, receiving only critical security fixes, and reach end of support on 25 February 2027. The X-Ray service continues. New projects should instrument with OpenTelemetry through ADOT or upstream SDKs, exporting through the CloudWatch agent, an ADOT collector or the X-Ray OTLP endpoint, and existing SDK-based code should be migrated before end of support.

#### Scenario Questions

!!! question "A customer reports that order o-55120 took over ten seconds at about 14:20. How do you find the cause using tracing?"
    If services record `order_id` as an annotation, run the filter expression `annotation.order_id = "o-55120"` for the time window in the trace console or `GetTraceSummaries`. If the trace was not sampled, use Transaction Search (if enabled) to search spans by the order attribute, or find the trace ID in the logs by order ID (Section 7.2) and look it up. Read the timeline to find the longest span or repeated retries, then check the service's logs by trace ID for the error detail. If no trace exists because of sampling, raise the reservoir for the checkout rule or enable adaptive sampling so that future anomalies are captured.

!!! question "After adding an SQS queue between two services, the trace map shows the consumer as a separate, disconnected graph. What is wrong?"
    The trace context is not crossing the queue. Either the producer's SDK call is not instrumented (so `AWSTraceHeader` is not set), or the consumer is a custom worker that does not request `AWSTraceHeader` in `MessageSystemAttributeNames` and does not extract it. Instrument the producer with OpenTelemetry or the Lambda tracer, request and extract the attribute in the consumer, and use span links for batch processing.

!!! question "Tracing costs have tripled, and analysis shows most traces are GET /health requests from the load balancer. What do you change?"
    Create a sampling rule with a higher priority than the default that matches the health check path with `FixedRate` 0 and `ReservoirSize` 0, or exclude health paths in the auto-instrumentation configuration or collector filter. Health checks run every few seconds from every load balancer node and carry no diagnostic value in traces. Review other high-volume, low-value paths and give them low fixed rates.

#### Architecture Questions

!!! question "Design tracing for a system with API Gateway REST APIs, Lambda functions, an ECS service, SQS, EventBridge and Step Functions."
    Enable stage tracing on API Gateway so it records segments and starts traces. Instrument Lambda functions with active tracing plus OpenTelemetry or Powertools for subsegments and annotations. Instrument the ECS service with the ADOT SDK and a CloudWatch agent sidecar, with the X-Ray remote sampler and a composite propagator. Rely on `AWSTraceHeader` for SQS and on EventBridge trace header propagation, instrumenting all producers; enable tracing on Step Functions state machines. Define sampling rules in IaC that exclude health checks and give checkout a reservoir, enable adaptive sampling where supported, and consider Transaction Search for complete span search. Grant write permissions to each execution or task role, route through VPC endpoints, and standardise `service.name` and annotation keys.

!!! question "Compare running the collector as an ECS sidecar, as an EKS DaemonSet and as a central gateway tier."
    A sidecar runs in each task, reachable on localhost, uses the task role and fails independently, which suits Fargate where there is no node to host a daemon; it costs CPU and memory per task. A DaemonSet runs one collector per EKS node, reducing overhead, but must be sized for the busiest node and needs its own IAM role. A gateway tier centralises processing such as tail sampling, redaction and multi-backend export, and simplifies configuration changes, but adds a tier to scale and operate and requires trace-ID-aware load balancing for tail sampling. Many estates combine local collectors with a gateway.

!!! question "How would you migrate a Java service instrumented with the X-Ray SDK to OpenTelemetry without losing trace continuity with other services?"
    Replace the X-Ray SDK with the ADOT Java agent (auto-instrumentation) and replace manual X-Ray subsegments with OpenTelemetry spans and attributes. Configure the X-Ray ID generator (or rely on Transaction Search's W3C support) and a composite propagator that reads and writes both W3C and `X-Amzn-Trace-Id` headers, so services still using the X-Ray SDK continue the same traces. Use the X-Ray remote sampler so existing sampling rules apply. Replace the X-Ray daemon with the CloudWatch agent or an ADOT collector. Migrate service by service, verifying on the trace map that edges remain connected.

#### Troubleshooting Questions

!!! question "A Lambda function has active tracing enabled, but no traces appear. What do you check?"
    Check that the execution role has `xray:PutTraceSegments` and `xray:PutTelemetryRecords`. Check that invocations are occurring and that the time window is correct. Remember that only one request per second plus 5 per cent are sampled, and that an upstream caller may have sent `Sampled=0`. If the function is in a VPC without internet access, the Lambda service still sends its own segment, but instrumentation in code that exports through a collector may need a VPC endpoint. Finally, check that the console is showing the correct Region.

!!! question "Child spans appear to start before their parent in a trace timeline. What causes this?"
    Clock skew between hosts. Each service timestamps its own spans using its local clock, so a host whose clock is ahead or behind produces misaligned bars. On EC2 use the Amazon Time Sync Service, check that containers are not running on hosts with drifted clocks, and interpret small offsets with care. Lambda and Fargate hosts are synchronised by AWS.

!!! question "An ECS task restarts under peak load and the logs show the collector sidecar consuming all task memory. Why, and how do you fix it?"
    The collector's export queue or tail-sampling buffer grew without bound, perhaps because X-Ray export was slow or throttled, or because the decision window multiplied by throughput exceeded the memory reservation. Add the `memory_limiter` processor, bound queue sizes, reduce `num_traces` or the decision window, give the sidecar an explicit memory reservation and limit, and mark it non-essential if the application should survive a collector failure. Consider moving tail sampling to a dedicated gateway tier.

### 7.1.3 Health Checks and Readiness Probes on AWS

#### Conceptual Questions

!!! question "Explain the difference between readiness, liveness and replacement checks, and why their design should differ."
    A readiness check decides whether a component receives new traffic; failing it removes the component from load balancing, which is quick and reversible. A liveness check decides whether a process is restarted; failing it loses in-flight work and incurs a cold start. A replacement check, such as an Auto Scaling health check, terminates and replaces an instance or task, the most disruptive action. Because the cost of a false failure increases from readiness to replacement, liveness and replacement checks should be narrow and conservative, testing only the component itself, while readiness may include local conditions such as initialisation and draining.

!!! question "What does it mean that an Application Load Balancer fails open, and what does it imply for health check design?"
    If all targets in a target group are unhealthy, the ALB routes requests to all of them regardless of health, on the assumption that a universally failing check is more likely wrong than every target being broken. It implies that a health check that fails on a shared dependency protects nothing: when the dependency fails, all targets fail and still receive traffic. Target health checks should therefore detect problems specific to individual targets.

!!! question "How does Route 53 decide that an endpoint is healthy, and why can it not check a private IP address?"
    Health checkers in several AWS Regions probe the endpoint independently at 10- or 30-second intervals, each applying a failure threshold; the endpoint is healthy if more than 18 per cent of checkers report it healthy. HTTP checks require a TCP connection within 4 seconds and a 2xx or 3xx response within 2 seconds, optionally with a string match in the first 5,120 bytes. The checkers run on the public internet, so they cannot reach private addresses; private resources are monitored through CloudWatch alarm-based health checks.

!!! question "Contrast EC2 system status checks, instance status checks and Auto Scaling ELB health checks."
    System status checks detect problems with the AWS host (power, network, hardware) that AWS must fix, typically remedied by stopping and starting or automatic recovery. Instance status checks detect problems inside the guest (failed boot, memory exhaustion, network misconfiguration) that the customer must fix. Neither sees application failures. The Auto Scaling ELB health check type uses the load balancer's view of the application, so an instance whose application stops responding is replaced even though both status checks pass.

!!! question "Why do Lambda functions not have health checks, and how is the health of a serverless API established?"
    Lambda has no long-running instances for the customer to probe; execution environments are created, reused and replaced by the service. Health is established from metrics (errors, throttles, duration percentiles, backlog age), from Synthetics canaries that exercise the API end to end, and, for multi-Region failover, from Route 53 health checks against a `/health` route or from CloudWatch alarm-based health checks.

#### Scenario Questions

!!! question "Newly deployed ECS tasks are repeatedly stopped with the reason that they failed ELB health checks, although the application logs show a normal start-up that takes 50 seconds. What is wrong and how do you fix it?"
    The service's `healthCheckGracePeriodSeconds` is shorter than the start-up time (possibly zero), so the ALB's failed checks during warm-up count and ECS replaces the tasks in a loop. Set the grace period above the measured cold start (for example 90 seconds), set the container health check `startPeriod` similarly, and confirm the health check thresholds and path. The deployment circuit breaker would eventually roll back the deployment, which masks the configuration error rather than fixing it.

!!! question "During every EKS deployment, a small number of requests fail with 502 errors, both when new pods start and when old pods stop. What changes do you make?"
    At start-up, pods become Ready by their readiness probe before the ALB has registered and health checked their IPs, and old pods are terminated too soon: enable pod readiness gates for the namespace so pods are Ready only when healthy in the target group, and use `maxUnavailable: 0`. At termination, endpoint removal and ALB deregistration race with `SIGTERM`: add a `preStop` sleep, handle `SIGTERM` by failing readiness and draining, set the target group deregistration delay above p99 request duration, and set `terminationGracePeriodSeconds` above the sum.

!!! question "A company runs its API in ap-south-1 with a standby in ap-southeast-1 and wants automatic failover when the primary Region cannot serve customers. Design the health checks."
    Use Route 53 failover records with alias targets to each Region's ALB. Evaluate the primary with a calculated health check whose children are an HTTPS endpoint check on a cached `/health/deep` route (critical dependencies such as the database writer), and a CloudWatch alarm-based check on the primary's 5xx error rate or Application Signals availability. Set a failure threshold of 3 at 30-second intervals to avoid flapping and a low TTL on the records. Ensure the standby Region has sufficient capacity and that database promotion is automated or covered by a tested runbook, since DNS failover alone does not make the data layer writable.

#### Architecture Questions

!!! question "Design the health endpoint contract for a platform of 40 microservices on ECS and EKS."
    Every service exposes `/health/live` (process responsive, no dependencies) for ECS container health checks and Kubernetes liveness; `/health/ready` (initialised, not draining, local pools available, target-specific dependencies only) for ALB and NLB target health and Kubernetes readiness; and `/health/deep` (critical dependencies with cached results and short timeouts, degraded flag for optional dependencies) for canaries, dashboards and Route 53. Endpoints return minimal bodies, are unauthenticated but cheap, are excluded from tracing and verbose logs, and are wired automatically by the platform's IaC modules with standard thresholds, grace periods and timeout ordering.

!!! question "Why does static stability matter for health checks, and how would you design for it in a three-AZ ECS service?"
    Health checks remove unhealthy capacity, and the remaining capacity must absorb the load at once, because scaling takes minutes and may itself be impaired during an incident. For a three-AZ service, provision enough tasks that losing one zone leaves at least 100 per cent of peak capacity in the other two (about 150 per cent of peak in total), spread tasks evenly across zones, use target group health thresholds so a degraded zone is drained, and consider zonal shift for gray failures. The cost of the extra capacity is the price of not depending on control-plane actions during a failure.

!!! question "Compare handling a failed shared database with health checks versus with application resilience patterns."
    Health checks cannot fix a shared dependency failure: all targets fail together, the ALB fails open, and if restarts or replacements are triggered, recovery is slowed by cold starts and connection storms. Application patterns handle it better: short timeouts, a circuit breaker that fails fast, fallbacks or degraded responses, and retries with backoff and jitter (Chapter 4.3). Health checks remain responsible for individual target failures, and Route 53 for Regional failure; alarms inform humans about the dependency.

#### Troubleshooting Questions

!!! question "All targets in a new target group remain unhealthy with the reason Target.Timeout. What do you check?"
    That the target security group allows the health check port from the load balancer's security group; that the health check port matches the port the application listens on; that the application binds to `0.0.0.0` rather than `127.0.0.1`; that network ACLs allow the traffic and return path; that the timeout is longer than the endpoint's response time; and, for instance targets, that the instances are running and the application started (check the user data or container logs).

!!! question "Targets flap between healthy and unhealthy every few minutes under peak load. What is happening and how do you stabilise it?"
    The health endpoint slows down under load and exceeds the timeout, or readiness is tied to load in a way without hysteresis, so targets are removed, the load moves to the remaining targets, which then fail, while the removed ones recover and return. Make the endpoint cheap and in-memory, served on a path that does not queue behind application work, increase the timeout and unhealthy threshold modestly, add capacity or scale earlier, and if load shedding by readiness is intended, add hysteresis. Check `TargetResponseTime` and CPU correlation.

!!! question "A Route 53 failover occurred even though the primary Region was serving customers normally. How do you investigate?"
    Examine `get-health-check-status` observations and the health check's history to see which checkers failed and why (connection timeout, status code, string mismatch). Common causes: the security group or WAF blocked some Route 53 checker ranges; the deep endpoint included a non-critical dependency; the string match failed after a response body change; certificate or SNI issues with HTTPS checks; or an alarm-based child check changed state due to insufficient data. Fix the check definition, restrict deep checks to critical dependencies, and consider a calculated check that requires multiple signals before failover.

## 7.2 Centralized Logging

### 7.2.1 Log Aggregation with Amazon CloudWatch Logs

#### Conceptual Questions

!!! question "Why is the log group, rather than the log stream, the unit of configuration in CloudWatch Logs?"
    Streams are created dynamically, one per task, pod, instance or Lambda execution environment, and their number is unbounded. Configuring retention, encryption or filters per stream would be unmanageable and would change with every scaling event. The log group represents a stable logical component (a service in an environment) and applies retention, KMS keys, metric filters, subscription filters, data protection, field indexes and access control to every stream it contains, present and future.

!!! question "Explain why structured logging is a prerequisite for effective centralised logging."
    Centralisation brings together millions of events from many services. Machines, not humans, must filter and aggregate them. Structured JSON gives each fact a named, typed field, so Logs Insights discovers fields automatically, metric filters match on field values, field indexes accelerate lookups, and OpenSearch maps fields to columns. Unstructured prose requires fragile parsing expressions that break when message wording changes. A shared schema with consistent field names further enables queries across services.

!!! question "Contrast a metric filter with a subscription filter."
    A metric filter evaluates events at ingestion and publishes a numeric data point to a CloudWatch metric for each match, so that alarms and dashboards can use it; the original events stay in the log group. A subscription filter delivers a copy of matching events themselves, in near real time, to Kinesis, Firehose, Lambda or a cross-account destination for further processing, storage or reaction. Metric filters answer "how many"; subscription filters move the data.

!!! question "When would you choose the Infrequent Access log class, and what do you give up?"
    For high-volume logs that are kept for occasional investigation, forensics or compliance and that drive no automation, such as verbose access logs or audit trails queried only on request. Ingestion costs roughly half. You give up metric filters, subscription filters, Live Tail, EMF, Container and Lambda Insights ingestion, anomaly detection, field indexes and the `GetLogEvents` and `FilterLogEvents` APIs, and the class cannot be changed later.

!!! question "What is the difference between a correlation ID and a trace ID, and why log both?"
    A trace ID is generated by the tracing system (X-Ray or W3C trace context) and links spans and logs of a sampled trace. A correlation ID is an application-level identifier generated at the system edge and propagated explicitly through headers and message attributes. Logging both links logs to traces when traces exist, while the correlation ID still joins all events of a request when the request was not sampled or crossed a component that does not propagate trace context.

#### Scenario Questions

!!! question "A startup's CloudWatch bill has tripled in one month although traffic is flat. How do you investigate and fix it?"
    Use Cost Explorer filtered to CloudWatch and usage type to confirm that log ingestion (`DataProcessing-Bytes`) is the driver. Examine `IncomingBytes` per log group to find the offender, and compare it with deployment history. Typical causes are DEBUG logging enabled in production, logging full request payloads, a retry loop logging each attempt, or a new vended log source. Fix at the source (log level, sampling, field selection), consider Infrequent Access or direct-to-S3 delivery for passive logs, set retention on groups that have none, and add an anomaly alarm on `IncomingBytes` so the next spike is caught within hours.

!!! question "A bank requires that application and security logs from 60 accounts are retained for seven years and cannot be deleted by workload administrators. Design the logging architecture."
    Use AWS Organizations with a dedicated Log Archive account. Create CloudWatch Logs centralisation rules that copy selected log groups (and, by data source, CloudTrail and VPC Flow Logs) into the archive account, with a backup Region if required. In the archive account, retain logs in CloudWatch for an operational window (for example 90 days) and stream them with an account-level subscription to Firehose delivering to an S3 bucket with versioning, S3 Object Lock in compliance mode for seven years and lifecycle transitions to Glacier storage classes. Encrypt with customer managed KMS keys owned by the archive account. Protect with service control policies denying `logs:DeleteLogGroup`, `logs:PutRetentionPolicy` and bucket policy changes to everyone except a break-glass role, enable deletion protection, and audit with CloudTrail.

!!! question "An ECS service in private subnets fails to start new tasks after a network change. Stopped tasks show a log driver error. What happened?"
    The network change probably removed the route to CloudWatch Logs: either the NAT gateway was removed or the interface VPC endpoint for `logs` was deleted or its security group no longer allows HTTPS from the task security group. The `awslogs` driver cannot create the log stream, so the task fails to start. Restore a Logs VPC endpoint (and the ECR and S3 endpoints for image pulls) with correct security groups, and confirm that the task execution role still has `logs:CreateLogStream` and `logs:PutLogEvents`.

#### Architecture Questions

!!! question "Compare awslogs, FireLens and a Fluent Bit DaemonSet for container logging on AWS."
    `awslogs` is a Docker log driver used by ECS: zero extra containers, CloudWatch Logs only, minimal processing; ideal as the default. FireLens runs Fluent Bit as a sidecar in each ECS task: it can parse, filter and enrich, and send to several destinations (CloudWatch Logs, Firehose, OpenSearch, third parties), at the cost of sidecar resources and configuration management. A Fluent Bit DaemonSet on EKS runs one collector per node, reading all containers' log files and adding Kubernetes metadata; it is more resource-efficient than per-pod sidecars and is installed by the CloudWatch Observability add-on. The choice follows the orchestrator and the need for routing and filtering.

!!! question "Design logging for an event-driven order system built from API Gateway, Lambda, SQS, an ECS worker and EventBridge, so that a support engineer can reconstruct one customer's order in a single query."
    Configure API Gateway JSON access logs including `$context.requestId` and the trace ID, and pass the request ID to Lambda as the correlation ID. Use Powertools in Lambda to inject the correlation ID into every log line, copy it into SQS message attributes and EventBridge event detail, and have the ECS worker and downstream consumers read and log it. Include `orderId` and `tenantId` as fields. Each component logs to its own governed log group. Create field indexes on `correlationId` and `orderId`. A Logs Insights query across the relevant log groups filtering on `orderId` then returns the full sequence of events sorted by timestamp, and the trace ID links to the X-Ray trace.

!!! question "Explain how you would ensure that logging never causes an application outage."
    Write logs to `stdout` or a local buffer and ship asynchronously; never call `PutLogEvents` synchronously in the request path. Use the ECS `awslogs` non-blocking mode with a sized buffer, configure Fluent Bit with bounded memory and filesystem buffering, and give sidecars adequate resources. Handle `SIGTERM` to flush before exit. Keep the logging path independent of critical dependencies (VPC endpoints in each AZ). Monitor for dropped logs and delivery errors rather than making the application wait. Only records with legal significance should use blocking delivery, and then with explicit monitoring of back-pressure.

#### Troubleshooting Questions

!!! question "A metric filter was created for ERROR events but its metric shows no data, although the log group clearly contains errors."
    Check that the pattern matches the actual event shape: JSON selectors are case-sensitive, and runtime wrappers change the shape (for example, Lambda JSON format wraps application output with `timestamp`, `level` and `message`, while `print` output remains plain text that no JSON pattern can match). Check that the errors occurred after the filter was created, because metric filters are not retroactive. Confirm the log group is Standard class, since Infrequent Access does not support metric filters. Use the console's "test pattern" feature against sample events. If the metric exists but shows gaps, set `defaultValue` to 0.

!!! question "Logs from a batch job that replays files from last month never appear in CloudWatch Logs."
    CloudWatch Logs rejects events older than 14 days or older than the log group's retention period, and batches whose events span more than 24 hours. The replayed events are silently dropped or rejected by the shipper. Reprocess the files into S3 and query them with Athena, or use their ingestion time as the timestamp and keep the original time as a field, and split batches by time window.

!!! question "A Lambda subscription destination is invoked, but it fails immediately with a JSON decoding error on every invocation."
    Subscription payloads are gzip-compressed and Base64-encoded under `event["awslogs"]["data"]`. The function must Base64-decode, decompress and then parse JSON before reading `logEvents`. It should also ignore the `CONTROL_MESSAGE` sent when the subscription is created.

!!! question "Developers can see log groups in the console but receive access denied errors when running Logs Insights queries."
    Their policies allow `logs:DescribeLogGroups` but not `logs:StartQuery` and `logs:GetQueryResults` on the relevant log group ARNs, or the log group is encrypted with a customer managed KMS key whose key policy does not allow the service to decrypt on their behalf, or their resource ARNs omit the `:*` suffix required for log stream-level actions. Review the identity policy against the specific log group ARNs and the KMS key policy.

### 7.2.2 Log Analysis with Amazon CloudWatch Logs Insights

#### Conceptual Questions

!!! question "Explain schema on read, and why it makes Logs Insights both flexible and potentially expensive."
    Schema on read means that CloudWatch Logs stores events without a fixed schema and Logs Insights imposes structure only when a query runs, by discovering JSON fields or parsing text. This is flexible: any question can be asked of any historical data without prior preparation, and storage is simple. The cost is that each query must read and interpret the raw data again, so latency and price grow with the bytes scanned and with how often the question is asked. Schema-on-write systems such as OpenSearch pay the interpretation cost once at ingestion and then answer repeated questions cheaply.

!!! question "Why does adding a selective `filter` not reduce the cost of a Logs Insights query, and what does?"
    Without an applicable index, the engine must read every event in the selected log groups and time range to decide whether each one matches, so bytes scanned, the billing measure, are unchanged. The filter reduces the rows produced and the aggregation work, not the scan. Cost falls only when fewer bytes are read: selecting fewer log groups, shortening the time range, or filtering on fields covered by field indexes (with `filter` or `filterIndex` using equality or `IN`) so that non-matching events are skipped.

!!! question "Contrast `filter` and `filterIndex` on an indexed field."
    Both return events whose indexed field matches. `filter` scans every selected log group, using the index where it exists and scanning fully where it does not, so results are complete but unindexed groups are paid for in full. `filterIndex` restricts the query to log groups that have the index and scans only matching events within them, so it is much cheaper across thousands of groups but silently omits events from groups without the index or older than the index coverage. It is the right tool when an organisation-wide index policy guarantees coverage.

!!! question "What do `pattern` and `diff` provide that a hand-written query cannot?"
    A hand-written query finds what the engineer already suspects. `pattern` clusters millions of events into a small number of templates by replacing variable tokens, revealing the dominant messages and their proportions without prior knowledge. `diff` compares those patterns with the previous equal-length period and highlights new, vanished or changed patterns, which is ideal immediately after a deployment. Together they find unknown unknowns.

!!! question "When would you choose OpenSearch SQL over Logs Insights QL in CloudWatch?"
    When the question is relational: joining events from two log groups on a key, using sub-queries, `HAVING` clauses or window functions, or when the users are analysts fluent in SQL. SQL is also useful when the same query must run in OpenSearch Dashboards. QL remains preferable for day-to-day investigation, for `pattern`, `diff`, `anomaly` and `filterIndex`, and for Infrequent Access log groups, which PPL and SQL do not support.

#### Scenario Questions

!!! question "An SRE builds a CloudWatch dashboard with six Logs Insights widgets, each querying the last 24 hours of production log groups that ingest 200 GB per day, auto-refreshing every minute. What will happen, and what should be built instead?"
    Each refresh of each widget scans about 200 GB, costing roughly USD 1. Six widgets refreshing 1,440 times per day cost about USD 8,640 per day. The widgets also consume query concurrency continuously, so during an incident, when refreshes and engineers' queries compete, interactive queries may be queued or rejected. The numbers shown should come from metrics: EMF metrics from the application or metric filters on the log groups, with alarms on them. Logs Insights widgets, if kept, should use short time ranges, narrow groups and manual refresh, and be placed on an investigation dashboard rather than a wall screen.

!!! question "After a Friday release, customers report intermittent failures, but no alarm has fired. How would you use Logs Insights to investigate within 15 minutes?"
    Select the affected service's log groups and a window starting at the release time. Run RED statistics by `bin(1m)` over the access logs to confirm the symptom and its start. Filter to ERROR and WARN events, run `pattern` and then `diff` against the previous equal period to identify new patterns. Group errors by `version` to confirm the new release is responsible. Take one affected correlation ID and run the request-timeline saved query across services to see the failing hop, then open the trace through the trace ID. The evidence supports a rollback through the pipeline, and the missing alarm becomes a post-incident action: add a metric for the new failure mode.

!!! question "A security analyst must list every IAM principal that received more than 20 AccessDenied errors in CloudTrail yesterday and everything else those principals did in the same period. Describe the approach."
    Query the CloudTrail log group (or the CloudTrail data source) for the previous day. A sub-query first selects principals with `errorCode = "AccessDenied"` grouped by `userIdentity.arn` with a count above 20; the outer query then selects all events whose principal is in that set, sorted by time. In SQL this is a `WHERE userIdentity.arn IN (SELECT ... GROUP BY ... HAVING COUNT(*) > 20)` form. Use the default field index on `eventName` where helpful, keep the time range to one day, export the result to the case record because results last only 7 days, and avoid granting the analyst `logs:Unmask` unless the investigation requires it.

#### Architecture Questions

!!! question "Design a query strategy for an organisation with 400 microservices across 30 accounts so that any engineer can reconstruct a request's path in under a minute."
    Standardise a JSON schema with `correlationId`, `traceId`, `service`, `version` and business identifiers through shared logging libraries. Aggregate logs into a central observability account (centralisation rules, or cross-account observability for query-in-place). Apply an account-level field index policy on `correlationId`, `orderId` and `tenantId` for all production log group prefixes, so that coverage is guaranteed and `filterIndex` is safe. Name log groups consistently (`/<platform>/<env>/<service>`) so `SOURCE` prefixes select production exactly. Publish a parameterised "request timeline" saved query in runbooks and IaC. Monitor query concurrency and reserve Logs Insights for investigation by keeping dashboards metric-based.

!!! question "Compare three ways to produce a daily report of failed payments per tenant: a Logs Insights scheduled query, a metric filter, and a nightly export to S3 queried with Athena."
    A scheduled query runs the aggregation daily and delivers rows to S3 or triggers EventBridge; it is simple, flexible and costs one scan per day, suitable when the report needs grouping by tenant and occasional changes. A metric filter counts failures continuously but cannot carry high-cardinality dimensions such as tenant without creating many custom metrics, so it suits a total count and alarms rather than a per-tenant report. Export or Firehose to S3 with Athena suits long histories (months or years), joins with business data and cheap repeated analysis over compressed columnar data, at the cost of a pipeline. For a daily per-tenant report over recent data, the scheduled query is the best balance.

!!! question "Explain how Logs Insights and OpenSearch Service should divide responsibilities in a large logging platform."
    Logs Insights serves ad hoc investigation over all logs already in CloudWatch, with no infrastructure and pay-per-scan pricing; it is the default for engineers during incidents. OpenSearch serves workloads that repeatedly query the same large datasets interactively: long-lived security analytics dashboards, full-text relevance search, correlation rules and detectors, and teams that live in OpenSearch Dashboards. Logs flow once into CloudWatch; only streams that justify indexed storage are routed to OpenSearch, and OpenSearch direct query can query CloudWatch data in place for occasional use. The dividing line is query frequency and latency requirement against the cost of indexing and storing a second copy.

#### Troubleshooting Questions

!!! question "A query that worked yesterday now returns no rows, although the service is clearly running."
    Check the scope: were the correct log groups selected, and did a redeployment change the log group name (for example a new stack suffix)? Check the time range and time zone. Check `recordsScanned`: if it is zero or small, the query looked in the wrong place. If records were scanned but none matched, inspect a raw event: a library upgrade may have changed field names or casing (`correlationID` versus `correlationId`), or switched the Lambda log format from JSON to text. Finally, if the query uses `filterIndex`, confirm that the index policy still covers the log group.

!!! question "An automated Lambda function that runs Logs Insights queries starts failing with `LimitExceededException`."
    The account has reached the concurrent query quota (100 for QL, 15 for PPL and SQL), often because dashboards refresh frequently, several automations run at once, or queries are abandoned without `StopQuery` and keep running. Reduce dashboard auto-refresh, stop queries on timeout, add retries with exponential backoff and jitter, serialise automated queries through a queue (Chapter 6.3), and move always-on views to metrics. Request a quota increase only after removing waste.

!!! question "A PPL query fails against one log group but the equivalent QL query succeeds."
    The log group is probably in the Infrequent Access class, which supports only Logs Insights QL. Alternatively the PPL uses a command or function not supported in CloudWatch's PPL implementation, or a field with special characters is not enclosed in backticks. Use QL for that group or verify the syntax against the CloudWatch PPL reference.

!!! question "Developers can run queries, but values such as email addresses appear as asterisks, and a developer insists on seeing the original values for debugging."
    A data protection policy on the log group masks the identified data. Seeing the original requires `logs:Unmask`, which is deliberately withheld. The correct response is usually to debug with identifiers (order ID, correlation ID) rather than personal data; if unmasking is genuinely needed, a privileged, audited role with `logs:Unmask` can be used temporarily, and the access is recorded in CloudTrail.

### 7.2.3 Log Storage and Analytics with Amazon OpenSearch Service

#### Conceptual Questions

!!! question "Explain how an inverted index makes full-text search fast, and what it costs."
    At ingestion, an analyser splits each `text` field value into terms, and the index records for each term the list of documents containing it. A search for several terms intersects short postings lists rather than scanning every document, so selective queries take milliseconds regardless of total volume, and relevance can be scored from term statistics. The cost is paid at write time: CPU to analyse and index every document, storage for the index structures in addition to the source, and inflexibility, because changing a field's analysis or type requires reindexing.

!!! question "Why do log platforms use time-based indices or data streams instead of a single index?"
    Logs are append-only and retained for a limited period. With time-based backing indices, retention is enforced by deleting whole old indices, which is cheap, instead of deleting individual documents, which is expensive and fragments segments. Rollover keeps shards within the recommended size as volume changes, allows new settings or mappings to apply to the next index, lets old indices move to cheaper tiers, and lets queries skip indices outside the time range.

!!! question "Compare UltraWarm, cold storage and the writable warm tier."
    UltraWarm stores index data in S3 with a cache on dedicated warm nodes; indices are read-only and need no replicas, so cost per GiB is far lower than hot storage while remaining searchable. Cold storage detaches indices from compute entirely and keeps them in S3 at the lowest cost; they must be migrated back to UltraWarm before querying. The writable warm tier of multi-tier storage uses OI2 instances with local NVMe caching and S3, allows writes to warm indices (useful for late-arriving data), but has no cold tier. The choice depends on whether older data must accept writes and how long it must stay retrievable.

!!! question "What is the difference between a managed domain and an OpenSearch Serverless time series collection from an architect's perspective?"
    A domain exposes the cluster: the architect chooses instance families, node counts, storage tiers, shard strategy and lifecycle policies, gaining control, plugins, tuning options and the lowest cost for large steady workloads, at the price of operational responsibility. A Serverless collection hides the cluster: indexing and search capacity scale automatically in OCUs over S3-backed storage, retention is a lifecycle policy, and security is expressed as encryption, network and data access policies. It suits variable workloads and small teams but has minimum OCU charges on the classic architecture, a subset of APIs and fewer tuning options.

!!! question "What is direct query, and when is it preferable to indexing?"
    Direct query lets OpenSearch analyse data where it already lives, in CloudWatch Logs, S3 or Security Lake, through a data source connection, using PPL or SQL, with optional indexed views materialised into a Serverless collection. It avoids a second copy and an ingestion pipeline, and charges for compute only while queries run (plus source-side charges). It is preferable for occasional analysis, for exploring new sources before deciding whether to index them, and for long archives. It is not suited to high-frequency, sub-second dashboards over large volumes.

#### Scenario Questions

!!! question "A logging domain suddenly rejects writes and Fluent Bit buffers are growing. Cluster status is yellow and `FreeStorageSpace` is near zero on two nodes. What happened and what do you do?"
    Disk usage crossed the flood-stage watermark, so OpenSearch applied a write block to indices with shards on those nodes; replicas could not be allocated, turning the cluster yellow. Immediately free space by deleting expired indices or moving older indices to UltraWarm, or add storage or nodes through a configuration change; then remove the index write block if it does not clear automatically. Upstream buffers will drain once writes resume. Afterwards, fix the cause: attach or correct ISM policies so retention is automatic, alarm on free storage well before the watermark, keep headroom of about 25 per cent, and review shard balance, since uneven shard sizes can fill some nodes first.

!!! question "A security team wants 12 months of searchable CloudTrail and VPC Flow Logs for 80 accounts, with interactive investigations mostly over the last 30 days. Propose a design."
    Centralise the logs into a Log Archive account with CloudWatch Logs centralisation and an S3 archive of record (7.2.1). Stream them through a cross-account subscription to Kinesis and an OpenSearch Ingestion pipeline that normalises fields and enriches with account ownership, into a managed domain in a security tooling account. Keep 30 days hot on OpenSearch Optimized instances across three AZs, migrate indices to UltraWarm up to 12 months with ISM (or use writable warm if late data is expected), then delete from OpenSearch while the S3 archive keeps the long-term copy, reachable with direct query. Enable Security Analytics detectors, FGAC with roles per analyst group, VPC access, KMS encryption and audit logs. Buy Reserved Instances for the steady hot tier.

!!! question "A startup indexes all application logs into OpenSearch Serverless for a small internal tool used a few times a week, and the bill is several hundred dollars per month although data volume is tiny. Why, and what would you recommend?"
    Classic time series collections have minimum OCU charges regardless of usage; with standby replicas the floor is roughly 2 OCUs running continuously, several hundred dollars per month at about USD 0.24 per OCU hour. For a tool used a few times a week over small data, Logs Insights (pay per GB scanned) or direct query would cost a few dollars. If OpenSearch is required, disable standby replicas for a non-production collection or share the collection with other workloads using the same encryption key, and revisit next-generation Serverless if its collection types come to support the workload.

#### Architecture Questions

!!! question "Design the ingestion path from 200 ECS and EKS services into OpenSearch so that no logs are lost during a cluster outage of up to one hour."
    Collect with FireLens on ECS and Fluent Bit DaemonSets on EKS, with filesystem buffering and unlimited retries. Send to an OpenSearch Ingestion pipeline over SigV4-authenticated HTTP with persistent buffering enabled, which retains data across AZs for up to 72 hours and applies back-pressure with 408 and 429 responses rather than dropping data. Configure the pipeline's sink retries and an S3 dead-letter queue for documents the cluster rejects. Optionally fan out a raw copy to S3 (or keep CloudWatch Logs as the landing zone) so any gap can be backfilled. Size the pipeline's maximum OCUs to drain the backlog after recovery, and alarm on buffer usage and DLQ writes.

!!! question "Compare four ways to analyse ALB access logs delivered to S3: Athena, OpenSearch Ingestion into a domain, direct query from OpenSearch, and loading into CloudWatch Logs for Logs Insights."
    Athena queries the objects in place with SQL, costs per TB scanned, suits periodic reports and long histories, and needs partitioning and preferably columnar formats for efficiency. OpenSearch Ingestion with an S3 source (using SQS notifications) indexes each new object into a domain, enabling fast dashboards and full-text search at the cost of instance and pipeline charges; it suits operational dashboards used continuously. Direct query from OpenSearch analyses the S3 data through the Glue Data Catalog with PPL or SQL, with optional indexed views for specific dashboards; it suits occasional analysis with OpenSearch tools. Loading into CloudWatch Logs adds ingestion cost for data that is already durably stored and is rarely justified. The choice follows frequency and latency needs.

!!! question "How would you provide a multi-tenant SaaS product with a customer-facing log viewer built on OpenSearch while guaranteeing tenant isolation?"
    Store all tenants in shared data streams with a mandatory `tenantId` keyword field, avoiding per-tenant indices that would explode shard counts. Serve the viewer through a backend that authenticates the customer and calls OpenSearch with a role whose document-level security restricts every query to that tenant (for example through a role per tenant or attribute-based substitution), and field-level security that hides internal fields. Never trust a tenant filter supplied by the browser. Enforce retention per tenant tier with ISM or separate streams for tiers, audit access, and test isolation with automated negative tests as part of the pipeline.

#### Troubleshooting Questions

!!! question "Documents from a new service never appear in OpenSearch, but Firehose shows successful deliveries."
    Firehose reports delivery of batches; individual documents may still be rejected, typically with mapping conflicts (a field sent as a string where the index maps a number, or an object where a keyword is expected). Check the Firehose S3 backup prefix for failed documents and their error messages, and the domain's error logs. Fix the producer or the index template, and replay the failed documents from S3. Also confirm that the index pattern in Dashboards covers the index name Firehose writes to.

!!! question "Dashboards become very slow every morning and `ThreadpoolSearchRejected` increases, while indexing is normal."
    Many users open dashboards that aggregate over long ranges of raw documents at the same time, exceeding search capacity. Check slow logs and Query Insights for the heaviest queries. Remedies include rollups or transforms for long-range panels, narrower default time ranges, filter context, dedicated coordinator nodes, additional replicas or data nodes, and moving rarely viewed long-range analysis to warm indices or direct query.

!!! question "Cluster health is yellow on a newly created single-node domain."
    Replica shards cannot be allocated on the same node as their primaries, so any index with `number_of_replicas` of 1 or more leaves replicas unassigned on a one-node cluster. Set replicas to 0 for development indices, or add nodes (preferably across AZs) for anything that needs redundancy. On multi-node domains, yellow status usually means a node was lost or disk watermarks prevent allocation; check `_cluster/allocation/explain`.

!!! question "After enabling fine-grained access control, a Lambda function that previously indexed documents receives 403 errors."
    With FGAC, IAM authorisation alone is no longer sufficient: the Lambda execution role must also be mapped to an OpenSearch role (for example a custom role with `create_doc` and `create_index` permissions on `logs-*`, or the built-in writer roles) through a role mapping on its IAM ARN as a backend role. Also confirm the domain access policy still allows the role and that requests are signed with SigV4 for the `es` service.

## 7.3 Observability and Alerting

### 7.3.1 Creating CloudWatch Dashboards and Alarms

#### Conceptual Questions

!!! question "Explain the difference between a symptom-based and a cause-based alarm, and why paging alarms should almost always be symptom-based."
    A symptom-based alarm detects something users or callers experience, such as a high error rate on a critical API, high p99 latency, an old message in a queue or a failing canary. A cause-based alarm detects an internal condition that might lead to a symptom, such as high CPU or a restarted task. Symptoms are few, directly correlated with harm and independent of the particular failure mechanism, so they catch unknown failure modes as well as known ones. Causes are numerous, often self-healing (auto scaling, task replacement) and only loosely correlated with harm, so paging on them produces alert fatigue. Cause alarms are appropriate when they predict unavoidable harm that needs human action, such as storage exhaustion or certificate expiry, and even then usually as tickets.

!!! question "Define SLI, SLO, SLA and error budget, and explain why an SLO should be stricter than the SLA but less than 100 per cent."
    An SLI is a measured ratio of good events to valid events, such as the proportion of requests that succeed within 300 ms. An SLO is a target for that SLI over an interval, such as 99.9 per cent over 28 days. An SLA is a contractual commitment with penalties. The error budget is the permitted unreliability, 100 per cent minus the SLO, applied to the interval. The SLO is stricter than the SLA so that internal alarms and policies act before contractual penalties apply. It is below 100 per cent because perfect reliability is unattainable and each additional nine sharply increases cost while providing no perceptible benefit; the budget also gives teams permission to deploy and experiment.

!!! question "What does an alarm with period 60 seconds, evaluation periods 5 and datapoints to alarm 3 mean, and why is this preferable to 1 of 1?"
    The alarm considers the last five one-minute datapoints and enters `ALARM` if any three of them breach the threshold. It returns to `OK` when fewer than three of the last five breach. Compared with 1 of 1, it ignores single transient spikes, reducing flapping and false pages, while still detecting sustained problems within about three to five minutes. Requiring all five to breach would be slower and could miss intermittent but serious problems.

!!! question "Compare the four missing-data treatments and give a metric for which each is correct."
    `missing` counts absent periods as neither good nor bad and moves the alarm to `INSUFFICIENT_DATA` when all are absent; correct when you want to know that data has stopped and act on `INSUFFICIENT_DATA`. `notBreaching` counts absent periods as good; correct for Lambda `Errors`, which is only emitted when there are invocations. `breaching` counts absent periods as bad; correct for heartbeat metrics and canary success, where absence means failure. `ignore` keeps the current state; occasionally used for very sparse metrics, but it risks never detecting an outage that stops data.

!!! question "What is burn rate, and why does the multi-window, multi-burn-rate technique use a long and a short window together?"
    Burn rate is the observed error rate over a look-back window divided by the budgeted error rate (1 minus the SLO). A burn rate of 1 exhausts the budget exactly at the end of the interval; higher values exhaust it sooner. The long window (for example 1 hour) ensures that the problem is significant enough to consume a meaningful share of the budget, which avoids paging on brief blips. The short window (for example 5 minutes) ensures that the problem is still happening, so the alarm resets quickly after recovery rather than staying in `ALARM` for an hour. Combining them with `AND` in a composite alarm gives both precision and fast reset.

#### Scenario Questions

!!! question "An online store has alarms on CPU, memory, disk and task restarts for 40 services. On-call engineers receive about 60 pages per week and have started ignoring them. Last Friday checkout failed for 40 minutes because a payment provider returned errors, but no alarm fired. Redesign the alerting."
    Define SLOs for the critical journeys (browse, add to cart, checkout, payment) using Application Signals availability and latency or ALB metrics. Create multi-window burn-rate alarms per SLO and combine them into page-severity and ticket-severity composite alarms routed to separate SNS topics. Add a Synthetics canary for the checkout journey and anomaly detection on orders per minute to catch silent drops. Convert CPU, memory, disk and restart alarms to dashboard widgets or ticket-level alarms, except those predicting unavoidable harm. Add owners and runbooks to every paging alarm and hold a monthly review. The payment failure would have produced a fast burn on checkout availability and a failing canary, and paged within minutes, while weekly pages would fall to a handful of actionable ones.

!!! question "A nightly batch job on ECS Fargate normally runs at 02:00 and publishes a `RowsProcessed` metric. Last month it stopped running for five days after a scheduler change and nobody noticed. How do you detect this in future?"
    Publish a heartbeat metric such as `JobSucceeded = 1` at the end of each successful run (or rely on `RowsProcessed`). Create an alarm with `TreatMissingData = breaching`, a period slightly longer than the schedule allows (for example a daily evaluation covering the expected run window, using multi-day or 24-hour evaluation), and a threshold of less than 1. Absence then drives the alarm to `ALARM`. Also alarm on `RowsProcessed` falling below an expected minimum, and route to a ticket topic, or to a page if downstream reporting depends on the job by morning.

!!! question "During a database failover, 15 downstream services all page their teams simultaneously, although only the data platform team can act. How can CloudWatch prevent this?"
    Represent the failover with an alarm owned by the data platform team, for example on an RDS event-driven custom metric or on Aurora failover events converted into a metric. Give each downstream service a composite customer-impact alarm whose children have no actions, and configure the failover alarm as `ActionsSuppressor` with a wait period long enough for the failover alarm to fire first and an extension period long enough for connections to recover. Downstream composites still change state and appear on dashboards, but only the data platform team is paged. If downstream impact persists beyond the extension period, downstream teams are then notified.

#### Architecture Questions

!!! question "Design the monitoring architecture for an organisation with 30 AWS accounts running ECS, EKS and Lambda workloads, with a central operations team and autonomous service teams."
    Create a monitoring account and link all workload accounts with CloudWatch cross-account observability so that metrics, logs and traces are visible centrally. Service teams own per-service alarms, composite alarms and SLOs, deployed from their own pipelines using a shared CDK construct or Terraform module that enforces standard RED alarms, burn-rate alarms, DLQ alarms, runbook links and tags. The central team owns Level 0 and Level 1 dashboards in the monitoring account, fleet-level multi time series query alarms selected by tags (for example any production Lambda function with sustained errors), and the organisation-wide SNS topics or EventBridge routing to the paging tool. Alarm state-change events from all accounts are forwarded to a central event bus for reporting and automation. Silencing permissions are restricted and audited through CloudTrail, and a weekly hygiene report lists disabled, orphaned and runbook-less alarms.

!!! question "Explain how CloudWatch alarms participate in safe deployments in a CI/CD pipeline for Lambda and ECS."
    CodeDeploy deployment groups reference CloudWatch alarms. For Lambda, traffic shifts gradually between alias versions (canary or linear); alarms on errors and latency filtered by the new version (for example the `ExecutedVersion` dimension) are evaluated during the bake time, and if any enters `ALARM` CodeDeploy shifts all traffic back. For ECS blue/green deployments, alarms on the green target group's 5xx rate and latency play the same role, and the ECS deployment circuit breaker can also roll back on failed tasks. Alarm quality therefore becomes a deployment-safety property: alarms must be fast, specific to the new version and free of noise, otherwise good releases are rolled back or bad ones are promoted.

!!! question "When would you choose a multi time series Metrics Insights alarm, a log query alarm, and a static metric alarm for the same platform?"
    Use a static metric alarm for a small number of critical, individually tuned resources, such as the checkout service's latency or one payment queue's backlog age, where thresholds differ per resource and detection must be immediate. Use a multi time series Metrics Insights alarm for fleet coverage with a uniform rule, such as any production Lambda function with more than 10 errors per minute, because it follows new resources, emits per-contributor events and avoids hundreds of alarms. Use a log query alarm when the condition exists only in logs and needs rich parsing or grouping, such as a spike in a specific exception type per tenant, accepting schedule-bound latency and per-run scan cost; for high-volume, simple patterns a metric filter remains cheaper and faster.

#### Troubleshooting Questions

!!! question "A newly created alarm has been in INSUFFICIENT_DATA for two hours although the service is receiving traffic. What do you check?"
    Check that the namespace, metric name and every dimension name and value match the metric exactly, including case and the full ALB target group or load balancer identifiers; a single mismatch creates an alarm on a non-existent metric. Check that the statistic is valid for the metric and that the period is not shorter than the metric's publishing interval. Check the Region. Confirm in the metrics console that datapoints exist for that exact dimension combination. For metric math alarms, confirm each referenced metric returns data and that the expression does not divide by zero or return no data at low traffic.

!!! question "An error-rate alarm flaps between OK and ALARM every few minutes each night between 01:00 and 05:00. Why, and how do you fix it?"
    At night traffic is very low, so a ratio of errors to requests is dominated by single failures: one error in five requests is a 20 per cent error rate. Fix it with a minimum-traffic guard in the metric math expression (for example `IF(requests > 50, ...)`), a longer period, M of N evaluation, or a composite requiring both a ratio breach and an absolute error count above a floor. For latency percentiles, set `EvaluateLowSampleCountPercentile` to `ignore`. SLO burn-rate alarms with request-based SLIs are also naturally more stable at low volume.

!!! question "A composite alarm entered ALARM during an incident but no notification was sent. The SNS topic works when tested manually. What could explain this?"
    The composite may have an actions suppressor that was in `ALARM`, or within its wait or extension period, so actions were suppressed. An alarm mute rule may have been active for that alarm. Actions may have been disabled with `DisableAlarmActions`. The composite's actions may only be configured for `OK` and not `ALARM`. If the topic uses a customer managed KMS key, the key policy may not allow CloudWatch to use it, causing publishes from the alarm to fail even though a manual publish by an administrator succeeds. Check the alarm history, which records suppression and action results, the mute rules, and SNS `NumberOfNotificationsFailed`.

### 7.3.2 Automated Incident Response with AWS Lambda

#### Conceptual Questions

!!! question "Distinguish mitigation from resolution and explain why automation targets mitigation."
    Mitigation stops or reduces user impact, for example by rolling back a release, shifting traffic away from a failing zone or adding capacity. Resolution fixes the underlying cause, for example correcting the defect in code. Mitigation actions are generic and repeatable across many incidents, so they can be tested and automated safely; resolutions are specific to each defect, require understanding and go through the normal CI/CD process. Automating mitigation therefore delivers large reductions in customer impact with manageable risk, while resolution remains a human engineering task.

!!! question "Why must Lambda responders be idempotent, and what is a good idempotency key for an alarm-triggered responder?"
    CloudWatch alarm actions, EventBridge and SNS deliver at least once, and Lambda retries failed asynchronous invocations, so the same alarm transition can reach the responder more than once. Without idempotency the responder could roll back twice, skipping a good version, or isolate a resource repeatedly. A good key identifies one alarm transition: the alarm name combined with the state-change timestamp. The alarm name alone would suppress legitimate future incidents on the same alarm. The key should be recorded with a conditional write before the action so that concurrent duplicates cannot both proceed.

!!! question "Compare Lambda, Systems Manager Automation and Step Functions as executors of automated responses."
    Lambda runs custom code for up to 15 minutes and is best for small, fast decisions and application-aware actions such as enrichment or alias rollback. SSM Automation runs typed runbook steps, offers hundreds of AWS-provided runbooks, native approvals, rate control over fleets and multi-account execution, and is best for standard infrastructure procedures. Step Functions orchestrates multi-step workflows with waits, retries, compensation and callback-based approvals for up to a year, and is best when a response involves several steps and decisions. Mature designs combine them: Step Functions orchestrates, Lambda decides, SSM Automation performs procedures.

!!! question "What is a remediation loop? Give two examples and their prevention."
    A remediation loop is a cycle in which the automated action re-creates the triggering condition or conflicts with another control system. Example one: a latency alarm triggers task restarts, restarts reduce capacity, latency rises and more restarts follow; prevention is never restarting on capacity symptoms, plus cool-downs and an action budget with escalation. Example two: a responder sets an ECS service's desired count while target tracking scaling resets it, and the two oscillate; prevention is changing the scaling policy's minimum capacity rather than the desired count. Event loops, where a responder's change emits an event matching its own rule, are prevented by excluding the responder's role in the event pattern.

!!! question "What do CloudWatch investigations provide, and what are their limits?"
    CloudWatch investigations use generative AI to correlate metrics, logs, traces, Application Signals data, deployment events, Health events and CloudTrail changes, presenting observations, a topology of affected resources and root-cause hypotheses that engineers accept or discard. They can suggest and run SSM Automation runbooks and generate incident reports, and can be started automatically by an alarm action. Their limits are quotas (for example two concurrent investigations and a monthly cap on AI-analysed investigations per account), dependence on the quality and consistency of telemetry, and the probabilistic nature of hypotheses, which must be validated by engineers before action.

#### Scenario Questions

!!! question "A team's responder restarts ECS tasks whenever p99 latency exceeds 2 seconds. During a database slowdown, the orders service went from degraded to completely unavailable. Explain what happened and redesign the response."
    The latency was caused by the slow database, not by the tasks. Each restart removed capacity and forced new tasks to open new database connections, increasing load on the already slow database and reducing the healthy task count until the service failed entirely: a restart storm. Redesign: remove restarts as a response to latency. Page on the latency SLO burn rate with enrichment showing database metrics from Database Insights; add a composite alarm with the database alarm as an actions suppressor so the data team is paged for the shared cause; if automation is wanted, make it load-shedding (lower API Gateway throttles for non-critical routes) or read-replica failover with approval, with cool-downs and a circuit breaker on the responder. Restart only on specific, task-local failure signals such as health check failures, which ECS already handles.

!!! question "Security wants every GuardDuty finding of type 'instance communicating with a known malicious IP' to isolate the instance automatically. The instances sit behind an ALB serving customers. Design the response."
    Route the finding by severity through EventBridge to a Step Functions workflow. First capture evidence: snapshot volumes, record instance metadata, network interfaces and recent flow logs. Then check tags: for non-production or tagged-disposable instances, isolate immediately by replacing security groups with a quarantine group, deregistering from the target group and detaching the instance from the Auto Scaling group so that a replacement launches. For production instances, post the evidence to the security channel with an approval button and a short timeout; because Auto Scaling replaces capacity, isolation of a single instance usually has low customer impact, so the safe default after timeout can be to isolate. Notify security, open a case, and alarm on workflow failures. Exclude the workflow's own changes from triggering further rules.

!!! question "An automated rollback succeeded, but twenty minutes later the same defective version was deployed again and the incident recurred. Why, and how do you fix the design?"
    The rollback changed the running version but not the source of truth: the pipeline still considered the defective commit the latest and redeployed it, either automatically on another trigger or through a retry. The responder must also stop the pipeline, for example by disabling the inbound transition to the production stage with a recorded reason, or by marking the artifact as rejected, and notify the owning team that redeployment requires review. The post-incident review should add a test that would have caught the defect.

#### Architecture Questions

!!! question "Design a multi-account automated response architecture for 40 workload accounts with a central platform team."
    Workload accounts keep their alarms and forward page-severity alarm state changes and security findings from the default bus to a central operations bus in an automation account using rules deployed by StackSets. In the automation account, rules route events to Lambda responders, Step Functions workflows and SSM Automation runbooks. Responders assume narrowly scoped remediation roles in workload accounts, which trust only specific responder role ARNs and include `aws:PrincipalOrgID` conditions. State (idempotency, cool-downs, action budgets) lives in DynamoDB, kill switches in Parameter Store or AppConfig. All actions publish to SNS topics consumed by Amazon Q Developer in chat applications and a partner paging tool via API destinations, and create or update OpsItems. The bus archives all events for replay-based testing, CloudTrail organisation trails audit every action, and responders are deployed through a pipeline with tests and a dry-run stage.

!!! question "Where would you place each of the following on the automation maturity scale, and why: EC2 status check recovery, Lambda canary rollback, Aurora cross-Region failover, revoking an IAM user's access keys after a GuardDuty credential exfiltration finding?"
    EC2 status check recovery is level 5 or 4: it is a built-in alarm action, well understood, reversible and low risk. Lambda canary rollback is level 4: CodeDeploy performs it automatically on alarm, it is reversible and limited to one function. Aurora cross-Region failover is level 3: well understood but high blast radius, with data loss implications depending on replication lag, and it requires human judgement about whether the Region is truly impaired, so it should be prepared automatically and approved by a human. Revoking a compromised user's keys is level 4 for human users, because the harm of an attacker using the keys outweighs the inconvenience; for keys used by production workloads it becomes level 3 with a short approval timeout, because revocation could cause an outage.

!!! question "Explain how Part 7.3.1 and Part 7.3.2 depend on each other in an alarm-based rollback design."
    The rollback responder is only as good as the alarm that triggers it. If the alarm is noisy, good deployments are rolled back; if it is slow, bad deployments harm users for longer; if it is not specific to the new version, failures in old versions trigger pointless rollbacks. The alarm must therefore be symptom-based, version-specific (alias `Resource` or `ExecutedVersion` dimension, green target group), use M of N evaluation to avoid transient triggers and treat missing data correctly. Conversely, the existence of automated response raises the value of alarm quality work, and composite alarms from Part 7.3.1 can aggregate signals so that responders receive one well-formed event instead of a storm.

#### Troubleshooting Questions

!!! question "An alarm enters ALARM and its SNS notification arrives, but the Lambda responder listed as an alarm action never runs. What do you check?"
    Check the alarm history for the action result, which usually states the failure. Confirm that the function's resource-based policy allows `lambda.alarms.cloudwatch.amazonaws.com` to invoke it and that any `aws:SourceArn` condition matches this alarm's ARN exactly. Confirm the function is in the same account and Region as the alarm. Check that the function exists at the ARN listed, including any version or alias qualifier. Check Lambda `Throttles` and reserved concurrency: a reserved concurrency of 0 (perhaps set as a kill switch) rejects invocations. Finally check the asynchronous invocation configuration: events may have expired due to a very short maximum event age or been sent to the on-failure destination.

!!! question "A responder works when tested with SetAlarmState but crashes on real alarms. Why might that be?"
    Real and test transitions produce the same event structure, so differences usually lie in content. Real alarms may be metric math or composite alarms, whose configuration contains expressions rather than a single metric with dimensions, so code that assumes `metricStat.metric.dimensions` fails. The responder may be receiving events through a different path in production (EventBridge or SNS instead of the direct action) with different formats. Real incidents may also occur under load, when API calls made by the responder are throttled or dependencies are degraded. Normalise event formats, handle metric math and composite alarms explicitly, add retries with backoff for AWS API calls, and test with recorded real events.

!!! question "After an incident, the team finds that the responder performed 27 rollbacks in one hour across different services. Diagnose and prevent."
    A shared cause, such as a failing dependency, triggered alarms on many services, and the responder treated each as a bad deployment. Because rollbacks do not fix a shared dependency failure, alarms stayed in or re-entered `ALARM`, and rollbacks continued, possibly rolling back healthy releases and disrupting teams. Prevention: roll back only when the service's deployment is recent; add a global action budget and circuit breaker so that more than a small number of automated actions per window stops automation and pages humans; route shared-dependency alarms as actions suppressors on composite alarms so downstream services do not trigger responders; and correlate with AWS Health events and dependency alarms before acting.

### 7.3.3 Performance Optimization Using AWS Tools

#### Conceptual Questions

!!! question "Explain Little's Law and use it to explain why a slow database can exhaust Lambda concurrency and database connections without any increase in traffic."
    Little's Law states that the average number of requests in a system equals the arrival rate multiplied by the average time in the system. If an API receives 300 requests per second and each Lambda invocation takes 200 ms, average concurrency is 60. If the database slows so that invocations take 2 seconds, concurrency rises to 600 with the same traffic, each holding a database connection. Lambda may reach its concurrency limit and throttle, and the database may reach its connection limit, which slows it further. The remedy is to fix the database bottleneck, bound concurrency and connections (reserved concurrency, RDS Proxy), and set timeouts so that slow calls fail fast rather than accumulate.

!!! question "What does DB load measured in average active sessions tell you, and why must it be compared with the number of vCPUs?"
    DB load is the average number of sessions that are active, either running on CPU or waiting for a resource such as I/O, locks or commits. If DB load is below the vCPU count, the database is generally not saturated. If it exceeds the vCPU count, sessions are queuing. Whether adding CPU helps depends on the composition: if most of the load is CPU, the database is CPU-saturated and query optimisation or a larger instance helps; if most is waits such as locks or I/O, more CPU will not help and the queries, indexes, transactions or storage must change.

!!! question "Why can increasing a Lambda function's memory reduce its cost?"
    Lambda allocates CPU in proportion to memory and charges for memory multiplied by duration. For CPU-bound code, doubling memory roughly doubles CPU and halves duration, keeping cost roughly constant while improving latency; if duration falls by more than half (for example because the function also benefits from more network bandwidth or reaches a multithreaded sweet spot), cost falls. For I/O-bound code duration barely changes, so extra memory only increases cost. Power Tuning measures which case applies.

!!! question "Describe the difference between observation, recommendation and experimentation tools, with one AWS example of each and when you would use it."
    Observation tools show how the running system behaves, for example Database Insights for database load; use them to find a bottleneck in production. Recommendation tools analyse history and propose changes, for example Compute Optimizer for rightsizing; use them to find fleet-wide waste and candidates for change. Experimentation tools test behaviour under controlled conditions, for example load testing with Distributed Load Testing on AWS; use them to verify that a change improves performance and to learn how the system behaves beyond current traffic.

!!! question "Why should rightsizing happen before purchasing Savings Plans or Reserved Instances?"
    Commitments discount a level of usage for one or three years. If that usage includes over-provisioned or idle resources, the organisation commits to paying for waste for the whole term, and later rightsizing produces unused commitment rather than savings. Rightsizing and modernising first establishes a lean, stable baseline; commitments then cover that baseline and leave variable demand to on-demand or Spot capacity.

#### Scenario Questions

!!! question "A course registration API on ECS Fargate and Aurora PostgreSQL has p99 latency of 3 seconds during registration week. The team proposes doubling the number of tasks. How do you decide whether that will help?"
    Start with Application Signals or traces for the registration operation to see where time is spent. If traces show most time in database calls, open Database Insights for the period: compare DB load with vCPUs and identify the dominant waits and top SQL. If the load is dominated by lock waits on a seat-count row or by a sequential scan on an unindexed table, doubling tasks would increase contention and worsen latency; the fix is an index, a query rewrite or a design that avoids the hot row. If traces show time in the service code with CPU throttling in Container Insights, more or larger tasks may help. Validate the chosen change with a load test replicating registration traffic before the next registration period.

!!! question "Compute Optimizer recommends downsizing 40 per cent of a company's EC2 instances. The operations manager wants to apply all recommendations immediately. What do you advise?"
    Treat the recommendations as hypotheses. Check that the CloudWatch agent publishes memory metrics, otherwise memory-bound instances may be under-sized. Exclude instances that deliberately carry headroom for failover or seasonal peaks outside the look-back period, and consider 93-day look-back for workloads with quarterly cycles. Prioritise options with very low or low performance risk and significant savings, and implement changes through IaC in waves, starting with non-production and stateless tiers, watching SLO dashboards and alarms after each wave. Only after the new baseline stabilises should the organisation review Savings Plans coverage.

!!! question "An e-learning platform's users in one region report slow page loads, but server-side latency metrics look normal. How do you investigate?"
    Server-side metrics measure only the time inside AWS. Use CloudWatch RUM to segment page load and Core Web Vitals by country, device and browser, confirming which users are affected and whether the delay is in network, resource loading or rendering. Use Internet Monitor to see whether specific city-networks or ISPs show degraded performance to the application's Region. If the network path dominates, introduce CloudFront for static and cacheable content and consider edge acceleration; if rendering dominates, reduce page weight and JavaScript. Verify with the same RUM segments afterwards.

#### Architecture Questions

!!! question "Design a continuous performance engineering capability for a platform of 30 microservices on ECS, EKS and Lambda."
    Define SLOs and latency budgets per critical journey. Instrument services with Application Signals and OpenTelemetry traces, enable Container Insights and Lambda Insights for critical services, and Database Insights Advanced for production databases. Add a pipeline stage that deploys to a production-like staging account built with IaC, runs a k6 or Distributed Load Testing scenario per service with SLO-based thresholds and baseline comparison, and runs Power Tuning for changed Lambda functions. Enable Compute Optimizer organisation-wide with Graviton preferences and route low-risk recommendations to team backlogs by tag; use Trusted Advisor organisational view for broad checks. Track latency percentiles, cost per request and observability spend per team on dashboards, and hold a monthly performance review that feeds findings into design changes.

!!! question "How would you govern the cost of observability for an organisation whose CloudWatch bill has tripled in a year, without weakening incident response?"
    Attribute spend by tagging log groups, alarms and canaries and using Cost Explorer by CloudWatch usage type and tag. Identify the largest drivers: log groups by ingested bytes, metric namespaces by series count, expensive queries and canaries. Fix at the source: reduce log levels and payload logging, remove high-cardinality metric dimensions in favour of EMF log fields, sample traces and set Transaction Search indexing percentages, move passive logs to Infrequent Access or direct-to-S3 delivery, set retention everywhere, replace per-resource alarms with query alarms and template dashboards. Introduce observability tiers by service criticality and per-team budgets. Protect telemetry that drives paging alarms, SLOs and security detection, and review changes against the question of which incident would become undiagnosable.

!!! question "Explain how the three parts of Section 7.3 combine to handle a gradual performance degradation caused by a growing database table."
    Performance optimisation practices should detect the trend first: Database Insights shows rising DB load from a statement whose plan degrades as the table grows, and capacity dashboards show the trend. If it is missed, the latency SLO burn-rate alarm from Part 7.3.1 fires as users are affected, with a slow burn producing a ticket before a fast burn produces a page. Part 7.3.2's enrichment responder attaches the top SQL and recent deployments; a CloudWatch investigation proposes the database as the likely cause. Mitigation may be an approved scale-up or read-replica routing; resolution is an index or partitioning change deployed through CI/CD and verified by a load test with production-scale data. The post-incident review adds a proactive alarm on DB load relative to vCPUs.

#### Troubleshooting Questions

!!! question "After a team increased a Lambda function's memory from 512 MB to 2,048 MB, latency improved slightly but the bill for that function tripled. What happened?"
    The function is probably I/O-bound or single-threaded beyond one vCPU: most of its duration is spent waiting on network calls or on a single thread, so four times the memory did not reduce duration proportionally. Cost is memory multiplied by duration, so cost rose almost fourfold while latency barely changed. Run Power Tuning or analyse `REPORT` lines by memory size, check traces for where time is spent, and choose the memory size on the cost-latency curve that meets the latency target; address the waits (parallel calls, caching, connection reuse) rather than memory.

!!! question "Compute Optimizer shows no recommendations for several EC2 instances and marks others as 'optimised' although they run at 5 per cent CPU. Explain possible reasons."
    Instances without enough metric history in the look-back period, or recently launched or changed instances, receive no recommendations. Instances in Auto Scaling groups may be analysed at group level. Some instance types or configurations are not supported. An instance at 5 per cent CPU may still be classified as optimised if another resource, typically memory reported by the CloudWatch agent, network or EBS throughput, is highly utilised, or if the preferences (headroom, excluded families) leave no cheaper option that meets its needs. Check enrolment, look-back settings, agent memory metrics and preferences.

!!! question "A load test shows p99 latency of 150 ms at 2,000 requests per second, but production p99 at 800 requests per second is 600 ms. Why might the test be misleading?"
    The test may not be realistic: an unrepresentative traffic mix (only cheap read endpoints), a small dataset that fits in cache or database memory, a warm cache that production does not have, missing authentication or payload sizes, or a staging environment with a different database class or configuration. It may measure only the load generator's view without the network path real users experience. Compare the operation mix, data volume, cache hit ratios and Database Insights load between test and production, and rebuild the test to match production behaviour.
